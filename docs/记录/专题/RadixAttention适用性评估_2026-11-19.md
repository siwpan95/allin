# RadixAttention 对 `allin` / `write` 的适用性评估与优先级规划

> **本文是 2026-11-19 的一次性记录，不作为约束。**

- 日期：2026-11-19
- 范围：`/allin`（治理仓）、`/repos/write`（网文创作工作区）
- 方法：外部技术调研 + 两仓代码实读 + 本机实测（耗时 / 体量 / 语料重复率）
- 证据脚本：`/repos/write/tools/repeat_probe.py`（零依赖、只读、可复跑；**他仓文件，非本仓链接**）
- 落点说明：**结论与证据随本仓留存，执行物留在被评的仓里** —— 探针是 `write` 语料分析工具，
  故入 `/repos/write/tools/`；本仓不承载项目源码（`SPEC-006 §3`）。

## 0. 一句话结论

**RadixAttention 本体对两个仓都没有帮助**——它是推理引擎内部的 KV 缓存复用技术，前提是"你自己在 GPU 上跑模型"，而两仓都是模型 API 的**消费方**，没有可优化的 prefill。

**但它的核心思想（同一段内容只应有一个身份、只该被计算一次）在 `write` 里照出了一个真问题**：全仓 3370 万字节语料中，存在大量**整档级重复副本**——`小说/`（废土旅法师）有 **81.0%** 的汉字被重复存放（846 段极大重复，最长单段 5326 字，即整章重复），且重复档**已经进入 PKM 索引**。这一项的收益（检索质量 + 索引体积）比任何推理优化都大一个量级。

> 判据：**值得做的是"语料副本治理"，不是"推理优化"。**

## 1. 技术基线：它是什么，需要什么前提

| 项 | 事实 |
|---|---|
| 定义 | SGLang 提出的 KV 缓存管理技术：把所有请求的 KV 缓存按 token 前缀组织进一棵**基数树（radix tree）**，相同前缀只算一次、存一份，后续请求命中即复用 |
| 关键机制 | 前缀查找（O(k)）／节点分裂／**LRU 淘汰叶节点**／**cache-aware scheduling**（按最长共享前缀优先组批，理论可逼近最优命中率） |
| 论文收益 | 相对 vLLM/TGI 等，吞吐最高 **6.4×**、延迟最高降 **3.7×**；命中率实测 50%–99%（论文 v2） |
| 收益来源 | **并发批处理**下的大量共享前缀。单请求场景只体现为 TTFT 下降，不体现为吞吐 |
| 2026 现状 | SGLang v0.5.21（2026-10-02），前缀缓存已换 **Rust 内核并默认启用**；2026-08-11 发布 **Unified Radix Cache**（一棵树统一 Full/SWA/Mamba 复用规则）；**HiCache** 三层（GPU L1 / Host L2 / Mooncake·3FS L3）；**Session-aware Eviction**（按 `session_id` 优先保留活跃会话缓存） |
| **硬前提** | **必须有自己控制的推理服务**（GPU 显存 + 模型权重 + SGLang runtime）。它不在客户端生效，也不对第三方 API 生效 |

**推论**：一个只调 `api.deepseek.com` 的项目，用不上 RadixAttention——它连 prefill 都不在自己手里。

## 2. 两仓的 LLM 负载事实（实读 + 实测）

| 仓 | 是否自己跑推理 | LLM 调用情况 | 实测 |
|---|---|---|---|
| `allin` | **否**。`platform/` 是零依赖 Node 进程编排（登记/启停/审计），`kernel/` 是 Cordis 服务图，`preset/allin` 只是 DSH 的声明式治理 preset | 仅 `deploy/graphrag/` 一处：GraphRAG 走 **litellm → OpenAI `gpt-4o-mini`**（外部 API），配 `cache: json`（GraphRAG 自带 prompt 级缓存）；语料由 `build_input.py` 从 git tracked 文件生成，已排除冻结历史树与 junction 别名重复 | 无本地推理 |
| `write` | **否** | **零 LLM 调用**：`tools/doc_review.py` 是纯规则引擎（八类检查），全仓 grep 无 `openai`/`deepseek`/`api_key`/`chat/completions` | 69 文件审校 **1.95 s**（≈28 ms/文件） |
| 本机硬件 | — | — | **RTX 3060 12 GB** |

这两个事实直接决定了判定：

1. 没有推理服务 → RadixAttention 无处安装；
2. `write` 的审校器是确定性的、毫秒级的，**本来就没有"重复计算"可省**（这一点顺带否掉了"给审校加增量缓存"的想法：69 文件 1.9 秒，缓存只会增加复杂度）。

## 3. 三层适用性判定

### L1 直接采用（本机自托管 SGLang + RadixAttention）——**否**

三条独立理由，任一条即足以否掉：

1. **质量不匹配**：RTX 3060 12 GB 现实可跑的是 7B–14B 量化模型；`write` 的审校是中文长文一致性判断，需要的是 552B MoE 级别的 `V4.1-Flash` 这一类模型。换小模型省下的推理成本，会被"审校质量下降、需人工复核"的成本反噬。
2. **收益结构不成立**：RadixAttention 的 2×–6.4× 来自**并发批处理下的共享前缀**。个人单机工作流并发度≈1，最多拿到 TTFT 改善（约 −37%，论文/实测口径），拿不到吞吐收益。
3. **可维护性倒退**：为一个"审校"需求引入 GPU runtime、模型权重、驱动/CUDA 版本约束，与两仓现有的"零依赖、换机即跑"工程纪律（`tools/README.md`「Python 内核零三方依赖」）正面冲突。

### L2 机制迁移（把"前缀复用"纪律用到 API 侧）——**理论成立，量级不成立**

API 侧确实有等价物：DeepSeek 自 2024-08-02 起**默认开启**硬盘前缀缓存，命中/未命中差价 **50×**（Flash：$0.003 vs $0.15 /1M，非高峰），并且每次响应都返回 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`，**可逐次审计**。规则严格：前缀完全匹配才命中，**开头改一个字节，后面全部 miss**。

但把量级算出来就不值得投入了：

| 项目 | 实测体量 | 折算 token（中文字≈1.5 字/token） | 全 miss 成本 | 全命中成本 |
|---|---|---|---|---|
| `write` 稳定前缀（README+工作区规范+分类表+模板 SOP+零件库 README+tools README） | 132,253 字节 | ≈ 3–4 万 | $0.005 | $0.0001 |
| `write` 全库 md | 1,846 文件 / 33,705,359 字节 | ≈ 730 万 | **≈ $1.13** | ≈ $0.023 |

**结论**：把全库冷跑一遍的输入费约 1 美元；即便把命中率从 0 拉到 100%，单遍最多省 **≈ $1.1**。这个量级不足以支撑"造一个前缀包工具 + 命中率审计器"的工程投入——那会是为 1 美元建一套基础设施。

（唯一会翻盘的情形：把 GraphRAG 抽取搬到**本地模型**。那时 prefill 从"免费的外部 API"变成"自己的 3060 算力"，RadixAttention 才从"无关"变成"决定可行性"。见 §8 触发条件。）

### L3 结构迁移（基数树作为"前缀身份"的判据）——**是，且查出真问题**

基数树解决的是"同一段 token 序列被算了多次"。把"token 序列"换成"汉字序列"，同一个判据就能问出一个更朴素的问题：**同一段内容，在你的仓里被存了几份？**

实测（`repeat_probe.py`，K=20，最短 40 字，覆盖去重后的极大重复段，全仓 11 个作品目录）：

| 项目 | 文件数 | 规范化汉字 | 极大重复段 | 被重复覆盖 | **重复率** |
|---|---|---|---|---|---|
| `小说/`（废土旅法师） | 309 | 1,858,289 | 846 | 1,504,568 字 | **81.0%** |
| `格物录` | 9 | 43,079 | 21 | 34,325 字 | **79.7%** |
| `点子库` | 306 | 858,214 | 323 | 626,005 字 | **72.9%** |
| `提交确实未创建` | 196 | 626,826 | 126 | 32,792 字 | 5.2% |
| `廓者未名夜` | 25 | 108,946 | 54 | 5,242 字 | 4.8% |
| `蜀山之撼天凡蚁登天路漫漫` | 132 | 1,031,736 | 176 | 48,709 字 | 4.7% |
| `华夏克苏鲁` | 41 | 467,155 | 128 | 13,331 字 | 2.9% |
| `综网废柴逆命` | 69 | 151,589 | 23 | 2,492 字 | 1.6% |
| `创造主们的战争` | 9 | 39,739 | 2 | 178 字 | 0.4% |
| `霜语` | 59 | 137,164 | 5 | 402 字 | 0.3% |
| `十三叩_U-1990` | 43 | 50,108 | 1 | 90 字 | 0.2% |
| **合计** | **1,198** | **5,372,845** | **1,705** | **2,268,134 字** | **≈ 42.2%** |

最长的单段重复达 **5,326 字**——即整章内容在 `正文五卷-整合版.md` 与 `第五卷/第216章_下舰.md` 中各存一份。

**这不是笔误，是结构**。重复全部来自同一模式——**"派生整档"与"分档"并存**，只是各项目命名不同：

| 项目 | 派生整档 | 对应分档 |
|---|---|---|
| 小说 | `正文五卷-整合版.md` | `第一~五卷/第XXX章_*.md` |
| 点子库 | `05-实体书/正文/卷一.md`、`05-实体书/小册-*.md` | `02-正文/*.md` |
| 格物录 | `原稿/*-原稿.md` | `正文/第01章_*.md`、`设定与参考/` |
| 提交确实未创建 | `bible/40-章节细纲/第001-030章.md` | `bible/40-章节细纲/第XXX章.md` |
| 蜀山 | `_正文施工规格-V3-卷三.md` | `_正文施工规格-V3-卷三-施工单部分.md` |

问题不在文件存在（合订本有阅读价值），而在**下游口径没有为它们标注身份**：

1. **索引冗余**：`PKM/index.json` 的 1,613 篇里明确含 `小说/正文五卷-整合版.md` 与 `蜀山之撼天凡蚁登天路漫漫/正文/_正文施工规格-V3-卷三-施工单部分.md` 两个派生整档。索引里同一段正文有两份，检索排序会让"合订本切片"和"单章"互相竞争，命中粒度不稳定（拿到的可能是合订本里的第 216 章，而不是 `第五卷/第216章_下舰.md`）。
2. **图谱污染**：`PKM/graph.json` 的 2,574 条链接里，派生档与源章各贡献一份出链/入链；孤立率与枢纽度都会被这份冗余扭曲。
3. **抽取双份**（若将来把 `write` 接入 GraphRAG 式索引）：同一段内容被 chunk 两次，实体与关系各抽一遍，图里出现重复节点/边——这正是 `allin/deploy/graphrag` 的 `build_input.py` 已经用「只取 git tracked + 排除 junction 别名」防住的那类问题，`write` 侧还没有对应防线。

> 对照价值：`allin` 侧其实**已经把这件事做对了**——`build_input.py` 用 git tracked 取文件、排除冻结历史树与 junction 重复，`preset/allin/refresh-gov-block.py` 更是把"治理段三份副本必须字节一致"做成了带退出码的检查。`write` 缺的正是同一套"身份纪律"。

## 4. 优先级规划

| 级别 | 事项 | 判断 | 依据 |
|---|---|---|---|
| **P0** | `write` 语料副本治理：给派生整档标注身份，索引口径排除或降权 | **做**。成本低、收益确定、可验证 | §3-L3 实测全仓 ≈42.2%；5 个项目重复率 >4%；两个派生档已进索引 |
| **P1** | 修审校侧的「派生件豁免」口径（`DUP-CROSS` **已存在**，缺的是豁免族） | **做**，已随 P0 一并完成 | 原判断有误，见 §9 订正：`check_duplicate` 早就有跨文件比对，只是 `is_aggregate` 只看文件名、漏了 4 族 |
| **P2** | 前缀纪律（稳定内容前置、易变内容后置、同批沿用同一会话） | **顺手做，不专门造工具** | §3-L2 单遍上限 ≈ $1.1；DeepSeek 已默认缓存，harness 已经是追加式会话 |
| **P3** | 本机 SGLang 自托管 + RadixAttention | **不做**，留触发条件 | §3-L1 三条理由 |
| **P4** | 自建"前缀包 + 命中率审计"工具 | **不做** | 为 ≈$1/遍 的收益建基础设施，投入产出不成立 |

## 7. 失效条款（何时需要重估本结论）

本判断建立在"两仓不跑推理、模型走外部 API"这一时点事实上。出现下列任一情形，须重估：

1. **GraphRAG 迁本地模型**（隐私/离线/成本原因）——L1 判定从"否"变为"需评估"，RadixAttention 直接决定 3060 上的可行性；
2. 审校从"规则引擎"改为"本地小模型批量推理"——同上；
3. 语料规模跨过 **5,000 万字**（当前 3,370 万字节）——L2 的美元量级才可能变得可观；
4. 模型供应商**取消自动前缀缓存**或改为"写入收费"模式（OpenAI/Anthropic 就是写收费+读折扣）——L2 的纪律价值上升；
5. SGLang 出现**消费级显卡 + 单请求**场景的显著收益证据（当前证据集中在并发批处理）。

## 9. 执行记录（2026-11-19 · 放行后）

### 9.1 订正：原报告有一处判断错误

§4 的 P1 原写「`doc_review.py` 现只有段内重复」——**这是错的**。
`check_duplicate()` 早已实现 `DUP-CROSS`（跨文件 ≥36 字完全重复，带 2% 覆盖率门槛、Top N 截断），
并且已有「合集/导出件豁免」概念 `Corpus.is_aggregate`。

真实缺口比原判断窄，但确实存在：`is_aggregate` 只看**文件名**、只认 10 个词，漏了
`合并稿` / `施工单部分` / 合订区间命名 / `05-实体书`·`原稿` 目录族。
后果是整档对整档的大段重复被当成真问题逐条报出，真正要看的跨文件回扣被淹没。

### 9.2 已落地（提交 `dc9d096`，origin + github 双远端 IN_SYNC）

| 层 | 改动 | 效果 |
|---|---|---|
| PKM 索引 | `Doc.derived` + `scanner.is_derived()`；命中文档跳过倒排与标题兜底表，保留在 docs/图谱 | 1,613 篇中 **15 篇**标为派生；`pkm search` 不再返回合订本切片 |
| 审校 | `Corpus.is_aggregate` 扩命名族 + 合订区间 + 导出/历史目录（目录判定前置到 `is_chapter` 之前） | 整档噪音不再进入 `DUP-CROSS` 告警 |
| 治理 | 元数据清单增 `derived` 字段（误判可 `false` 拉回，源文件不动） | 口径可人工接管 |
| 测试 | T1 夹具硬编码 `1224` 已失效（长期红）→ 改为就地自增现值；新增 **T6**「索引判派生 ⇒ 审校也认派生」8 例（含 4 负例） | `npm test` 由 4/5 → **6/6** |
