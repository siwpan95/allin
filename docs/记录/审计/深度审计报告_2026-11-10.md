#### S-1 registry `launch.command` 白名单放行解释器内联参数 → 等价任意命令执行

| 项 | 内容 |
| --- | --- |
| **位置** | `platform/packages/core/src/registry.js:62-76`（校验）、`platform/packages/core/src/registry.js:64`（首词白名单）、`platform/packages/core/src/launch.js:216-221`（执行） |
| **实测** | 用仓内真实模块 `commandProblems()` 复现：`bash -c id` / `sh -c whoami` / `python -c print(1)` / `node -e 1` **全部返回 `[]`（无问题，放行）** |

**代码原文**（`registry.js:62-76`）：
```js
const COMMAND_FORBIDDEN = /[;&|<>`$]|\r|\n/
const COMMAND_TRAVERSAL = /(^|[\\/])\.\.\.([\\/]|$)/
const COMMAND_HEAD = /^(?:python|python3|pythonw|py|node|npm|npx|dse|ls|dir|echo|git|cmd|powershell|pwsh|bash|sh|robocopy|make|explorer|start)(?:\.exe)?(?:\s|$)/i
```
```js
// launch.js:216-221
  const child = spawn(prepareCommand(entry.launch.command), {
    shell: true,
    cwd: resolvePath(entry.path),
    detached: true,
    stdio: 'ignore',
  })
```

**为什么是问题**：该文件注释（`registry.js:59-61`）自称修的是「能写一份 yaml 就等同拿到任意命令执行入口」。修复只禁了 shell 元字符 `; & | < > \` $` 与 `..`，**未禁解释器的内联代码参数**。`bash` / `sh` / `python` / `node` 都在首词白名单内，而 `-c` / `-e` 不是元字符 —— 于是「一个受控程序 + 一个内联代码参数」完整穿过校验，随后被 `spawn(..., {shell:true})` 送进 shell 执行。

**影响**：任何能写入 `platform/registry/projects/*.yaml` 的主体（仓库 PR、被攻陷的发布区、经 MCP `registry.add` 起草后被人工搬运的草稿）可构造 `launch.command: bash -c "<任意载荷>"`，在门户 `/api/library/{id}/start` 或 CLI 触发启动时，以当前用户权限执行任意命令。`stop.command` 同样走 `shell: true`（`launch.js:281`）。

**联网依据**：OWASP OS Command Injection Defense Cheat Sheet 明确将「Avoid running `sh -c`, `cmd.exe` or `powershell.exe` with untrusted input」列为不可接受模式；且强调「Every OS Command Injection is also an Argument Injection」——本例正是**纯参数注入**形态，不含任何元字符。

#### S-2 registry `path` 字段无 `..` 校验 → 逃出仓库根，且 `launch.command` 在逃逸后的 cwd 下执行

| 项 | 内容 |
| --- | --- |
| **位置** | `platform/packages/core/src/registry.js:87-93`（`resolvePath`）、`registry.js:145-149`（`validateEntry`） |
| **实测** | `validateEntry()` 对 `path: ".."` / `"../allin"` / `"../../projects"` **返回 `[]`（零报错）**；`resolvePath("..")` = `D:\projects`，`resolvePath("../allin")` = `D:\projects\allin` |

**代码原文**（`registry.js:87-93`）：
```js
export function resolvePath(p) {
  if (!p) return p
  if (path.isAbsolute(p)) return p
  return (p === 'repos' || p.startsWith('repos/'))
    ? path.resolve(WORKSPACE_ROOT, p)
    : path.resolve(ALLIN_ROOT, p)
}
```

**为什么是问题**：`validateEntry` 只用 `RX_DRIVE`（禁盘符）检查 `path`，**完全没有 `..` 遍历检查**——`COMMAND_TRAVERSAL` 只作用于 command 字符串，与 path 无关。`resolvePath` 也不做边界收敛。

**影响**：
1. 把项目启动/探测的 `cwd`（`launch.js:218`）指向仓外任意目录（如用户主目录、系统目录），配合 S-1 即为「在任意 cwd 下执行任意命令」。
2. 门户读取文件时使用该路径（`platform/apps/portal/src/index.js:187`：`path.join(resolvePath(e.path), 'data', 'divergence-events.jsonl')`）⇒ 构成**任意文件读取**（文件名固定，目录可逃逸）。

**联网依据**：CWE-22 / CWE-23 —— 路径构造未收敛到受限目录；CWE-22 缓解措施明确要求「Use a built-in path canonicalization function that produces the canonical version of the pathname, effectively removes ".." sequences」+「Assert containment」。

#### S-3 repocheck 单条规则崩溃 ⇒ 该规则从判定中消失 ⇒ `--fail-on error` 仍返回 0（假绿）

| 项 | 内容 |
| --- | --- |
| **位置** | `tools/repocheck/rulebase.py:183-189`（异常捕获）、`tools/repocheck/scanner.py:259`（兜底）、`tools/repocheck/scanner.py:337-344`（`evaluate_fail_on`） |
| **实测** | 构造 `findings=[]` + `rule_errors=[1 条]`，`evaluate_fail_on(..., 'error')` → **0**；`'warn'` → **0**；`'any'` → **0** |

**代码原文**（`rulebase.py:183-189`）：
```python
        try:
            res = rule.check(ctx)
        except Exception as exc:  # noqa: BLE001 - 单条规则异常不应毁掉整次扫描
            result.errors.append({
                "id": rule.id,
                "label": rule.label,
                "error": f"{type(exc).__name__}: {exc}",
            })
            continue
```

**为什么是问题**：规则抛异常时被记入 `result.errors` 后 `continue`，**不产生任何 Finding**。而 `evaluate_fail_on` 只遍历 `r.get("findings", [])`，`rule_errors` 完全不参与判定。`report.summarize` 同样得到 `errors=0`。

**影响**：`scripts/run_all_gates.sh:314`（monorepo 口径）与 `:320/:328`（子件口径）都用 `--fail-on error` 跑 repocheck。**任一规则内部崩溃（编码 bug、权限错误、依赖缺失）都会让该规则静默失效，门禁照常报绿。** 更糟的是异常信号在**三处同时消失**：退出码（0）、严重度计数（errors=0）、评分分母（`report.py:252-253` 注明「已从评分分母剔除」）。这是「本该失败的检查显示通过」——本仓治理体系的核心信任基础。

**联网依据**：Bandit B110 / B112 的官方文档指出吞异常「represents a potential security issue. A larger than normal volume of errors from a service can indicate an attempt is being made to disrupt or interfere with it. Thus errors should, at the very least, be logged.」；CWE-703（Improper Check or Handling of Exceptional Conditions）。fail-closed 是安全门禁的基本要求。

#### H-1 portal 顶层 async handler 无 try/catch 且无 `unhandledRejection` 钩子 ⇒ 单条坏 registry 数据即可让门户整体下线

| 项 | 内容 |
| --- | --- |
| **位置** | `platform/apps/portal/src/index.js:201`（`http.createServer(async (req,res)=>{...})`）、`:214`（`await libraryPayload()`）、`platform/packages/core/src/probe.js:83` |

**为什么是问题**：`http.createServer` 的 async handler 抛错**不会**被 Node 捕获；`portal/src/index.js` 中**没有 `process.on('unhandledRejection')`**（实测全文仅有 `process.on('exit', ...)`）。触发链：registry yaml 里 `port: not-a-number` → `probePort(Number('not-a-number'))` → `net.connect` **同步**抛 `ERR_SOCKET_BAD_PORT`（`sock.on('error')` 只覆盖异步 error）→ `Promise.all` reject → `libraryPayload()` reject → async handler 抛出。

**影响**：Node ≥15 默认 `unhandledRejections=throw` ⇒ **整个 portal 进程退出（exit 1）**，客户端收不到任何 HTTP 响应（挂起至 socket 关闭）。**一个写错的 yaml 就能让门户整体下线**——这是可用性维度的高危。

**联网依据**：Node.js 官方语义 —— 自 Node 15 起默认 `--unhandled-rejections=throw`，未处理的 Promise 拒绝会作为 uncaught exception 抛出，进程以退出码 1 终止。

#### H-4 `allin_cli.py` 未命中分支静默返回 `None` ⇒ 映射为退出码 0

| 项 | 内容 |
| --- | --- |
| **位置** | `allin_cli.py:45-50`（`_exit_code`）、`allin_cli.py:104`（`return None`） |

**代码原文**：
```python
def _exit_code(rc):
    if isinstance(rc, int):
        return rc
    if hasattr(rc, 'returncode'):
```
