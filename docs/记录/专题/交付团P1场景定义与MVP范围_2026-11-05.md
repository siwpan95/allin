## 0. 一句话场景定义

**全哥（独立开发者一人团队）在单一本机工作区里，通过一条治理命令、一个 loopback 门户和一份双形态治理 Agent 文本，把 138 个 Gitee 仓的登记、体检、启停、门禁、官网与备份从「分散的三套面」收敛为「一键贯通、全绿可验证」的自治工作区——不引入付费 LLM 运行时、不公网暴露、不多人协作。**

## 1. 问题定义

### 1.1 目标用户画像（三类，非多租户）

| 用户 | 是谁 | 使用动机 | 使用频次 | 关键诉求 |
|---|---|---|---|---|
| **U1 全哥本人（主用户）** | 独立开发者，一人团队，多机检出（3 台接入机器） | 日常治理自己的 138 仓组合：启停项目、跑门禁、改文档、推送发版、维护官网 | 每天 | 一次命令全绿；少记路径/端口；故障可从日志恢复；换机可重建 |
| **U2 他仓采用者（潜在）** | 想复刻这套治理模式的他人（对外 Wiki 已存在） | `pip install allin-governance` → `init` 拿到可跑的最小治理骨架 | 偶尔 | 十分钟上手；init 产物 exit 0；文档能看懂 |
| **U3 访客** | 通过 Gitee Wiki / GitHub Pages 门面站 / website 官网了解 allin 的人 | 读方法、看产品、留联系方式 | 被动 | 页面可达、内容不泄漏（明文不落盘） |

**重要定性**：U1 占需求的 90% 以上。凡是「为 U2/U3 优化而增加 U1 维护负担」的需求一律降级或不做。

### 1.2 核心场景（3 个）

**S1 日常治理巡检（U1，每天）**
> 全哥在任一接入机器上，想知道 138 仓组合「现在健康吗」：跑 `bash scripts/run_all_gates.sh` + `npm run check:governance`，期望全绿 exit 0；发现红项时能一眼定位是哪道门禁、哪个文件、哪条规则。

**S2 三面贯通编排（U1，开发/重构时）**
> 全哥改了治理事实（如新增一门禁、改 registry、加 website 功能），需要：kernel CLI（执行面 A）能调起 platform 工具与 preset 校验；platform 门户（执行面 B）能看到 kernel/platform 状态；website（对外交付物）冒烟 19 项全绿；Agent 双形态文本同步无漂移——四件事目前各面独立，需要一条端到端冒烟把它们串起来验证。

**S3 本机常驻与灾备（U1，开机/换机/事故后）**
> 全哥希望 website 等常驻服务开机自启、进程守护、日志留痕、数据与密钥有备份；换机或密钥丢失后，能按文档一步步恢复到 verify:crypto 10/10 + smoke 19/19 全绿。

### 1.3 现有替代方案与痛点

| 现状能力 | 已有 | 痛点（来自 README 实证） |

| Agent 双形态 | verify-mount.ps1 漂移层 + check:governance | 同步判据存在，但「15 个专项 skill 路由」的实际命中情况无台账可查 |

## 3. MVP 范围

### 3.1 本期必做（Must）—— 「贯通可验证」最小闭环

1. **M1 端到端三面冒烟（`smoke:e2e`）**：一条命令串 CLI→kernel→platform 门户→website→Agent 漂移判据，证据落 JSONL。这是北极星，SC6。
2. **M2 门禁覆盖缺口收口**：核实 README ⚠ 2026-11-01 承诺的三条（体检 B)、ps1 BOM、repo_hygiene --all）确实在 run_all_gates.sh / CI 双路执行，复测 exit 0（防「写了不跑」复发）。
3. **M3 双形态同步判据双路拦截**：verify-mount.ps1 漂移层接进 CI（若尚未接）；漂移输出可定位。
4. **M4 website 密钥灾备演练落地一次**：备份→恢复→verify+smoke 全绿，记录落 docs/记录/（登记 INDEX.md）。
5. **M5 skill 路由台账的门禁化最小版**：15 个专项 skill 存在性/入口可读性校验进 check:governance（Could 部分——若工作量超 1 天则降 Should，【待确认】工作量）。

### 3.2 本期应做（Should）

- website 开机自启 + 崩溃守护 + 日志轮转（机制选型交系统架构师，P1b）。
- platform 库页对 kernel 能力的只读状态透出（最低成本形态：状态卡片，非完整控制面）。
- allin-governance 0.0.0a3：init 产物在干净机器复验 + wiki「一条命令上手」口径对账。

### 3.3 本期可做（Could）

- skill 路由命中统计台账（谁在什么场景被命中）。
- 端到端冒烟的 CI 定时复跑（防长周期漂移，借鉴「B) 红了 30 天」教训）。
- PORTFOLIO.md 刷新脚本接入门禁（数字口径防漂移，SPEC-204 迁移教训）。

### 3.4 本期不做（Out of Scope）与原因

| 不做项 | 原因 |
|---|---|

## 4. 人机边界（智能体场景设计）

本升级**不引入运行时 LLM**；Agent 双形态是「文本注入的治理大脑」。边界划法：

| 环节 | 执行方 | 理由 | 兜底策略 |
|---|---|---|---|
| 门禁全量执行（19 道 + docs_index + repocheck + hygiene） | **确定性代码**（run_all_gates.sh / npm scripts） | 可重复、零歧义，绝不该交给 Agent 判断 | 门禁红了 → exit 非 0，Agent 只读输出做解释与路由 |
| 端到端冒烟 smoke:e2e | **确定性代码**（脚本串探活） | 验收必须可机械复跑 | 任一检查点失败 exit 1 + 指名失败面 |
| 治理放行判断（该不该改这个文件、要不要登记 INDEX.md） | **Agent（双形态文本）** | 高不确定性、需要读四事实源做上下文判断 | 判据钉死：改 docs 必登记 INDEX.md，否则门禁红——机器兜底拦「Agent 判断错」 |
| 专项任务执行（部署修复、发版、体检） | **Agent 路由 → 15 个专项 skill** | 匹配到即转交不重造 | 路由台账门禁化（M5）拦「skill 消失/腐化」 |
| 双形态文本同步 | **人工改一侧 + 判据脚本拦另一侧** | 文本语义无法自动等价改写，只可机器判漂移 | verify-mount.ps1 漂移层 + check:governance 双路 |
| 密钥灾备执行 | **确定性代码**（backup-key/restore-key） | 事故链路必须零即兴 | fail-loud：恢复后必跑 verify+smoke（SPEC-106 §6） |
| 端口/进程启停 | **确定性代码**（platform launch/probe） | 并发与进程安全不该由 Agent 即兴 | 优雅停止→树杀回退；端口未登记拒绝登记 |

**原则**：能用规则解决的不上模型。本期 Agent 只做「读事实源→判断→路由→解释」，全部落点动作由门禁与脚本硬编码兜底。
