# 参与与反馈

> 这个项目**只有一个人维护**，而且它的主要用户也是 AI。
> 所以下面写的是我真实能兑现的承诺，不是模板里的客套话。

---

## 一、三种通道，用哪个

| 你想说 | 去哪 | 期望 |
| --- | --- | --- |
| **跑不通**（装不上、命令报错、门禁莫名其妙地红） | [Issues](https://gitee.com/siwpan/allin/issues/new) → 选「跑不通 / Bug」模板 | 最优先。这是我最缺的信息 |

> 只有公开 issue 里的讨论会被长期保留。私信我会看，但不会成为决策依据 —— 因为下一个人搜不到。

## 二、提 issue 前，请先做这三件事

1. **贴出版本**：`allin-governance --version`
2. **贴出你跑的那条完整命令**，以及它的完整输出（含退出码）
3. **贴出环境**：操作系统、Python 版本、有没有 Node（`node --version`）

如果报错里有 `UnicodeEncodeError` 或 `charmap`，请顺手贴一下 `echo $PYTHONIOENCODING`（Windows 上是 `$env:PYTHONIOENCODING`）—— 这类问题我在自己的 CI 上栽过两次，有固定套路可以查。

### 一个特别有价值的反馈：第一次跑的两分钟

> **你在 `init` 之后、第一次跑 `npm run check:governance` 之前，卡了多久？卡在哪？**

这个问题对我比"能不能跑通"更重要。因为到目前为止，跑通过这套东西的人**只有我自己**，而我知道所有答案 —— 我不知道一个不知道答案的人会在哪里停住。

如果你愿意，把这两分钟的原始过程（包括你以为要装什么、实际要装什么、哪一步的输出看不懂）写在 issue 里。这类反馈会直接变成文档的修改。

## 三、提 PR 之前

**约定只有四条：**

1. **一次 PR 只做一件事。** 混着改的 PR 我没法复核，会要求拆。
2. **改判据要连带改自检。** 任何动了 `gates/*.py` 的 PR，必须让 `--selfcheck` 仍然 `caught ≥ 1`、`misreports == 0`。只改判据不加自检的 PR 会被拒。
3. **不要直接改「快照文件」。** `tools/gate/governance/` 下的东西是从 `packages/allin-governance` 生成出来的；直接改会在下次 `init --force` 时被覆盖。想长期保留，就把它做成**你自己的门禁**（新 id、新脚本、新注册条目、写进 `RULES.md`）。
4. **文本编码**：所有文本文件用 UTF-8 + LF。仓库里有 `.gitattributes` 钉着，别绕过它。

**跑一遍再提交：**

```bash
bash scripts/bootstrap.sh          # 建 venv + 装依赖 + 建文档别名（幂等）
bash scripts/run_all_gates.sh      # 20 道门禁 + 自检 + 仓库体检
```

`run_all_gates.sh` 最后一行是「全部门禁通过。」才算干净。

## 四、我会怎么回

诚实版本：

- **跑不通 / 文档有歧义**：通常 1–3 天内回。这类我最积极，因为它暴露的是产品问题。
- **功能建议**：会回，但可能只是"记下了"。这个项目的纪律是**冻结新功能、先把已有的做扎实**（见 `docs/记录/审计/` 里的方向修正记录）。
- **纯夸奖**：谢谢，但不占用回复额度。

**不会发生的事**：我不会为了留住贡献者而接受一个我不打算维护的功能。宁可拒绝，也不留一个没人管的开关。

## 五、许可

**MIT-0**（MIT No Attribution）。没有署名要求，商用、改、闭源分发都可以，不用问我。

如果你想在自己仓库里放一份改过的门禁，最省事的方式不是 fork 这个仓库，而是：

```bash
pip install allin-governance
allin-governance init my-repo
```

然后改你仓库里那一份 —— 那是你的，不是我的。

## 六、它现在最需要什么

按价值排序，只有三条：

1. **陌生人第一次跑的真实卡点**（最有价值，见第二节）
2. **哪条判据在你那儿是误报** —— 误报比漏报更伤，因为它训练人忽略门禁
3. **你用一条退出码解决过什么重复问题** —— 这类故事比功能请求有用，它会变成新的门禁
