## 二、整合目标（用户拍板的方向）

**一个综合引擎**：以 alloy 为唯一引擎宿主（它已有 ECS + 可逆装配 + WorldLog + sync/dump 纪律 + 6 个内联副本生态），把"引擎类能力"收敛为它的**子系统**；其余引擎类项目降级为"应用/内容层"或"外部库"。

目标形态（草案）：

```
alloy（唯一综合引擎）
├── core/            ECS + EventBus(emit/waterfall/serial) + Context + WorldLog（唯一运行时）
├── world/ systems/ combat/ ai/ render/ audio/ fx/（既有游戏域）
├── media/           【整合新增】公式引擎 + CA + 粒子/流体 + JSON 内容层（自 pywallpaper 并入）
│                    —— pywallpaper 降级为"壁纸应用"：内联 alloy 引擎 + 自身效果 JSON + patch
└── audio 层         bloodmusic 维持外部库引用（版本化依赖，不吞并）
```

**三条整合纪律**（沿用此前确立的）：
1. 每个子系统独立更新（插件化）；
2. 不盲目整合（应用项目保持独立，只收敛"引擎内核"）；
3. 统一端口（媒体/音频服务的端口已在端口分配表）。

## 三、联网调研补充（已检索，结论摘要）

1. **Bevy（bevy.org / bevy-cheatbook 核心架构）**：社区公认的"一切皆插件"引擎样板——App + Plugin（build(app) 注册系统/资源/事件）+ 系统集（SystemSet 排序）+ 跨切面关注点靠插件边界；与本仓库 alloy 三件事 / Cordis 簇同构，**是整合后的 alloy 子系统组织参考**。
2. **Godot 模块化**（gamedev.stackexchange 相关讨论）：核心引擎 + 模块（rendering/audio/physics）+ GDExtension 外置扩展——"单引擎多领域"的成熟形态：内建模块收能力、外置扩展留生态。
3. **社区整合教训（gamedev.stackexchange）**：多引擎合并的共识风险 = ECS/组件类型双轨导致身份分裂（本仓库 G:\game 曾踩 Position 类身份坑）、双份生命周期/事件系统互相打架、公共设施重复（timing/asset/logging）。**对策与现状一致：唯一 ECS + 唯一事件总线 + 唯一 Context，能力以子系统/插件接入。**
4. 调研明确**不做**：不为合并引入 C++/Rust 重写（Python 生态与复制优于共享哲学不变）；不做 Godot 式二进制模块（成本远超收益）；不学 Bevy 的 Rust 借用体系（只借组织形态）。
