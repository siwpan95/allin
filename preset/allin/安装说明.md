# `allin` preset —— 工作区治理模式的 0.1.7+ 声明式载体（创造模式兼容）

> **这是什么**：本目录把工作区治理模式（"开卷必读四份事实源 + 三条铁律 + 本机边界"）
> 落进 DeepSeek Harness `@deepseek-ai/dsh-root` **0.1.7+** 的**声明式 preset** 机制。
> 那段治理 persona 原本只活在运行中的 DSH 部署内、未入任何 git；0.1.7 把承载它的
> `packages/preset/agent-presets/` 整包移除、改为声明式注册表 —— 升级即失。
> 这里存的是**能原样重装**的声明式补丁，把"单点"变成"可复原"。

## 一、`allin.patch.yml` 是什么（恒等式，可复核）

```yaml
- insert:
  - id: preset-allin
    name: '@deepseek-ai/dsh-agent-preset'
    config:
      id: allin          # ← 独立 id（不是 cordis），挂不上时自动降级到工厂预设
      order: 5
      plugins: [...]     # 与出厂 cordis.patch.yml 同序同形的完整 capability 集
```

**恒等式（可复跑证明）**：本 preset 的 `config.plugins` 与 shipped
`packages/bundle/web-app/presets/cordis.patch.yml` **同序同形**，唯一差异是
`persona` 的 `prefix` 末尾追加了一段治理段（`<!-- GOVERNANCE:BEGIN -->` … `<!-- GOVERNANCE:END -->`）。
⇒ 把治理段删掉，本文件应逐行等于出厂 cordis 声明（除 `id: allin` 与 `order`）。

**为什么是"插入一行 `@deepseek-ai/dsh-agent-preset`"而不是目录副本**（详见 doc §4.2.4）：
声明式 preset 的注册表**不扫目录、也不接受 preset 路径**；新/覆盖一个 preset = 往 profile 装一个
bundle 补丁，里面插一行 `@deepseek-ai/dsh-agent-preset`（新 id）或按该行 id 覆盖（改既有）。
这正是"原有**创造模式**（creator/cordis 声明式 preset 编写）"的落地方式 —— 在对话里也能等价编写。

**为什么 id 必须叫 `allin`（不叫 `cordis`）**：同名 id 由靠前根赢；叫 `cordis` 会被随包那份压住永不生效。
作为独立 id，工厂 `cordis`/`standard` 始终在；**本 preset 挂不上时会话自动降级到工厂预设**（见第五节）。

## 一之一、治理段路径自适应（去符盘 · 跨机零配置）

治理段的「开卷必读」四份事实源（`docs/MEMORY.md` 等）**不再写死盘符**——换机克隆后由
agent 在运行时**自发现仓根**，无需改任何路径。

> **为什么不能靠 DSH 展开环境变量**：`@deepseek-ai/dsh-persona` 的 `prefix`/`suffix` 是模板，
> 仅在 `renderPrompt()` 阶段**严格插值已注册的 prompt 变量**（`{{cwd}}`/`{{model}}`）；
> `{{env.ALLIN_ROOT}}` 这类**不被支持**（原样残留或丢段）。故自发现交给 agent 自己跑，
> 不依赖 DSH 改版 —— 也抗上游破坏性变更（与独立 gitee 仓同源）。

**定位仓根协议（persona 前缀第 3 步，命中即用，按序）**：
1. 环境变量 `ALLIN_ROOT` 已设且其下 `docs/MEMORY.md` 存在 → 用之（最快，推荐每台机设一次）；
2. 会话工作目录 `{{cwd}}` 跑 `git rev-parse --show-toplevel`，结果下 `docs/MEMORY.md` 存在 → 用之；
3. 否则运行随 preset 附带的 `locate-root.ps1` —— 它用**自身位置 `$PSScriptRoot`** 反推仓根
   （脚本恒提交在 `allin_push/preset/allin/`，故 `../../` 即仓根），**零配置跨机可用**；
4. 仍失败 → 用 `tool-fs-search` 搜 `allin.patch.yml` 定位 preset 目录，仓根为它的 `../../`。

**`locate-root.ps1`**：分层 `ALLIN_ROOT → git toplevel(cwd) → 向上走 → $PSScriptRoot/../../ →
搜 $PROJECTS_ROOT/$HOME/各逻辑盘`；命中即打印仓根并缓存 `$DSH_HOME/.allin_root`。
**不含任何硬编码盘符字面量**（逻辑盘动态枚举），通过 `scan_hardcoded.ps1` 门禁；
bundle 已一并打包它（`make-bundle.ps1` 自动拷），`dsh plugin add` 后 agent 也能找到。

**`verify-mount.ps1` 现加两道运行期门禁（② 续）**：治理段含 `[A-Za-z]:[\\/]` 硬编码盘符 →
**FAIL（exit 2，运行期强制铁律 5）**；并跑 `locate-root.ps1` 断言四事实源存在（缺失 WARN）。

## 二、安装（三选一，推荐 1）

### 路径 1 · 声明式 bundle（持久，推荐）

把 `allin.patch.yml` 包成一个 npm bundle 包，再用 `dsh plugin` 装进 web profile：

```powershell
# ① 建包目录（任选位置，例如 preset/allin/bundle）
$dir = 'preset/allin/bundle'
New-Item -ItemType Directory -Path $dir -Force | Out-Null
# ② bundle 的 patch 文件 = 本目录 allin.patch.yml（内容直接拷过去）
Copy-Item 'preset/allin/allin.patch.yml' (Join-Path $dir 'cordis.patch.yml') -Force
# ③ 写 package.json（dsh.bundle.patch 指向该 patch）
@'
{
  "name": "allin-agent-preset",
  "version": "0.1.0",
  "private": true,
  "dsh": { "bundle": { "patch": "cordis.patch.yml" } }
}
'@ | Set-Content (Join-Path $dir 'package.json') -Encoding UTF8
# ④ 装进 web profile（pnpm 在后台跑；首次会从本地路径 link）
dsh plugin --profile web add $dir
```

> ⚠️ CI 提醒：bundle 是 `allin.patch.yml` 的派生副本，改了源必须重跑 `.\make-bundle.ps1` 刷新（或 CI 跑 `.\make-bundle.ps1 -Check` 拦截落后），否则装进去的是旧治理段；`make-bundle.ps1` 会一并把 `locate-root.ps1` 打进 bundle，使跨机自发现随安装包走。

### 路径 2 · 启动 overlay（临时，零安装）

每次启动 Web 时带 `--patch`，不改 profile 持久状态：

```powershell
dsh web --patch 'preset/allin/allin.patch.yml'
```

> 适合"先验证、不污染部署"；缺点是要写进启动别名/快捷方式才持久。

### 路径 3 · 直接写进 profile 用户层（持久，最直接）

把 `allin.patch.yml` 整份（即那个 `- insert:` 块）**追加**到 profile 用户层：

```
%USERPROFILE%\.dsh\profiles\web\cordis.patch.yml
```

（`$DSH_HOME` 未设时默认是 `%USERPROFILE%\.dsh`；该文件是 profile 自己的覆盖层，随启动合成。）

## 三、装完必做两件事

1. **重启 DSH**，然后在 Web GUI 的 **设置 → Agent presets** 里确认出现「`allin`」卡片
   （persona 描述应带【工作区治理·铁律】）。
2. 把它设为默认：设置里 `agent-presets.default: allin`
   （当前部署此值通常是 `cordis`）。**改完只影响之后新建的会话**，本会话不变。

**回滚**：把 `agent-presets.default` 改回 `cordis`，或直接卸掉 bundle / 删掉追加的 insert 行。
两者互不影响 —— 因为 `allin` 是独立 id，工厂预设永远在兜底。

## 四、校验（推荐跑 `verify-mount.ps1`）

本目录附 `verify-mount.ps1`，做三层校验并给兜底指引（UTF-8 带 BOM 运行）：

```powershell
# 默认：自动发现已安装补丁 + 源文件，校验合法性/治理段/与随包 capability 漂移
.\verify-mount.ps1
# 额外跑一次免启动合成层检查（验证 profile 能解析）
.\verify-mount.ps1 -Boot
```

退出码：`0=PASS`（已挂且治理段完好） / `1=WARN`（挂上了但有上游漂移风险） / `2=FAIL`（没挂上）。
校验项：① 安装层（三种路径都能发现）；② 结构层（YAML 合法 + `GOVERNANCE:BEGIN/END` 完好）；
② 续（铁律 5 去符盘）：治理段含 `[A-Za-z]:[\\/]` 硬编码盘符 → **FAIL（exit 2）**；并跑
`locate-root.ps1` 断言四事实源存在（缺失 WARN）；③ 漂移层（比对随包 `cordis.patch.yml` 的
capability 集合，allin 引用了随包已不存在的 plugin id/name 就预警「上游破坏性变更」）。

## 五、已知边界 / 破坏性变更响应（无法挂载怎么办）

| 项 | 事实与处置 |
| --- | --- |
| **独立 id = 自动降级兜底** | `allin` 是独立 id（非 `cordis`）。DSH 升级若破坏性变更导致本 preset 挂载失败（注册表拒绝），**会话自动降级到工厂 `standard`/`cordis`** —— 部署不崩，只是该会话无治理段。 |
| **挂载失败怎么发现** | `dsh --dump-config` 是**免启动合成**、不挂载 preset，不能证明运行时挂载成功。真要确认须实跑一次 `dsh web`：看 Web GUI 设置里 `allin` 卡片是否出现、新建会话首条回复是否带【工作区治理·铁律】。 |
| **破坏性变更指纹** | 上游重命名/移除 plugin（`!!js` 失效、`{{var}}` 非法、YAML schema 漂移）→ 新会话绑不上 `allin`。`verify-mount.ps1` 的漂移层会在升级后第一时间报警。 |
| **独立 gitee 仓的意义** | `siwpan/deepseek-harness` 即为此而建：上游破坏性变更只动我们的 **pin**，不动源；比对 shipped `cordis.patch.yml` 即可定位漂移点，按 `docs\DSH升级与插件不兼容_2026-09-24.md` §六 检查清单回放补丁、核对 capability SHAPE。 |
| **上游仅作参考 + PR 前确认无冲突** | 官方 `github.com/deepseek-ai/deepseek-harness` 只作 SHAPE 核对 / 漂移定位的**参考对象**，不直接 fetch 进部署；其更新经 PR 合入主干前须确认与 allin overlay **无冲突**（`verify-mount.ps1` 漂移层作判据之一）。完整纪律见 `docs\DSH升级与插件不兼容_2026-09-24.md` §八。 |
| **治理段内容滞后** | 段内只列了铁律 0/1/2；`docs\MEMORY.md` 若新增铁律，以 `MEMORY.md` 为准、同步改 `allin.patch.yml` 的治理段。 |

**升级后回放补丁的最小动作**：
1. 跑 `.\verify-mount.ps1 -Boot`，看是否 FAIL/WARN；
2. 若 WARN（漂移），用 `/projects/deepseek-harness-master/packages/bundle/web-app/presets/cordis.patch.yml`
   与 `allin.patch.yml` 比对 `plugins` 差异，按新 capability 集更新 `allin.patch.yml` 后再重装；
3. 若 FAIL（没挂上），先 `agent-presets.default` 回退 `cordis` 恢复可用，再修补丁。
