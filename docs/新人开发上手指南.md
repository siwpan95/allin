# 治理系统上手指南

> **这份文档写给谁**：想把「这套治理模式」搬到自己工作区的人 —— 无论是接手本工作区的新人
> （人或 AI 协作者），还是看到公开仓后想复刻这套做法的外部开发者。
>
> **一句话**：本仓（`allin`）是一套**为「一个人 + 多个 AI 协作者 + 上百个仓库」设计的、
> 可执行、可审计、事故驱动**的工程治理模式。它的核心不是文档写得多漂亮，而是
> **每条规矩都有事故来源、每个断言都有可复跑的证据、每次改动都留下可追溯的账**。
>
> **它不是什么**：它不是「某个游戏引擎」，也不是「一堆项目的集合」。
> 那些项目各自独立成仓、公开 + MIT；**本仓是管它们的那个中枢**。
> 换句话说：**repos 是被治理的对象，allin 是治理本身 —— 而 allin 自己现在也住在 repos 里**
> （2026-11-23 起，`<工作区>/repos/allin`）。这条变化不是搬家，是**取消特权视角**：
> 门禁对别的仓要求什么，对 allin 自己也一样要求。此前两条腿走路时，
> 治理规则越写越细、被管对象纹丝不动，右腿迈快了必然扯着左腿 —— 现在只剩一条腿。
>
> 📌 本仓文档契约：所有 `docs/` 下的文档都必须在 [`docs/INDEX.md`](INDEX.md) 登记。
> 本文件已登记为 `HUB-06`；本文的策略背景见 [`docs/记录/审计/allin自身做大做强方向修正_2026-10-31.md`](记录/审计/allin自身做大做强方向修正_2026-10-31.md)（REC-AU-21）。

## 第 0 章 · 10 分钟上手

> **目标**：在一台**没装过任何东西**的机器上，10 分钟内让本仓的门禁全绿。
> 这一章是全文的**唯一硬承诺**，其余章节都是它的展开。

### 0.1 三条命令

```bash
# ① 克隆（公开仓，匿名可 clone）
git clone https://gitee.com/siwpan/allin.git
cd allin

# ② 一条命令建环境：建 .venv + 装依赖 + 重建文档别名 + 打印下一步
bash scripts/bootstrap.sh

# ③ 跑全部门禁（期望：末行「全部门禁通过（环境不适用 N 项已如实标注，不计入通过）。」、退出码 0）
bash scripts/run_all_gates.sh
```

> **关于克隆到哪**（2026-11-23 起）：生产布局是 `<工作区>/repos/allin` —— 本仓自己
> 就是被管的仓之一。克隆到任意目录都能跑（②③ 不看位置），差别只在 `g17-registry`
> 的**发布区完备性检查**：它按「父目录名是 `repos` 则取父目录，否则 `<本仓>/../repos`」
> 定位发布区。布局不符时它会报 `SKIPPED (not a pass)` —— 那是「没检查」，不是「通过」，
> 别把它当成绿灯。要指定别处用 `ALLIN_REPOS_ROOT=<路径>`。

**Windows 用户注意**：第 ② 步需要 **Git Bash**（或 WSL）—— `.sh` 脚本在 `cmd` 里跑不了。
如果你更习惯 PowerShell，等价路径是（**系统自带的 PowerShell 5.1 即可，无需 PowerShell 7**）：

```powershell
# 手动版 bootstrap（Windows 自带 PowerShell 5.1 可跑）
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
powershell -NoProfile -ExecutionPolicy Bypass -File tools/gate/make_doc_aliases.ps1
```

> 🔒 **2026-11-11 本机实测订正**：本机**已装 PowerShell 7**（`pwsh` **7.6.6**，在
> `C:\Program Files\PowerShell\7\pwsh.exe`，PATH 上可直接调用）。
> `bootstrap.sh` 因此走 **`pwsh` 分支**（输出「已用 make_doc_aliases.ps1 重建」），
> **不再**落到「未找到 pwsh，跳过别名重建」那条老路上。
> 🔒 **2026-11-22 二轮订正（@`KQABATS`，本机无 `pwsh`）**：旧版脚本缺 `pwsh` 时落
> `cmd mklink /J` 兜底，**中文真身目录编码必败**（⇒ bootstrap exit 1，见 FAQ 24）——
> 「mklink 兜底能让别名建出来」的说法**不成立**。已修为 **pwsh → powershell 5.1 → mklink**
> 三级回落：**装不装 PowerShell 7 都能把别名建出来**（PS5.1 路径实测通过），
> mklink 兜底只对真身目录为 ASCII 的仓可靠。
> 不要用 PowerShell 5.1 硬跑**别的** `.ps1` 代替，见 FAQ 第 4 / 16 / 17 条（别名脚本例外，见上）。

### 0.2 三种终端下的命令差异

| 目的 | 🪟 cmd | 🐧 Git Bash / WSL | 💙 PowerShell 7 |
| --- | --- | --- | --- |
| 治理 CLI | `allin.bat tools skills` | `.venv/bin/python allin_cli.py tools skills` | `.\.venv\Scripts\python.exe allin_cli.py tools skills` |
| 跑全部门禁 | （用 Git Bash 跑 `scripts/run_all_gates.sh`） | `bash scripts/run_all_gates.sh` | `bash scripts/run_all_gates.sh`（仍需 bash） |
| 单道门禁 | `npm run check:governance` | 同左 | 同左 |

### 0.3 怎么判断「装对了」

跑完第 ③ 步，你应当看到（**逐字对照**，这是本仓的验收基线）：

```
governance: 20/20 gate(s) clean
...
----------------------------------------
ALLIN_GATE_SUMMARY status=clean fail=0 skips=0 not_applicable=0
全部门禁通过（环境不适用 0 项已如实标注，不计入通过）。
```

且**退出码为 0**。如果看到的是 19/20 或任何一条红的，先看 FAQ 第 2 条
（最常见原因是解释器不一致 —— `PATH` 上的 python 没有 PyYAML）。

> 🔒 **2026-11-11 订正**：末行括注是 2026-11-08 深度审核 A3 引入 `not_applicable` 单列后加的
> （见 `scripts/run_all_gates.sh` 第 507–521 行），**旧版文档写的「全部门禁通过。」已不是逐字基线**。
> **稳定判据以 `ALLIN_GATE_SUMMARY status=clean` + 退出码 0 为准** ——
> 括注里的 `N` 会随本机环境变化（`not_applicable` 项数），别去盯它。

> **这一章是 2026-10-31 新增的**：在此之前本仓**没有** bootstrap 脚本，
> 新人只能从报错信息反推该装什么（`pyyaml` / `watchdog` 是从 `_cordis_locate.py`
> 的报错提示里猜出来的）。补齐这条链路的实测记录见
> [REC-AU-21](记录/审计/allin自身做大做强方向修正_2026-10-31.md) §七。

### 1.2 它解决什么真问题

一个人管上百个仓库，不是「不会写代码」，而是这七件事会塌方 —— **本工作区全都真实发生过**：

| 塌方 | 真实表现 |
| --- | --- |
| **事实源分裂** | 同一件事在 README、文档、聊天记录、脑子里各有一版；新人（或新的 AI 会话）拿到的是旧版 |
| **改动不留账** | 改完只在本地，或提交信息写「更新」；三个月后没人知道为什么这么改 |
| **假绿** | 验证脚本打印 `[PASS]` 但退出码是 0；只看重定向输出不看真控制台 |
| **门禁靠自觉** | 「记得别写死路径」—— 没有可执行的门禁，等于没有约束 |
| **冗余误判** | 按同名判定「A 已并入 B，可删」→ 删掉了 B 里没有的功能面（本工作区真删错过一次） |
| **许可失控** | 第三方 GPL/CC BY-SA 资产混进 MIT 公开仓，或反过来把必须 GPL 的仓「补成 MIT」 |
| **AI 协作者放大错误** | 一次错误的口径会被 AI 高速复制到几十个仓 —— 所以治理必须**机器可校验**，不能靠记忆 |

> **一句话结论**：**给人看的规矩要变成给机器跑的门禁，给机器跑的门禁要有给人看的账。**

### 2.1 运行时

| 运行时 | 最低版本 | 查自己版本 | 依据 |
| --- | --- | --- | --- |
| Python | `>=3.12`（内核） / `>=3.11`（repocheck） | `python --version` | `kernel/pyproject.toml`、`tools/repocheck/pyproject.toml` 的 `requires-python` |
| Node.js | `>=22.18` | `node --version` | 根 `package.json` 的 `engines.node` |
| Git | 近期稳定版 | `git --version` | — |

> 🔒 **建议用版本管理器**（`pyenv` / `nvm` / `mise`）锁定版本。本仓门禁对解释器敏感
> —— 见 FAQ 第 2 条，这是本仓最常见的假红来源。

**2026-11-11 实测现值**（`@SIWPAN` 机，`hostname` = `siwpan`）：PATH 上的 `python` 为 3.13.14、
Node 22.22.2、Git 2.55.0；`bootstrap.sh` 的候选探测命中 `python3.12`（**3.12.13**），
本次**复用已有 `.venv`**（**3.12.13**），`run_all_gates.sh` 也把该解释器钉给整批门禁。
`packages/allin-governance/pyproject.toml` 的 `requires-python` 为 `>=3.11`。
⇒ 三者都满足最低版本；**关键是整批用同一个解释器**，不是挑最高版本。

> 🔒 **注意「哪个 Python 是哪个」**：`PATH` 上的 `python` 是 **3.13.14**，
> 而仓内 `.venv` 是 **3.12.13** —— **两者不同是正常的**（`.venv` 由 bootstrap 当时的候选决定）。
> 判定口径只看**门禁实际用的那个**：跑批日志里 `governance: python X via <路径>` 那一行
> 就是本批钉住的解释器。它不同 ≠ 出问题；**同一批里前后不一致才是问题**（FAQ 第 2 条）。

**为什么门禁对解释器这么敏感**：门禁套件（Node 写的 `run.ts`）与 Python 写的工具
若各用各的解释器，同一次跑批的结论就不可复现。`run_all_gates.sh` 的做法是
**优先 `ALLIN_PYTHON` → 仓内 `.venv` → PATH 探测**，并且把选中的解释器
`export` 给整批门禁用。

### 2.4 终端纪律（🔒 本仓特有坑）

- `.ps1` 脚本**建议用 PowerShell 7（`pwsh`）**跑；PowerShell 5.1 会把无 BOM 的
  中文注释读成乱码并报假语法错（`check_ps1_bom.py` 门禁保证本仓脚本带 UTF-8 BOM）。
  🔒 **2026-11-11 实测订正**：本机**已装 PowerShell 7**（`pwsh` **7.6.6**，
  `C:\Program Files\PowerShell\7\pwsh.exe`，PATH 上可直接调用）。
  ⇒ `bootstrap.sh` 的 Windows 分支**优先走 `pwsh`**（实测输出「已用 make_doc_aliases.ps1 重建」），
  无 `pwsh` 时才回落到 `cmd` 内建 `mklink /J`（仍 exit 0，干净克隆也能建好别名）。
  实测 `pwsh -File tools/gate/make_doc_aliases.ps1 -Check` ⇒ **`ALIASES OK  4 个别名全部就位`**（exit 0）。
  🔒 **2026-11-11 S1 已修（现值）**：`allin_cli.py docs aliases` 改为
  「优先 `pwsh`、回落 `powershell`」，并捕获子进程输出**按字节自动探测编码**
  （UTF-8 / 系统 ANSI）后经 CLI 强制 UTF-8 的 stdout 写出 ⇒ 中文输出正常
  （实测 `完成：新建 0 个，异常 0 个。`，exit 0，见 FAQ 第 17 条）。
  ⚠ **只换解释器不够**：pwsh 7 在 Windows 管道重定向下同样按 ANSI(cp936) 输出中文，
  不解码回写仍然乱码 —— 这是 S1 第一版实测踩到的坑。
- `.sh` 脚本（`bootstrap.sh` / `run_all_gates.sh`）用 **Git Bash** 或 **WSL** 跑。
- **行尾由仓库说了算**：本仓有 `.gitattributes`，`*.sh` / `*.ps1` / `*.md` / `*.yml`
  一律 LF，`*.bat` / `*.cmd` 保持 CRLF。
  ⇒ **为什么**：本仓开发机 `core.autocrlf=true`，若无此文件，Windows 检出时 `.sh`
  会变 CRLF，Linux CI 检出是 LF —— 实测 CRLF 版本的 shebang 变成
  `#!/usr/bin/env bash\r`，直接执行报 `env: 'bash\r': No such file or directory`。

> `status=clean` 只表示「所有**适用**项都跑过且通过」，不等于「全绿已验证」。环境不适用项会在汇总单列，CI 里另有 warning 提示。

### 4.7 大模型 LLM 降级选择

本仓 MCP 工具面**全确定性、无 LLM 运行时**（真实模型调用在仓外编排层 DSH / WorkBuddy 执行）。这套确定性工具天然构成「模型不可用时的降级终点」——即使所有远程 LLM 不可达，25 个治理工具仍全可用。

降级三档（策略声明在 `preset/allin/allin.patch.yml` 的 GOVERNANCE 段，凭据槽位记在 `docs/事实源/模型凭据登记.yaml`，**只记槽位、不记值**）：

- **online**：主模型可达且会话预算未耗尽 → 正常调用主模型；
- **fallback**：主模型 429/5xx/超时，或预算耗尽 → 按 `priority` 切到次高优先级 fallback 模型；
- **offline**：全部远程不可达 → 走本地 Ollama（若有）或纯确定性 MCP 工具面。

可执行的决策层：`platform/apps/mcp/src/model_route.js` 的 `decideRoute()` 纯函数（零外部依赖、可单测）。两个只读 MCP 工具可直接查：

```bash
node platform/apps/mcp/src/index.js --selftest   # 含 model.route / model.fallback-catalog 自检
```

- `model.route`：返回当前降级档位决策（可传 `preferTier=offline` 做离线演练）；
- `model.fallback-catalog`：列出模型不可用时仍可完成的确定性任务清单。

可观测：每次模型降级决策会落到 agent trace 的 `degradation.tier` / `.reason` / `.fallback_from` 字段（见 `platform/apps/mcp/src/agent-trace.js`），便于事后复盘为何落到 offline / fallback。知识库 QA 的三档降级封装见 `deploy/graphrag/qa_wrapper.py`（`--selfcheck` 验证三档不崩；`full` 缺 `GRAPHRAG_API_KEY` / `facts.sqlite` 时自动降级，不假装 full）。

#### 4.9.1 发布区治理门禁（`publish_area_gate`）

#### 4.9.2 治理控制台（`console/`）

定位是**开发者治理控制台**，不是浏览器产品（契约见 [`SPEC-205`](规范/SPEC-205-allin-console契约.md) §0）。
Electron 只是承载方式；删掉所有网页标签页这个产品依然成立。

```bash

cd console && npm install

# 以下四个均可在仓根执行（根 package.json 有 console:* 转发）
```

3 个内置插件：`gate-reds`（门禁红项面板）/ `port-health`（端口健康）/ `registry-audit`（登记质量审计，命令 `registry.audit` + 面板 `governance.registry`）。

三条能力边界（照 `SPEC-205` 走，别扩）：
- **CLI 是唯一总线**：`info` / `version` / `selfcheck` / `launch` / `stop` / `logs`。

  「有 cli.py」≠「已接入」—— 148 条里只有 31 个真实现了 `info`。
- **启停不自己记 pid**：一律走 `@allin/core.startEntry/stopEntry`，与门户/CLI 共享 `running.json`。
- **插件只开三个扩展点**：`console.command` / `console.panel` / `console.on`，能力经 `ctx.deps` 注入，
  拿不到 `electron` / `fs` / `child_process`。

## 第 5 章 · 怎么改这套体系
### 5.1 协作两态（🔒 SPEC-002 §零）

| 模式 | 判据 | `git commit` | `git push` |
| --- | --- | --- | --- |
| **在场模式** | 本回合内有用户回应 | ✅ | ✅ 报一句「推什么」等放行 |
| **自主模式** | 无人值守推进 | ✅ **自主**（记账不等人） | ❌ **禁止** —— 攒着等在场 |

> 🔒 **推送在场前提（铁律 3）**：推送前必须用户在场并明确放行；推后务必
> `git ls-remote` 核对 `IN_SYNC`。**「没人看的时候推」是纯粹的多余动作。**
>
> 🔒 **高风险不分档**：推送 / 建仓 / 删除 / 密钥操作 / 仓库结构变更 —— **逐项确认后才做**，
> 不可逆动作绝不自主拍板。

### 5.2 提交规范

- **提交信息**：建议 **Conventional Commits**（`feat:` / `fix:` / `docs:` / `chore:` …）；
  本仓另用「记账」式引用（如 `REC-AU-18`、`SPEC-105`），改动若关联规范/记录请带上编号。
- 🔒 **借鉴必记账**：复制/借鉴任何外部代码、配置、概念前，记录「**来源 + 许可证 + 借用范围**」。
- 🔒 **新增 `docs/` 文档必须同批次登记 [`INDEX.md`](INDEX.md)**（§4.2 的文档索引契约门禁 D1/D8 强制）：
  加一行登记 + 更新头部与分类标题的**两处自述份数**，然后自查
  `python tools/gate/docs_index.py`。⚠ 这不是洁癖 —— 2026-11-08 曾有提交只落了 4 份审计文档、
  漏登索引，下一次任何人跑第 0 章就会主链全红（`g15` / `agent_regression` 连带红）。
- **提交前自检**：跑一遍相关门禁，确认全绿再提交（本仓 `.pre-commit-config.yaml`
  已挂 gitleaks 与基础钩子）。

### 5.3 提 PR / MR

本仓为单人开源作者模式；**外部贡献**走 Gitee Pull Request，规范见
[`SPEC-103`](规范/SPEC-103-社区协作规范.md)。评审重点关注 🔒：

- 是否过门禁（`npm run check` 是组合入口；**全量以 `bash scripts/run_all_gates.sh` 为准** ——

- 是否写死机器路径（`g01-paths` 会拦）
- 文档与索引是否同步更新（`g19-docs-refs` 会判文档里的命令与路径是否真实存在）
