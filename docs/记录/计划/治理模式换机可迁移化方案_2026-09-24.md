## 一、问题现象与结论

**现象**：新电脑上治理模式无法挂载；报错形如 `Cannot find package …` / `N row(s) did not activate …` / `… already registered` 之一（**原文待补**，见 §三）。

**结论先行**：这不是「挂载功能坏了」，而是三件事叠加：

| 层 | 一句话 | 性质 |
| --- | --- | --- |
| ① 机制层 | 上游已把 preset 从「目录式」改成「声明式」，`<dshHome>/.agent-presets/` 这条路**被有意取消** | 决定性 |
| ② 行层 | 本机 `allin` 是 rc.6 时代的副本，其中 `workflow-worker-thread` 等行在新版上已不存在/已改形 | 版本漂移 |
| ③ 坑层 | `tool-cordis` 的 Host inspect provider 是进程全局的，两个携带它的预设同进程 → 整个挂载被拒 | 已记档的老坑 |

**关键判断**：治理模式的**实体**从来只存在于本机私有目录，既不在任何 git 仓、也不在公开仓 `siwpan/allin`，也无脚本可生成；而它依赖的那套 DSH 机制本身又变了 —— 所以「拷过去就能挂」这个前提在新电脑上不成立。

## 二、三层原因（逐条实测）

### 2.1 机制层：上游把 preset 换成了「声明式」（决定性）

上游架构笔记的原话：

> 同时保留目录 preset 与声明。两个可写来源会争用标识，需要额外的优先级、迁移和编辑规则。普通 profile 配置已提供所需持久化和分层，**因此 preset 不再有独立路径**。
> —— `.agents/notes/implemented/architecture/2026-09-18-declarative-agent-presets.zh.md`

新版 registry README 的原话：

> 定义使用普通插件行；**注册表不扫描目录，也不接受 preset 路径。**
> —— `packages/preset/agent-preset-registry/README.zh.md` 第 46 行

新旧落地面对照（本机 vs 上游 master）：

| 维度 | 本机（rc.6 时代，`allin` 就是这个形态） | 上游现版 |
| --- | --- | --- |
| 发现方式 | 扫 `<dshHome>/.agent-presets/` 目录 | **不扫目录**，只认插件行 |
| 载体 | `agent.cordis.yml`（顶层行列表）+ `preset.yml` | 一行 `@deepseek-ai/dsh-agent-preset`，`config: {id, order, plugins: […]}` |
| 随发行版交付 | `apps/cli/config/agent-presets/<id>/` | `packages/bundle/web-app/presets/<id>.patch.yml` |
| 用户改动落盘 | 那个 preset 目录 | `$DSH_HOME/profiles/web/cordis.patch.yml` |
| 相关包名 | `@deepseek-ai/dsh-agent-presets`（复数） | `dsh-agent-preset` + `dsh-agent-preset-registry`（**复数包已不存在**） |
| 旧架构笔记 | — | 已移入 `.agents/notes/archived/architecture/2026-08-03-per-session-agent-presets.md` |

本机侧证据（2026-09-24 实测）：

- 预设实体：`/Users/13122/.dsh/.agent-presets/allin/` = `agent.cordis.yml`(18,625 B) + `preset.yml`(304 B) + `skills/`（2 个 `SKILL.md`），共 42 KB；
- 默认指向：`/Users/13122/.dsh/settings.yaml` → `agent-presets: default: allin`；
- 不在任何仓：`.agent-presets` 下无 `.git`，`.dsh` 本身也不是仓；
- 公开仓无产物：`git -C G:\allin ls-files` 只有 `docs/`、`audit-fragments/`、`LICENSE`、`README.md`、`.gitignore`、`目录索引.txt`；提到 preset 的仅 `docs/会话交接_2026-08-27.md` 里 5 处**绝对路径叙述**；
- 全盘无副本：整个 `G:\` 的 `*.yml` 搜 `allin 治理` → 0 命中。

> 旧机制的失败口径（供对照）：`preset "allin" not found (available: …)`（`dsh-agent-presets/lib/index.js:113`）；且默认值写入时不校验、**下次 `resolve()` 才失败**。

### 2.2 行层：30 行 vs 现版 34 行（逐行对照）

比对对象：本机 `allin`（rc.6 时代）↔ 上游 master `packages/bundle/web-app/presets/cordis.patch.yml`。

| 差异 | 内容 | 后果 |
| --- | --- | --- |
| **仅 allin 有** | `workflow-worker-thread` = `@deepseek-ai/dsh-workflow-worker-thread` | 该包上游**零命中**（`packages/workflow/` 现只剩 `workflow` / `workflow-ptc` / `tool-workflow` / `tool-ralph`）→ **`Cannot find package` 的头号嫌疑** |
| 仅现版有 | `preset-cordis`、`command-goal`、`workflow-ptc`、`present`、`tool-plugin-manager`（`@deepseek-ai/dsh-plugin-manager/tools`） | 治理版缺 goal 命令、成果物呈现、插件管理三块能力 |
| 同名行包名 | **30/30 完全一致** | 所以「找不到包」的现实候选只有 `workflow-worker-thread`，其余要怀疑**宿主安装不全**（见下） |

**配置形状漂移**（不是「等一会就好」，在新版上是配置非法）：

| 行 | 本机 allin | 上游现版 |
| --- | --- | --- |
| `persona` | `config.text:` | `config.prefix:` + `config.suffix:` |
| `tool-subagent`（产品行） | `enableRunInBackground: false` | `backgroundMode: one-shot` |
| `tool-subagent`（spawn 行） | 无 | 新增 `modelSelectionSettings: true` |
| `tool-web` | `fetch: false` | `fetch: true` |
| `tool-ralph` | 启用 | `disabled: true` |
| `skill-filesystem.customSkillDirs` | 指向 preset 目录的 `skills/` | 指向 `@deepseek-ai/dsh-agent-preset` 包内 skills |

**宿主安装完整性**（另一条 `Cannot find package` 的现实路径）：本机 `DEPLOY.md` 根因 4 记明，`--legacy-peer-deps` 会跳过全部 peer 解析，必须显式装两个外部 peer —— `@deepseek-ai/cordis-plugin-group`（缺则启动 `ERR_MODULE_NOT_FOUND`）、`node-addon-require-builtin`（纯 JS + 预编译平台二进制）。新电脑若走 `npm install` 而未补齐这两个，行会在导入期就失败。

**`N row(s) did not activate` 是另一类**：不是「找不到」，而是「包解析成功、依赖的 Host 服务没到」。本 preset 里 `tool-goal` / `tool-jobs` / `tool-web` / `tool-subagent*` 都消费 Host 服务（`goals` / `jobs` / `web` / `subagents` / `workflowEngine`），宿主组装一变、或 consumer 与 provider 落在不同 `isolate` 域，就会以 `waiting for <service>` 卡住。

### 2.3 坑层：`tool-cordis` 的进程级独占

`tool-cordis` 的 Inspect provider 注册进**进程全局**的 `cordisInspect`：同一进程内两个携带它的预设同时挂载 → `inspect provider "Service" is already registered` → **整个预设挂载失败**（上游现版 web patch 第 134 行仍在注释该事实）。

- 本机 `allin` 靠 `disabled: true` 规避（记档：`docs/会话交接_2026-08-27.md` 第 336 行）；
- 而上游现版 `cordis` preset 里 `tool-cordis` 是**启用**状态 —— 「到新电脑先复制一份 `cordis`」恰好把这个坑一起搬过去。

## 三、定位分支表（拿到报错原文即可定位）

**需要补的输入**：那台新电脑上的**一行报错原文**。按特征分支：

| 原文特征 | 归属 | 处置方向 |
| --- | --- | --- |
| `Cannot find package '@deepseek-ai/dsh-…'` | ①+② | 先看是否 `workflow-worker-thread`；否则查 §2.2「宿主安装完整性」两个外部 peer |
| `N row(s) did not activate: <id>: waiting for <service>` | ② | 定位 `<service>` 在新机由谁提供；多半是该行该挪进/挪出 `isolate` 域 |
| `… already registered` / `inspect provider "Service"` | ③ | 确认是否与 `cordis` 预设会话同进程；把 `tool-cordis` 行改 `disabled: true` |
| 预设根本不在选择器/名录里 | ① | 新机是现版：目录式**已被取消**，必须改走 §四 的 patch 声明 |

## 四、目标形态与交付物

### 4.1 形态转换（本方案的核心）

**从「拷一个私有目录」改成「发布一份声明 + 一个自检门禁」。**

- 旧：`<dshHome>/.agent-presets/allin/{agent.cordis.yml,preset.yml,skills/}` ← 新机上不被读取
- 新：profile 补丁里插一行 `@deepseek-ai/dsh-agent-preset`（`config.id: allin`，`plugins:` 列出治理版行）→ 落 `$DSH_HOME/profiles/web/cordis.patch.yml`，或由用户在 Web UI 的「Agent 预设」页编辑保存

### 4.2 交付物清单（拟落在 `siwpan/allin` 仓新增 `dsh/`）

| # | 文件 | 内容 | 验收标准 |
| --- | --- | --- | --- |
| 1 | `dsh/allin.patch.yml` | 一行 `@deepseek-ai/dsh-agent-preset`，`config.id: allin`，`plugins:` 从**目标机上现版 `cordis` preset 派生**（禁止再从本机 rc.6 副本派生 —— 这正是本次根因），含 `tool-cordis: disabled: true` | 在目标机 profile 上能挂载；`mounted OK` |
| 2 | `dsh/persona.md` | 治理精要投递正文（铁律/流程的**正文仍只在** `MEMORY.md` 与协作约定里，本文件只做引用） | 与 `MEMORY.md` 无第二条事实源冲突 |
| 3 | `dsh/install.ps1` | `$env:DSH_HOME ?? "$env:USERPROFILE\.dsh"` **动态定位**；写前备份 `cordis.patch.yml`；幂等；支持 `-DryRun` / `-Uninstall` | `-DryRun` 不落盘；重复执行结果一致 |
| 4 | `dsh/check.ps1` | 黄金值：① 目标文件存在且**用加载器方言**可解析（不能只 `ConvertFrom-Yaml`）② preset id 在名录可见 ③ 挂载校验回 `mounted OK` ④ 事实源路径逐一可达 | 退出码如实：0 干净 / 1 失败 / 3 环境错；人为破坏须变红 |
| 5 | `dsh/sync-rows.ps1` | **版本对齐门禁**（见 §五）：拉当前发行 `presets/cordis.patch.yml`，输出「本机行 × 现版行」对照，漂移即非 0 | 人为改一行包名须变红 |
| 6 | `dsh/README.md` | 装法、放哪、自检、回滚、已知坑（含 ③ 的进程独占） | 外部读者只读本文件能装成功 |

### 4.3 边界（不做什么）

- **不改随附 preset 安装目录**（`.../@deepseek-ai/dsh/config/agent-presets/`）—— 属部署，升级会覆盖；
- **不改 host composition**；治理模式只贡献一个 preset 声明；
- 修正治本方向仍是「随上游形态走」，不写补丁分支（治理准则：还原优于分支）。

## 五、版本对齐门禁（防复发）

`dsh/sync-rows.ps1` 的**第一份基线**就是本轮实测差异（直接抄进脚本做断言）：

1. `workflow-worker-thread` → `workflow-ptc`
2. 新增 `command-goal` / `present` / `tool-plugin-manager` / `preset-*`
3. `persona`：`text` → `prefix` + `suffix`
4. `tool-subagent` 产品行：`enableRunInBackground: false` → `backgroundMode: one-shot`；spawn 行加 `modelSelectionSettings: true`
5. `tool-web`：`fetch` `false` → `true`
6. `tool-ralph`：现版 `disabled: true`
7. `skill-filesystem.customSkillDirs`：改指 `@deepseek-ai/dsh-agent-preset` 包内 skills

同时记录新版硬约束：**用户覆盖替换整个子插件列表，不自动合并内置列表的未来更新** —— 所以「不对齐就跑门禁」这件事必须机械化，不能靠记性。

### 11.2 目录式机制「在」，但用户根有可用性前提

**用户根确实被扫描**，`allin` 进入了名单、`defaultId` 也正确解析。故 §4.2「必须改走 patch 声明」在本机**不是必需**。

但另有一条实测约束（本文未覆盖，须补记）：

- **扩展根的存在性在 host 启动时定死**：`AgentPresets` 构造函数只推导一次 `resolvedRoots`；`scanRoot()` 遇根目录不存在时 `ENOENT → return []`（**静默返回空、不报错**）。
  实测时序：host 启动 `14:07:00` ／ `.agent-presets` 创建 `14:47:23` → 相差 **40 分钟** → 该根全程返回空，预设不进名单。
- **`settings.yaml` 不校验名单健康度**：`agent-presets.default` 写什么就存什么，即使该 id 解析不了也**写入成功**。

### 11.6 归位结论（2026-09-24 盘位复核后，**本节覆盖上文 11.3 的定位判断**）

盘位复核发现：**旧机的 `F:`（大依赖盘）与 `G:`（项目盘）是两块外置 NTFS 盘，已原样接到本机**。

| 复核项 | 结果 |
| --- | --- |
| `G:\repos` | **107 个目录 / 107 个含 `.git`** —— 与文档记载逐数吻合 |
| `G:\` 目录契约 | `repos` `allin` `platform` `tools` `archive` `assets` `venvs` `notpython` `workbuddy` `job` `logs` `local` `tmp` `Temp` —— **一项不缺** |
| `F:\` 重工具链 | `Python314`(3.14.7) `node` `PowerShell` `mingw64` `VS2022` `ldyun`(ffmpeg) `calibre` `models` `venvs` —— 原样在 |
| `/tools/gate` | 原型门禁两件套在（`scan_hardcoded.ps1` 23,423 B、`check_undefined_names.py` 4,596 B、`audit\`） |

**因此：**

1. **「迁移」不是本方案要解决的问题** —— 工作区从未离开 `F:`/`G:` 这两块盘，换的只是硬件。
   本方案 §4.2 的交付物（`dsh/allin.patch.yml` 等）以及 §七 的"就绪清单"，**前提从"把工作区搬过去"改为"确认外置盘接上即可"**。
2. **`11.3` 的定位判断作废**：本机**不是**"迁移中状态"，而是「**旧工作区原样挂载在新硬件上**」。
   起因是我盘位盘点时只筛了 `DriveType=3` —— 外置 NTFS 盘同样报 `DriveType=3`，但被筛选条件漏掉。
   **纪律：枚举卷一律用 `Get-Volume` / `Win32_DiskDrive` 全量对照，先确认"盘到底有几块"，再下"缺什么"的结论。**
3. **唯一实打实的倒退是内存**（15.9 GB vs 旧机 32 GB）。
4. **§六 persona 变量化仍然成立且已完成**：persona 里的路径已从 `/local/...` 订正回 `G:\` 系列
