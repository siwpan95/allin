# 能力接缝作为治理边界（allin 侧，2026-10-26 并入后）

> **本文是 2026-10-26 的一次性记录，不作为约束。**
> 原则源自 DSH 架构笔记 `2026-06-17-filesystem-capability-seam`、`2026-08-09-cordis-event-walk-backstop`、`2026-06-11-structured-error-taxonomy`，按 allin 治理语境重构。

## 一、什么是能力接缝（capability seam）

一项"能力"（治理段向 agent 暴露的某个可操作面，如读文件、跑命令、调 LLM）应拆成**三个分包**，依赖方向单向：

```
Consumer（对外 API）  --依赖-->  Definition（接口/契约）  <--依赖--  Provider（实现/后端）
   模型面对的 tool 暴露              能力的词汇与契约                真正的执行体
```

- **Consumer 只依赖 Definition，永远不依赖 Provider**。换后端（本地→沙箱→远程→项目作用域）不改对外契约。
- 三个**独立演化**的关注点必须解耦：能力契约（能请求什么）、后端（现在本地、以后沙箱）、消费者 API（schema 与结果格式）。
- 反例：让对外 tool 直接 `node:fs`/`node:path`，等于把"执行策略、路径解析、原子写、文本解码、编辑语义"一次性耦合到 Consumer，换后端就改 schema。

## 二、为什么对治理段成立

`preset/allin/allin.patch.yml` 的 GOVERNANCE 块（经 `g14-preset` 守护）就是治理段的"能力清单"。把它当成接缝来设计，好处是：**治理契约**与**治理实现/后端**可以独立演化——例如"校验某文件是否在索引里"这条能力，其契约稳定，但实现可以从一次性扫描换成增量监听，对外（agent 看到的工具 schema）不变。

## 三、cwd ≠ 沙箱（关键反模式）

后端基目录只是**路径解析默认**，不是**隔离边界**。`cwd` 看起来像沙箱，其实只要后端契约或 `tools/execute` 策略不强制 containment，它就只是一层基础路径。结论：**隔离必须由后端契约或独立的权限/沙箱插件显式强制**，不能靠"给了个基目录"默认成立。

## 四、工作流策略不属于原始能力

观察态（read-before-write、observed-state）、所有权派生、节流等是**工作流策略**，应拆到独立策略插件（挂在能力的事件门上），不应活在能力本身。能力只持：后端铸造的版本令牌 + 可选的版本守卫（CAS）原语。

> 落到 allin：治理段里"先读后改""某 owner 的观察态"这类策略，不要写进 GOVERNANCE 块的基础能力，而应作为独立的策略校验层。

## 五、错误码是接缝的一部分

跨接缝的失败若被压成裸字符串，会丢 `name/code/stack`，下游重试/沙箱插件无法区分 `ENOENT` 与 `EACCES`。应有单一 `BaseError extends Error`：稳定 `code`（与 `message` 分离）、`cause` 链、`name` 默认取子类；跨接缝时结构化失败存活进日志供代码路由与回放。**但模型仍只见文本块**——结构化字段仅供代码与回放，不进模型历史。

> 收敛验证：allin 的 `govlib.Report`（kind/text/severity 结构化发现）已是同一思路的工程实例；本原则确认该设计正确，而非新发明。

## 六、原子写临时文件纪律

能力若涉及落盘（写文件、spill 文件），必须走：私有随机 `0700` 目录下放独占所有者临时文件（`'wx'` / `0o600`）→ 失败即清理 → 最终原子 `rename`。可预测的全局可读临时路径会招来 symlink 竞争与泄露。**这一条是接缝的硬性要求**，不是可有可无。

## 七、用独立扫描兜底"发现面"（cordis event-walk backstop 的治理类比）

DSH 的教训：能力/事件的"发现"靠投影（projection），但投影只走 host-face 可达文件——client-face 或不可达文件里的声明会**无声消失**，且没有任何东西报警。修法是给事件一套与 services **镜像**的独立扫描兜底，且两者都读**完整**源码树。

可迁移的治理原则：

1. **兜底必须与主投影独立失败**。主投影的可达性 bug 正是兜底要抓的，所以兜底必须是朴素的 AST/文档扫描，不共享主投影的 machinery。
2. **分区检查 fail-closed 双向**：未豁免的不可见项 = 错误；为"已渲染项"设的豁免 = 错误；没有任何合并声明的豁免 = 错误。
3. **策展豁免表**点名每一个"声明了但主投影看不到"的项，附原因与拥有它的 README。删掉一个活豁免就响亮失败并报告其名与声明文件；恢复后生成字节级一致——这反过来证明豁免恰好覆盖被扫面。
4. **可证伪**：删一个活豁免即失败，证明兜底真的在盯着。

> 落到 allin：`g00-meta` 对 registry 的独立校验、`g15-docs-contract` 对文档枢纽的独立扫描，正是这一原则的实例——它们独立于"门禁自身是否绿"地兜底治理面，fail-closed 且带豁免表（`RULES.md` §三/§四 的已机械化清单）。继续强化而非削弱这种独立性。

## 八、与现有门禁的对位

| 接缝原则 | 对应 allin 机制 |
| --- | --- |
| 能力 = Definition/Provider/Consumer 三分 | GOVERNANCE 块（契约） + 实际工具/后端（实现） + agent 工具 schema（Consumer） |
| cwd ≠ 沙箱 | `g01-paths` 拦写死绝对路径；隔离边界由权限策略显式强制，不由路径默认成立 |
| 错误码是接缝一部分 | `govlib.Report` 结构化发现；`g00-meta` 校验门禁自证输出 `SELFCHECK {caught,clean,misreports}` |
| 独立扫描兜底 | `g00-meta` / `g15-docs-contract` 独立校验治理面，fail-closed + 豁免表 |
| 原子写临时文件 | `g05-hygiene` 拦构建产物/字节码进仓；落盘纪律由工具自身保证 |

**判定口诀（给"给治理段加新能力"用）**：先写 Definition（契约与错误码），Provider 可换，Consumer 只依赖 Definition；隔离、策略、原子写三件事分别由后端/策略插件/能力原语各自承担，不要塞进一处。
