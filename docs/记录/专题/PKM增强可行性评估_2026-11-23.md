# allin 知识库（PKM）增强可行性评估（2026-11-23）

- **时点**：2026-11-23 23:59 ~ 次日 00:40
- **触发**：全哥「结合联网调研探讨为 allin 引入 PKM/知识库的可行性（其实也不算引入，更准确的说法是：**增强现有的相关技术**），并在确保 allin 相对干净的情况下按性价比完成推进」。
- **口径**：本文只评估「以最小新增面换最大可用性」。凡需要引入重依赖、在线服务、或让派生数据进仓的方案，一律先问「它比现有东西强在哪」。

## 零、结论先行

**allin 不缺知识库，缺的是「反向关系」。** 现有四层已经覆盖了从结构到检索的大部分需求，
本轮只补了一处真空，其余六项明确**不做**：

| # | 候选方案 | 成本 | 收益 | 结论 |
|---|---|---|---|---|
| 1 | 反向链接 / 影响面查询（`docs backlinks`） | 低（纯静态 150 行，零依赖） | **高**：改文档前知道波及谁 | ✅ **已落地** |
| 2 | 孤儿文档检测 | 低 | **零**（实测 0 孤儿，D1 已强制全量登记） | ❌ 不做 |
| 3 | 文档关系图可视化（Mermaid/SVG） | 中 | 低（单人团队，看图的频次远低于查影响面） | ❌ 不做 |
| 4 | SQLite FTS5 trigram 本地索引 | 中 | 中（但 MCP 已有 BM25，重复建设） | ⏸ 暂缓，见 §4 |
| 5 | 本地 embedding 语义检索 | 中高（模型 + 索引） | **低**（本仓专名密集，语义检索反而更差） | ❌ 不做，见 §3 |
| 6 | GraphRAG 全量索引 | 高（LLM 成本随语料线性） | 低（122 份语料远未到图检索的收益区） | ❌ 不做，骨架保留 |
| 7 | 引入 Obsidian/Foam/lat.md 等外部工具 | 中（工作流迁移） | 低（现有 D1–D17 已比它们严格） | ❌ 不做 |

## 二、本仓语料实测（2026-11-23，排除 junction 别名与冻结历史树）

```
真身文档      122 份
图内引用边    301 条（唯一 src→dst）
零入链文档    0 份   ← 关键：孤儿检测无收益
零出链文档    65 份
未解析链接    72 条  ← 多为 INDEX 的目录链接（D2 已豁免）与 .html 附属件
```

**「零入链 0」这件事直接否掉了两个方案**：
- 孤儿文档检测（候选 2）：没有孤儿可检。
- 「按链接补全 INDEX」类治理（隐含在候选 3）：D1 已强制每份文档登记，索引完备性由门禁保证。

若不排除 `docs/facts|records|spec|历史` 四个 junction 别名，同一份文档会被数两遍
（472 → 122 份的差异全在这里）。**做语料统计前先认别名**，否则所有数字都是假的。

## 三、为什么不选语义检索：本仓是「专名密集」语料

联网调研中最有价值的一条反证：某开发者对 14441 条书签做混合检索时发现，
**纯语义检索会对专名犯低级错误** —— 搜 `twscrape` 返回一堆通用爬虫工具，
唯独没有 `twscrape` 本身，因为嵌入模型把专名揉进了「网页抓取」这个语义球里，
字面唯一性被稀释。

allin 的文档满篇都是这种词：`g17`、`D12`、`SPEC-204`、`repos_root`、`ALLIN_REPOS_ROOT`。
对这类查询，**字面匹配（BM25 / trigram）是主力，语义检索是补充，不是替代**。
现有 MCP `docs.search` 用的正是 BM25 + 字段权重，方向本来就是对的。

⇒ 结论：引入本地 embedding 属于「花了钱把事情做差」，不做。

## 四、候选 4（FTS5 trigram）为什么暂缓而不是直接做

调研结论：SQLite FTS5 的 `trigram` 分词器对中文天然友好（按 3 字符滑窗，无需 jieba），
46,000 文件全库查询 1–40 ms。听起来很香，但对本仓有三处不划算：

1. **两字中文词搜不到**（trigram 不生成 2 字 token），必须补 LIKE 兜底 —— 而「门禁」「规范」
   这类两字词在本仓是高频查询。
2. **索引体积膨胀 3–5 倍**（实测值来自多方来源一致）。
3. **与 MCP 的 BM25 功能重叠**：同一批语料两套检索，口径必然漂移（本仓已被
   「两处计数各漂各的」教训过多次）。

⇒ 触发条件写在 §6：只有当 BM25 的实际检索延迟或召回质量成为瓶颈时才换，不是现在。

## 五、GraphRAG：骨架保留，不启动

`deploy/graphrag/README.md` 已把边界划得很清楚（规范/记录/adr 进图，事实源不进），
四模式、三档降级、citation 纪律、最小验收 5 条全部就位。**不启动的理由不是它不好，是时机不对**：

| 理由 | 依据 |
|---|---|
| 语料规模远未到图检索收益区 | Karpathy 2026-04 提出的 LLM Wiki Pattern 明确：**几百页以内 markdown + 链接路由就够，向量/图检索要到百万级文档才赢**；其实测 383 文件 + 100 会议记录，token 用量比向量 RAG 低 **95%** |
| 索引成本随语料线性 | GraphRAG 每个 TextUnit 至少一次 LLM 调用 + 每层社区摘要；122 份 / 196 万字的中文语料，成本与「问答命中率提升」不成比例 |
| 上游维护状态 | 微软官方 README 自陈已进入 "largely in maintenance mode"，定位 research demo |
| 本仓已有替代 | 单跳明细查询 BM25 足够；跨文档脉络问题用 `docs backlinks` + 交接卷足够 |

⇒ 保留骨架、保留 `build_input.py` 与 `qa.yaml`，**不装 graphrag、不建索引**。
触发条件见 §6。

## 七、本轮实际交付

`tools/docs_backlinks.py`（150 行，纯标准库）+ CLI `allin docs backlinks`：

```bash
python allin_cli.py docs backlinks SPEC-001     # 谁引用了它（带行号）
python allin_cli.py docs backlinks --hub        # 全图被引排行
```

**刻意不写盘**：122 份扫描 < 0.2 s，按需算即可。若生成反链页面，它自己也要被 D1 登记、
被 g15 判契约、被 g19 判链接 —— 为一份随时可重算的派生数据引入三处维护面，不值。

实测输出（SPEC-001）：

```
目标：规范/SPEC-001-铁律.md
  被引用 11 处 · 引用他文 1 处
  ← 谁引用了我（改动波及面）：
    INDEX.md:38
    MEMORY.md:14
    事实源/机器分区索引.md:24
    ...（共 11 处）
```

被引排行 Top3：`事实源/机器分区索引.md` 33 处、`记录/交接/2026-11.md` 27 处、
`事实源/组合分级决策索引.md` 12 处 —— 这三份是真正的「枢纽文档」，改动前必须先跑一遍反链。
