# TavernRogue 项目完成进度评估报告

> 评估基准：对照 `D:/allin/not/OK/TavernRogue/be like.txt` 中的初始方案（TavernRogue 2.0）
> 评估时间：2026-06-19
> 评估范围：代码、数据、UI 实现

---

## 一、总体结论

项目已经从一个**文字方案**推进到**可启动的 pygame-ce 图形界面原型**，核心场景（菜单、职业选择、招募、地图、战斗、商店、营地、事件、奖励、宝藏、结束）全部存在。然而，**实际可玩性和规则深度与方案仍有明显差距**：

- **表层完成度**：约 70%（界面、场景、数据文件、基础经济循环）
- **规则/战斗深度完成度**：约 40%（大量关键词、英雄技能、宝物效果在战斗中未生效或仅部分生效）
- **数据内容完成度**：约 45%（冒险者、敌人、宝物数量远低于方案规划，高星级内容几乎空白）
- **整体项目质量**：可运行，但存在多处功能性 bug 和状态不一致问题，需要一轮集中修复和补全才能真正“可玩”。

## 三、已实现的功能（可运行部分）

1. **图形界面启动**：`run_gui.py` 可成功启动，pygame-ce 初始化、字体加载、场景切换正常。
2. **12 个场景**：Menu、ClassSelect、Recruit、Map、Battle、Shop、Camp、Event、Treasure、Reward、GameOver、Victory 均存在且能渲染。
3. **5 个英雄职业**：基础类存在，战士/游荡者/法师技能在 UI 战斗中可直接使用。
4. **招募基础循环**：购买、刷新、部署、召回、出售、三连合成已能在 UI 中操作。
5. **铸币经济**：每回合 `3 + 层数` 铸币、上限 10、回合结束保留上限 5 已实现。
6. **地图生成**：9 层模板数据存在，地图节点随机生成，UI 可展示节点类型图标。
7. **营地训练**：休息和 +1/+1 训练可在 UI 中操作。
8. **商店购买**：冒险者和宝物可购买，价格按稀有度区分。
9. **基础数据文件**：冒险者 15 个、敌人 7 个、宝物 7 个、事件 5 个、地图模板 9 层均存在。
10. **战斗引擎雏形**：`BattleEngine` 可模拟简单的自动战斗，支持守卫、护盾、亡语（damage_random）、战吼（damage_random）、连击（FRENZY）。

## 四、主要 Bug 与代码质量问题

### 4.1 会导致运行时报错的 Bug

| 文件 | 位置 | 问题 | 影响 |
|------|------|------|------|
| `game/events.py` | 第 152-156 行 | `reics_data` 和 `reics` 变量名拼写错误（应为 `relics_data` / `relics`） | 事件选项“获得宝物”或“购买随机宝物”会触发 `NameError`，游戏崩溃 |
| `game/node_handler.py` | 第 25 行 | 使用了 `RelicSystem` 但没有 `import` | 当 `NodeHandler` 不传 `relic_system` 参数时创建失败；当前 `GameManager` 传了参数，所以游戏内不会触发，但模块本身不完整 |
| `ui/scenes/battle.py` | 第 149-157 行 | 玩家攻击逻辑完全手写，未调用 `BattleEngine`，也未处理剧毒、连击、亡语、战吼 | 关键词在 UI 战斗中几乎失效，游戏体验与方案偏差大 |
| `ui/scenes/battle.py` | 第 168-191 行 | 敌人攻击逻辑同样手写，未使用引擎，且只处理 ARMOR | 同理，关键词和效果丢失 |

### 4.2 状态不一致与数据模型问题

| 问题 | 说明 | 后果 |
|------|------|------|
| `GameManager.health` 与 `Hero.health` 未同步 | `GameManager` 自己维护 `health`，`Hero` 类也维护 `health` | 术士生命分流减少的是 `Hero.health`，UI 状态条显示的是 `GameManager.health`，二者会不一致；牧师技能、再生护符等也会错乱 |
| 招募系统的 `gold` 与 `GameManager.gold` 靠手动同步 | `sync_to_recruit` / `sync_from_recruit` 模式容易遗漏 | 一旦某个场景忘记同步，铸币显示和操作就会不一致 |
| 战斗失败惩罚不一致 | `BattleScene._defeat` 扣 `GameManager.health` 10 点；`node_handler` 扣 `Hero.health` 的剩余敌人攻击总和 | 不同入口受伤逻辑不同，玩家体验不可预期 |

## 五、架构评估

### 5.1 优点

- **分层清晰**：`game/` 负责纯逻辑，`ui/` 负责图形，符合方案中的 MVC+Scene 思路。
- **数据驱动**：冒险者、敌人、宝物、事件、地图均用 JSON，便于后续扩展。
- **场景生命周期统一**：`enter / draw / handle_event / update / leave` 模式避免了阻塞式循环。
- **战斗引擎可独立测试**：`BattleEngine` 不依赖 pygame，可单独运行和单元测试。

### 5.2 缺点

- **MVC 耦合**：`GameManager` 同时是 Model 和 Facade，持有所有子系统引用，但 UI 战斗场景直接绕过 `BattleEngine` 手写战斗逻辑，破坏了架构一致性。
- **状态重复**：health、gold、hand、board、relics 在 `GameManager` 和子系统（`RecruitSystem`、`Hero`）中重复存在，需要大量手动同步。
- **战斗双轨制**：`game/engine.py` 的自动战斗和 `ui/scenes/battle.py` 的手动战斗并存，二者规则不一致，导致关键词系统分裂。
- **错误处理薄弱**：多处“简化处理”注释，实际功能缺失或返回错误结果。

## 六、优先级修复建议

### 第一优先级：修复会导致崩溃的 Bug

1. 修复 `game/events.py` 中 `relics_data` / `reics` 拼写错误。
2. 修复 `game/node_handler.py` 缺少 `RelicSystem` import。
3. 统一 `GameManager.health` 与 `Hero.health`，确保所有扣血/回血操作修改同一来源。

### 第二优先级：让战斗符合方案设计

1. **决定战斗模式**：要么将 UI 战斗改为真正的自动战斗并调用 `BattleEngine`，要么重写 `BattleEngine` 以支持手动战斗所需的完整关键词结算。
2. 在战斗循环中完整接入：守卫、护盾、亡语、战吼、血怒、连击、剧毒、种族共鸣、宝物效果。
3. 实现“场上冒险者全灭后，敌方幸存者攻击英雄”的规则。

### 第三优先级：补全游戏循环与规则

1. 实现地图路径选择：每层只需选择一条路径完成，不必全清。
2. 实现宝藏密室进入条件（携带特定物品）或改为击败 Boss 后可选。
3. 补全术士生命分流在 UI 招募中的使用入口。
4. 补全牧师治疗祷言在战斗中的触发。
5. 在招募界面增加站位调整入口（拖拽或交换按钮）。

### 第四优先级：填充内容

1. 补充 4-6 星冒险者（至少再增加 15-20 个）。
2. 增加中层 Boss 和更多精英敌人。
3. 增加事件数量和事件效果类型（damage_all、start_battle 等）。
4. 实现局外成长：职业解锁、进阶难度、冒险日志、本地存档。

### 第五优先级：打磨与发布

1. 增加游戏内帮助文本和关键词说明。
2. 增加音效/粒子反馈（可选）。
3. 编写测试用例，特别是战斗关键词交互。
4. 使用 PyInstaller 打包为可执行文件。

## 八、结论

当前 TavernRogue 项目完成了**从方案到可运行原型的第一步**，界面框架、数据文件、基础经济循环和招募系统已经搭起来。但项目目前面临的核心矛盾是：**底层战斗引擎（`game/engine.py`）和上层 UI 战斗场景（`ui/scenes/battle.py`）是两条平行轨道**，导致方案中承诺的“自动战斗、关键词嵌套、种族共鸣、宝物被动”等核心深度没有真正进入玩家体验。

建议全哥先停下内容扩张，用** 1-2 周集中做一轮“规则对齐 + Bug 修复”**：

1. 修好两个崩溃级 bug；
2. 让 `BattleScene` 调用 `BattleEngine` 做自动战斗结算；
3. 统一 health/gold 状态模型；
4. 把 7 个宝物和 6 个种族共鸣在战斗中真正跑起来。

完成这一轮后，再补充 4-6 星冒险者和 Boss，游戏会立刻从“能点按钮”变成“能玩出流派差异”。
