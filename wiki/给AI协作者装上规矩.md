# 给 AI 协作者装上规矩

> 这篇讲的不是"如何管理代码仓库"，而是一件更窄的事：
> **当写代码的不止你一个人（还有 AI）时，怎么让"什么算合格"从一句口头约定，变成一条会红的退出码。**
>
> 文中每个数字都有实测来源，包括那些不好看的部分。

---

## 一、先讲一次翻车

我的仓库在本地是绿的。20 道门禁，20/20 clean，我每天跑，从来没红过。

然后我把它接上了 CI。第一跑，Windows 那个 job 就挂了。

报错是这样的：

```
UnicodeEncodeError: 'charmap' codec can't encode characters in position 2-3
```

不是逻辑错了。是我写的那个脚手架工具在打印中文提示：

```python
print(f"  新建 {len(plan.created)}；保留 {len(plan.kept)}；覆盖 {len(plan.overwritten)}")
```

Windows CI 的默认控制台编码是 cp1252，装不下中文。

最难受的地方不是崩溃，而是**它崩在打印阶段**：

- 43 个文件已经全部写好；
- 命令以 `exit 1` 结束；
- 用户看到"失败"，磁盘上却是成功。

工具的价值全在信号上。信号说谎，比功能缺失严重得多 —— 因为它会让你开始不信任何一次"绿"。

同一天里，CI 一共抓出**四**个我本地看不见的缺陷：

| 缺陷 | 本地为什么看不见 |
| --- | --- |
| `g00-meta` 从不读注册表里的 `platforms` 字段 | 我在 Windows 上，唯一那道 Windows 专属门禁恰好能跑 |
| 聚合运行器同样不读 `platforms` | 同上：它 "按平台跳过" 的前提从来没被触发过 |
| `g15` 用裸 `sys.exit(main())` 绕过公共入口，于是没做标准输出重配 | Linux 默认 UTF-8，根本不报错 |
| 三处调用门禁的入口都没先建文档别名 | 我本机有别名，克隆一份干净的才会有这个问题 |

四条，本地一条都复现不了。

所以"只有一台机器验过"，真正的含义不是"覆盖不足"，而是 **等于没验过**。

## 二、写在文档里的规矩，等于没有规矩

我做这套东西的起点，是一个很不体面的观察：

> 我的 `CONTRIBUTING.md` 写得很认真，但我自己从来没在提交前读过它。

这不是意志力问题。人不会在读一段散文之后，把它编译成一个 0/1 判断。而**门禁会**。

一条规则只有在能被写成下面这句话时，才算真的存在：

```
这条规则，在什么输入下，以什么退出码结束？
```

我这套门禁用的退出码词汇是固定的四档：

| 码 | 含义 |
| --- | --- |
| `0` | 干净 |
| `1` | 基线之外的新阻断 |
| `2` | 用法错误 |
| `3` | 环境错误（缺解释器、缺 git 工作树等） |

还有一条不写在码里、但同等重要的约定：

> **SKIP 不是通过。**

跑不了的判据必须自己打印 `SKIPPED (not a pass)` 并计数，不许静默返回 0。

这条最容易被人当成挑刺，但它救过我很多次。举个真实的例子：一道门禁需要判断"本机磁盘上的路径是否还存在"。在 Linux CI 上它根本没有语义 —— 如果它选择"什么都不做然后退 0"，那么 CI 上那道门禁永远是绿的，而它本该判的东西一次都没被检查过。**你得到的是安全感的幻觉，不是安全。**

## 三、最小可用治理的真实边界

大多数"我有一套治理方法"的文章，只讲他有什么。我更想讲**哪一部分不能通用**，因为这个信息对做工具的人更有用。

我的门禁一共 20 道。当我准备把它们打包成"一条命令生成的治理骨架"给别人的仓库用时，我在一个空仓库上把 20 道逐个跑了一遍。结果是：

- **15 道通过**；
- **5 道不通过**；
- 通过的 15 道里，还有 1 道不能出厂。

不能出厂的那五道，判的是**我自己仓库的资产**：

| 门禁 | 它判什么 | 为什么不能给别人 |
| --- | --- | --- |
| `g14-preset` | 我的编辑器插件配置里的治理段落是否成对、插件序列是否与出厂清单一致 | 别人的仓库没有这套插件配置 |
| `g15-docs-contract` | 我的文档枢纽四分类与 ASCII 别名 | 这是我的文档约定，不是通用契约 |
| `g16-skill-preset-parity` | 三处治理载体是否说的是同一套事实 | 三处载体都是我的 |
| `g17-registry` | 我的发布区台账与分级索引是否对得上 | 台账是我的 |
| `g19-docs-refs` | 我的文档里引用的路径是否都能解析 | 依赖我的目录结构 |

而那道"通过但不能出厂"的：

- `g18-exceptions` 需要一个 YAML 解析库（PyYAML）才能读例外台账；
- 而我对这个包的承诺是 **运行时零第三方依赖** —— 治理工具得能在什么都没装的机器上跑起来。

两件事冲突时，我选零依赖，把 `g18` 列为"按需自行添加"。

**这一步筛完，只剩 14 道。** 它们判的是任何仓库都成立的事：

> 凭据泄漏、写死的本机路径、`.gitignore` 是否覆盖密钥面、序号文件是否连续、
> 自称"事实源"的文档是否带观测时点、删文件是否留下接任者说明、
> 文本 I/O 是否显式声明编码、门禁被喂坏输入时是否会大声失败、
> 有没有读了却没定义的名字、`HEAD` 可达对象是否都读得出来、
> `docs/` 里有没有混进脚本、机器事实与实况是否还一致。

这就是"最小可用治理"的真实边界。它不是我删繁就简的结果，而是**一道一道跑出来**的边界。

如果你也在做工具，这个问题值得问自己一遍：**你的"通用能力"里，有多少其实是你自己的私有资产？**

## 四、三条设计约束，每条都对应一次教训

### 约束一：门禁脚本必须物理位于被治理的仓库里

我最初的设计不是这样。我想让门禁住在 pip 安装目录里，目标仓库只留一份配置，`npm run check` 去调安装包里的脚本。这样升级方便、零重复。

这个设计被我自己的门禁否决了。`g00-meta` 的第一条判据就是：

> 注册表里 `script` 字段指向的文件，必须**在仓库内存在**。

它自己的注释写着理由：**注册表不是愿望清单。**

进一步想，如果门禁住在 `site-packages`：

- `git log` 看不到判据的变更历史 —— 治理的证据链断在安装目录里；
- `pip install -U` 会**静默改变**这个仓库的裁决结果，而仓库里没有任何一个字节记录它变过；
- 审计的时候你回答不了这个问题：**判我红的那 30 行代码，是谁、哪一版写的？**

那不叫治理，那叫调用外部服务。

所以最终形态是：**脚手架把门禁拷进你的仓库**。这不是"镜像"，是"交付物"——像 `cargo new` 生成的东西，有版本、有清单、覆盖要显式确认。

### 约束二：快照必须可核对

既然是拷进去的，就会有漂移。我的处理方式不是发誓"不会漂"，而是让漂移**可以逐字节判出来**：

生成时会写一份 `GENERATED.json`：

```json
{
  "generator": "allin-governance",
  "version": "0.0.0a1",
  "generated_at": "2026-10-31 10:39:18 +0800",
  "gates": ["g00-meta", "g01-paths", "..."],
  "files": {
    "tools/gate/governance/run.ts": "sha256:...",
    "tools/gate/governance/gates/g05_hygiene.py": "sha256:..."
  }
}
```

任何一个文件被手改、或被别的版本覆盖过，都对不上。升级用 `init --force`，覆盖前先比对清单。

### 约束三：`--force` 不覆盖你的内容

`--force` 的语义是"升级套装"，不是"我同意你重写我的文档"。

所以分得很清楚：

| 路径 | `--force` 的行为 |
| --- | --- |
| `tools/gate/governance/**` | 覆盖（这是套装本体） |
| `README.md` / `LICENSE` / `docs/**` | **只在缺失时创建，永不覆盖** |
| `package.json` / `.gitignore` | **只合并**，不动既有条目 |

第二条是常识，第三条是血泪：有个工具替你覆盖了 `.gitignore`，等于替你决定什么该入库。

## 五、它现在能做什么

一条命令：

```bash
pip install allin-governance
allin-governance init my-repo
cd my-repo && npm run check:governance
```

第三条命令的输出结尾是：

```
governance: 14/14 gate(s) clean
```

我不打算说"10 分钟上手"，因为**没有陌生人试过**（见下一节）。我能说的是：

- 这条路径在 Linux 与 Windows 的 CI 上各跑过一次，两次都 `exit 0`；
- 目标目录建在 runner 的临时目录里，不继承仓库内任何文件、别名或虚拟环境；
- 二次 `--force` 跑完 `git status` 是干净的（新建 0 / 保留 43 / 覆盖 0）；
- 27 个单测里，有一条专门用子进程 + `PYTHONIOENCODING=cp1252` 复现第一节那次崩溃。

生成的骨架包含：

- 14 道门禁（纯 Python 标准库，单跑不需要 Node）
- 文档四分类：`规范/`（约束）、`事实源/`（活台账）、`记录/`（证据流水，只增不改）
- `registry.json` 注册表 + `RULES.md` 规则映射
- 每道门禁一个空的基线文件（棘轮只能单向收紧）

跑聚合命令需要 Node ≥ 22.18；不想装 Node 也能逐道单跑：

```bash
python tools/gate/governance/gates/g05_hygiene.py
```

两个可选动作：

```bash
allin-governance init my-repo --with-exceptions   # 多带一道例外台账门禁（需 PyYAML）
allin-governance verify my-repo                   # 按清单复核快照：0 一致 / 1 有改动 / 3 无清单
```

`verify` 是把"快照可核对"从一句话变成退出码的那一步 —— 没有它，`GENERATED.json` 只是一份没人读的元数据。

## 六、它不能证明什么

这一段通常是这类文章省略的，但它比上一节重要。

**一、没有外部验证。** 到目前为止，跑通过这套东西的人只有一个 —— 我。CI 是机器，不是陌生人。CI 绿证明的是"机制可复现"，不是"人可复现"。二者之间隔着：文档是否有歧义、依赖是否装得上、报错是否说人话。这三件事我一件都还没被验证过。

**二、有一个"一路绿灯"的缺陷，我把它留着当教材。** 包里的两棵源码树靠 `pyproject.toml` 的 `package-dir` 从仓库映射进来。这套映射对 wheel 完全有效，对 **sdist 无效** —— sdist 不能收录项目根之外的文件。于是最初那两版只发了 wheel。这个缺陷的形状值得记住：

- `python -m build --sdist` 打印 `Successfully built`；
- `twine check` 报 `PASSED`；
- 包里没有源码；
- 从它装出来的包，命令在运行时找不到文件。

**三道检查全是绿的，产物是废的。** 所以修法不是"改一行"，而是换构建路径：物化到临时目录再打包，**构建完打开 tar 复核每棵树是否真的在里面**。判据必须是"产物可用"，不是"构建成功"。

**三、默认只覆盖 14 类问题。** 它不会告诉你架构错了、命名不好、测试没意义。它只判那些"能写成退出码"的事。认为它能替代判断力，是误解。

**四、第一节那四个缺陷，是被 CI 抓到的，不是被设计抓到的。** 这一点我很想强调：这套东西的可信度不来自我设计得多好，而来自它**当场抓出了我自己写的东西的问题**。一个从没抓过作者的门禁系统，大概也抓不到你。

## 七、如果你想自己做，四步

不必用我的包。这个思路本身可以抄走，四个步骤：

**第一步：挑一条你现在靠"记得"的规矩，把它写成退出码。**

不要挑"代码要清晰"这种。挑这种：

> 仓库里不许出现写死的本机绝对路径。

因为它可以判定：扫全部被跟踪文件，匹配盘符或 `/Users/`，命中就退 1。

**第二步：给它一个自检。**

这是最容易被跳过、也最值钱的一步。自检的意思是：**往沙箱里注入一个必然违规的样本，验证这道门禁真的会红。**

```bash
python tools/gate/governance/gates/g01_paths.py --selfcheck
# selfcheck ok for g01-paths: caught 3, quiet on 6, misreports 0
```

`caught 3` = 抓到了 3 个注入的缺陷；`quiet on 6` = 对 6 个合法样本保持沉默；`misreports 0` = 没有误报。

只打印 `PASS` 不算自检。**能抓到注入的缺陷**才算。

**第三步：注册它，并写清它为什么存在。**

一个 JSON 注册表，八个字段：id、标题、脚本路径、档位、覆盖的规则、支持的平台、依赖、是否支持自检。

外加一份 `RULES.md`，把"哪条规矩由哪道门禁执行"写成人能读的表。规则必须能找到执行它的门禁，门禁必须能找到它服务的规则 —— 双向可溯。

**第四步：让门禁验门禁。**

这是最后一块拼图，也是最反直觉的一块：一道 `g00-meta`，它的工作是

- 读注册表，逐条校验八个字段是否齐全；
- 确认每个脚本**真的在仓库里**；
- 跑每道门禁的 `--help`，确认它暴露了必需的开关；
- 跑每道门禁的 `--selfcheck`，确认它还能抓到注入的缺陷；
- 核对它是否被写进了 `RULES.md`。

一个有 20 道门禁的系统，如果不验自己，第 21 道加进来时就会悄悄失效 —— 而没有人会发现，因为它看起来还在跑。

## 八、最后

这套东西真正想解决的，不是"如何管好代码"，而是：

> **当你和一个不会累、不会抱怨、也永远不会说"我觉得这样不太对"的协作者一起写代码时，你需要的不只是更快的生成，还需要一套它无法绕过的判据。**

AI 会把一个错误的口径在几分钟内复制到几十个文件里。人不会。这是新的问题，需要新的防线。

而防线的形态只有一个：**可执行、可复跑、会红、而且红得诚实。**

至于我的实现好不好，你可以自己判断 —— 它在 Gitee 上，也在 PyPI 上。但更可能的情况是：你不需要它，你只需要照着第七节的四步，自己写四道门禁。那也完全够了。

**先做出来，再做好。做出来的东西，要好过它被设想时的样子。**
