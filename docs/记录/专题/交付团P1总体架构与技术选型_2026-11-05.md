### 1.3 核心链路：四个贯通点（G1–G4，按优先级）

| 编号 | 贯通点 | 数据流向 | 方向性 |
|---|---|---|---|
| **G1** | website 控制台看 platform 项目启停状态 | browser → website（requireAuth）→ 服务端代理 → platform `GET /api/library` + `GET /api/status` | website→platform，**只读** |
| **G2** | 门禁结果进 website 管理台（等价于「platform Alerts 展示 kernel 门禁结果」） | `tools/gate` 跑完落 `gate-runs.jsonl` → platform 既有 `GET /api/gate-history` → website 服务端代理展示；platform Alerts 页同样可读 | kernel→platform→website，**只读** |
| **G3** | kernel CLI 汇总 platform 状态 | `allin status` 子命令**只读** `running.json` + `gate-runs.jsonl`（文件系统），platform 离线时优雅降级为「未运行」 | kernel→platform 状态文件，**只读** |
| **G4** | 编排状态可视化（双形态路由表 + 漂移判据结果） | g21 门禁产出判据结果 JSON → platform `GET /api/orchestration` 聚合 → website 控制台/管理台展示 | kernel 产物→platform→website，**只读** |

## 2. 技术选型（每个关键决策含被否决备选与实证依据）

### 决策一：三面贯通的集成方式

| 备选 | 说明 | 裁决 | 理由 |
|---|---|---|---|
| (a) platform 门户扩容为统一网关，反向代理 kernel/website | portal 变常驻反向代理，所有流量过它 | **否决** | ① portal 现行定位是「按需启动、PORT=0 临时端口、关窗释放」的 DSH 同款形态（platform README / ports.yaml 9000 已 retired），改成常驻网关违背已拍板的形态演进；② kernel 是 CLI 非 HTTP 服务（kernel README 明确「不是 HTTP 服务」），反向代理它需先给 kernel 加 HTTP 面，与 ADR-0001「治理内核留在 Python 不迁 Node/Cordis」的轻量定位冲突；③ website 自带会话/CSRF，被反代后 cookie 域/CSRF origin 校验要重做，引入不必要风险面 |
| (b) 各面暴露本机 HTTP API + 薄聚合层 | 全部服务常驻 HTTP，加一个聚合服务 | **部分采纳** | kernel 侧否决「加 HTTP」：kernel 数据（门禁留痕）已经以 JSONL 落盘，HTTP 化是重复暴露；platform 侧采纳——它**已有** 13 路径 OpenAPI 契约，在其上做增量端点成本最低 |
| (c) 共享状态文件（JSON/JSONL）+ 文件监听 | 纯文件总线 | **部分采纳** | Windows 上跨进程文件监听（watchdog/FSWatcher）语义不可靠（删除/替换/杀毒锁），不适合做唯一集成通道；但**作为事实源层保留**（running.json / tasks.log / gate-runs.jsonl 本来就是「日志即事实源」纪律），读侧允许文件级只读（G3 的 `allin status`） |
| **主选：混合 (b)+(c)，platform 为治理状态唯一聚合出口，website 为唯一整合 UI 面** | portal 增量只读端点；website 服务端代理；kernel 保持 CLI + 文件只读 | ✅ | 与三条既有纪律零冲突：聚合不融合（只加只读边）、绝不 import 项目代码（全部走 HTTP/文件边界）、不新增端口（复用 portal.port 发现机制）。实证参照：homelab 领域主流做法也是「服务端聚合渲染的轻量 dashboard」而非全家桶反代——Glance 以 <30MB 内存、服务端聚合（后端轮询上游、浏览器只见单一源）胜出（101howto.com，2026 检索），本方案 website 代理模式同构 |

### 决策二：贯通后的身份边界

| 备选 | 裁决 | 理由 |
|---|---|---|
| 浏览器 iframe/直连 platform 端口 | **否决** | 破坏单源：platform 无鉴权（已知边界），浏览器直连等于把无鉴权启停能力暴露给任意本地页面（DNS rebinding 虽有 Host 围栏拦，但同源页面可直接打）；且 CORS 会逼 platform 放宽围栏 |
| platform 加会话鉴权 | **否决（现阶段）** | 单机单用户形态下重复建设鉴权，website 已有完整 scrypt+会话+CSRF+限流；给 platform 加鉴权是第二轮演进的事（见 §6） |
| **主选：website 服务端代理（BFF 模式）** | ✅ | ① 浏览器只认 website:9042 一个源，会话/CSRF/角色控制全在 website（requireAuth / requireRole('admin')）；② website 服务端发出的请求 Host 头即 `127.0.0.1:<port>`，天然落在 portal `hostAllowed()` 围栏内，**无需 platform 改任何安全代码**；③ 端口发现复用既有 `data/portal.port` 文件（openapi.yaml servers 注释已声明该机制），platform 未运行时看板显示「平台未启动」优雅降级，不报错 |
| kernel→platform 走 HTTP | **否决** | kernel 定位 CLI/库，`allin status` 直接只读 running.json/gate-runs.jsonl 更符合「文件即事实源」，且 platform 离线时仍可用（G3 的价值正在于此） |

**纵深防御注记**：写操作（启停）代理层叠三道闸——website 会话 + admin 角色 + CSRF 令牌，全部通过才转发 portal 既有 loopbackOnly 写接口。platform「无鉴权」的已知边界被 website 的鉴权面遮蔽，但不删除（platform 仍可被本机进程直接访问，单机单用户接受）。

### 决策三：贯通层数据契约

| 项 | 决策 |
|---|---|
| 原则 | **website 不持久化任何治理状态**——不建镜像表。platform JSONL/JSON 是唯一事实源（日志即事实源纪律），website 每次实时代理读取，自己只落「谁在何时看/操作了」到既有 `audit_log`（website 审计纪律） |
| schema 演进 | 新增端点照既有规矩进 `openapi.yaml`（OpenAPI 3.0.3、由真实源码生成），版本字段沿用 `version: 0.1.0 → 0.2.0`；枚举/字段只增不改 |
| 失败降级 | 代理层统一错误分类：`PORTAL_UNREACHABLE`（显示「平台未运行」）/ `PORTAL_FORBIDDEN`（围栏被改，fail-loud 报警）/ `UPSTREAM_TIMEOUT`（3s 超时，返回缓存上次快照 + 时间戳标注）。绝不把 502 原样吐给用户页 |
| 一致性模型 | 读操作接受秒级陈旧（library 页已有 5s 前端刷新惯例）；写操作同步等待 portal ActionResult，不引入消息队列 |

### 决策四：Agent 编排双形态的工程化升级（不引入 LLM）

| 升级点 | 方案 | 被否决备选 |
|---|---|---|
| 路由表机器可读化 | 把 15 个专项 skill 的路由条目（id / 触发条件 / 入口路径 / 双形态归属）提炼为 `routes.yaml`；SKILL.md 与 allin.patch.yml 的 GOVERNANCE 段**保持人写**，由门禁做三方对账（对账式而非生成式，符合「文档即测试」ADR-0004 判定口径） | 生成式（YAML 渲染出 Markdown）——否决：双形态文本各有措辞语境，机器渲染会丢失治理段的手写语义；且生成物与手写物边界模糊，漂移判据反而失灵 |
| 双形态同步判据自动化 | 新增 g21 门禁：解析 routes.yaml，逐条在 SKILL.md 与 allin.patch.yml 中定位对应路由锚点，缺失/漂移即红；判据结果落盘 JSON（供 G4 可视化） | 复用 verify-mount.ps1 扩展——否决：verify-mount 的职责是 DSH 安装层校验，往里塞仓内对账会让「安装校验」和「内容对账」两个失败域混在一起 |
| 编排状态可视化 | platform `GET /api/orchestration` 返回：路由条目 + g21 最近判据结果 + 双形态同步时间戳；website 控制台渲染「治理大脑健康卡」 | 做成实时 dashboard 长连接（SSE/WebSocket）——否决：单机单用户，轮询足够，长连接徒增复杂度 |

### 决策五：Windows 进程守护/自启

| 备选 | 裁决 | 理由（含联网实证，2026-11-04 检索） |
|---|---|---|
| PM2 + pm2-windows-service / pm2-installer | **否决** | 实证：pm2-windows-service、pm2-installer 「好几年没更新，社区活跃度低，与新 Node 版本冲突基本找不到解决方案，不建议优先选」（火山引擎 Windows 部署技术咨询文章）；另有 Jenkins/Windows 实测 PM2 后台行为异常的一手报告（poliweb.su，2026 检索）。且 PM2 是全局 npm 依赖，与本仓「零依赖/拷走即用」倾向相悖 |
| NSSM（Windows 服务包装） | **备选保留** | 实证：NSSM「轻量稳定、核心逻辑简单可靠，很多老项目至今依赖」（火山引擎）；devgex.com 亦列其为高可靠方案。**适用前提**：需要「不登录也常驻」（服务级自启）时启用；代价是需要管理员安装 |
| 启动文件夹放 .bat | **否决** | 无进程监视、无自动重启（devgex.com 对比结论），可靠性不达标 |
| **主选：Task Scheduler（计划任务，登录触发）** | ✅ | ① Windows 原生、零安装、免管理员、可配失败重启（`-RestartOnFailure`）；② 与「单用户=全哥本人、本机交互式使用」的形态吻合——治理面（portal/website）本来就该在用户登录后可用而非无人值守服务器场景；③ 实证：aiden 项目 Windows daemon 文档把 Task Scheduler 列为内置兜底方案并给出可复制的 `Register-ScheduledTask` 配方（github.com/k8scat/aiden daemon-windows.md）——**借鉴记账见 §8** |

落地形态：一个总控计划任务（登录触发）依次拉起 website（常驻，登记 9042 active）与 portal（沿用 PORT=0 按需形态或常驻均可，portal.port 文件发现不变）；崩溃重启由计划任务设置承担（间隔 1 分钟、重试 5 次的实测配方同上）。**kernel 不守护**——CLI 按需调用，无常驻进程可守护。

### 决策六：日志与备份

| 项 | 决策 | 依据 |
|---|---|---|
| 日志 | 维持「日志即事实源」：JSONL + 5MB 轮转（launch.js 现制）；计划任务 stdout/stderr 重定向到固定日志目录（按日轮转，保留 14 天）。不引入集中式日志系统 | 单机单用户，ELK/Loki 全部否决（成本/复杂度远超收益） |
| 备份 | ① 密钥灾备：完全复用 website 既有 `npm run backup-key`（0600、带口令、月度恢复演练已是 SEV1 防线，SPEC-106 §6）；② 治理状态备份：每日计划任务 `robocopy /MIR` 把 `platform/data/`、`website/data/`（含 site.db）镜像到仓外备份目录，7 天轮转；③ 备份落点**拒绝进仓库目录**（与 backup-key 同纪律，防 git 意外收走） | website README §6.5 已确立的威胁模型与纪律，直接复用 |

## 4. 非功能性设计

| 维度 | 目标 | 实现手段 | 验证方式 |
|---|---|---|---|

| **可用性** | 单机单用户不做 SLA；可量化为：登录后 60s 内治理面全部可用；portal 崩溃 1 分钟内被计划任务拉起；portal 离线时 website 看板**降级不报错** | Task Scheduler 失败重启；website 代理错误分类降级；kernel `allin status` 文件级读取不依赖任何服务在线 | 计划任务重启实测；smoke 增「platform 离线时看板 200 + 降级提示」用例 |

## 6. 演进路径与风险

| 触发条件 | 演进动作 | 成本估计 |
|---|---|---|
| 治理看板成为高频入口（日开 >20 次） | portal 转常驻（登记 9900 段空闲端口，走 ports.yaml 流程），去掉按需启动摩擦 | 小：改一处启动形态 + 登记两份端口文件 |

| 编排路由 > 30 条 / 双形态第三形态出现 | routes.yaml 升级为分文件 + g21 按目录扫描；评估 preset apply 落地（preset_service TODO） | 小–中 |
| 138 仓全量登记进 platform（现 105+） | registry 懒加载/分页（library 全量返回已显吃力征兆） | 中 |
