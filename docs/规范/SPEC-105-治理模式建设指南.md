## 0. 为什么需要它（问题定义）

一个人管上百科目的典型塌方路径，不是「不会写代码」，而是：

| 塌方 | 真实表现（本工作区都发生过） |
| --- | --- |
| **事实源分裂** | 同一件事在 README、文档、聊天记录、脑子里各有一版；新人（或新的 AI 会话）拿到的是旧版 |
| **改动不留账** | 改完只在本地，或提交信息写「更新」；三个月后没人知道为什么这么改 |
| **假绿** | 验证脚本打印了 `[PASS]` 但退出码是 0、进程还活着就算过、只看重定向输出不看真控制台 |
| **门禁靠自觉** | 「记得别写死路径」——没有可执行的门禁，等于没有约束 |
| **冗余误判** | 按同名判定「A 已并入 B，可删」→ 删掉了 B 里没有的功能面（本工作区真删错过一次） |
| **许可失控** | 第三方 GPL/CC BY-SA 资产混进 MIT 公开仓，或反过来把必须 GPL 的仓「补成 MIT」 |
| **AI 协作者放大错误** | 一次错误的口径会被 AI 高速复制到几十个仓（所以治理必须**机器可校验**，不能靠记忆） |

一句话结论：**给人看的规矩要变成给机器跑的门禁，给机器跑的门禁要有给人看的账。**

## 1. 模式总览：五根支柱

```
                     ┌─────────────────────────────────────────────┐
                     │  ① 单一事实源（Single Source of Truth）      │
                     │  README / MEMORY / 会话交接 / 协作约定       │
                     └───────────────┬─────────────────────────────┘
                                     │  互相引用，不互相复制
   ┌─────────────────────────────────┼─────────────────────────────────┐
   │                                 │                                 │
┌──▼───────────────┐   ┌─────────────▼──────────────┐   ┌──────────────▼─────────┐
│ ② 铁律体系        │   │ ③ 门禁化（可执行）          │   │ ④ 记账化（可审计）      │
│ 每条都有事故来源   │   │ 死根门禁 / AST 检查 / 仓内   │   │ commit + MEMORY + 交接  │
│ 违反即"停手上报"  │   │ verify 门禁族 / 基线棘轮     │   │ + 计划文档 + 审计片段    │

                                     │                                 │
                     ┌───────────────▼─────────────────────────────────▼─────────┐
                     │ ⑤ 透明化与复用（Open by default）                          │
                     │ 文档枢纽入库公开仓 → 他处可读、可复跑、可续做               │
                     └───────────────────────────────────────────────────────────┘
```

## 2. 目录契约（先定布局，再谈纪律）

| 路径 | 角色 | 规矩 |
| --- | --- | --- |
| `/repos/<项目>` | 一个项目一个独立 git 仓 | 仓内自洽：`README.md` + `LICENSE` + `.gitignore` + 门禁与测试；**不写死绝对路径** |
| `/repos/allin-platform/` | 编排/平台层：注册表、端口表、启动器 | 端口与项目清单是**事实源**：`registry/projects/*.yaml`、`registry/ports.yaml`。**目录名 = 远端仓名**（2026-09-25 由 `G:\platform` 改名对齐；**2026-09-28 由仓根并入 `/repos/`**） |
| `/allin/` | 治理仓（公开，MIT-0）：目录索引 + 审计报告 + **文档枢纽 `docs/`** | 只放索引/文档，不放项目源码 |
| `/allin/docs/` | **文档枢纽**：四分类（`规范/ 事实源/ 记录/ md/`）+ 总目录 `INDEX.md` | **只放文档**：脚本、CSV、二进制、第三方资料一律不放（见 §7）；**索引与磁盘一致性由门禁保证** |
| `/tools/gate/` | 可执行门禁与工具（`scan_hardcoded.ps1`、`check_undefined_names.py`、**`docs_index.py`**、`make_doc_aliases.ps1`、基线） | 工具也要有 README，默认路径写清 |
| `/archive/` | 归档区（退役仓、迁出的非文档内容、历史工作区） | 归档=可逆保存，**补优于删**；每个归档目录带 `MANIFEST.md` |
| `/notpython/` `/assets/` `/web/` `/workbuddy/` 等物料区 | 参考源码、素材、外部工具工作区 | 与治理仓隔离；不进公开仓的内容在此就地标注（见 §6 非 MIT 标记） |

> ⚠ **路径口径（2026-09-28 实测订正）**：工作区**跨两块盘** —— 代码盘放 `/repos/<仓名>`（**含平台仓 `/repos/allin-platform/`**）、`/allin/`、`/tools/`、`/local/`；
> 数据盘放物料区（`/notpython/`、`/archive/`、`/assets/`、`/web/`、临时区），数据盘上是 **exFAT**（不支持硬链接与目录联接）。
> 具体盘符与卷标**不写进文档**（铁律 5），以 [`../事实源/机器分区索引.md`](../事实源/机器分区索引.md) 的现场实测为准。

**两条硬规矩**
1. **绝对的路径只允许出现在文档与配置里，且必须是「变量可覆盖」的默认值**（例如 `process.env.PLATFORM_PORTS || '<默认>'`）。
2. **一个事实只能有一份**：README 说「是什么/怎么跑」，MEMORY 说「铁律与约定」，会话交接说「发生过什么」，计划文档说「接下来做什么」。同一条事实**只在最合适的那份里写全**，其余只放链接。

## 3. 从零搭建：10 步 playbook

> 每一步都给出**产出物**与**验收标准**。顺序不能乱：没有盘清资产，后面所有判断都是印象。

### S1 盘清资产（先有地图，再有主张）
- 生成全盘索引：目录/文件/体量的快照（本工作区为 `目录索引.txt`，500 MB 级，周期性重生成而非逐次改）。
- 生成**仓映射**：`仓名 | remote | 分支 | HEAD`，逐仓 `git ls-remote` 核实（**只信远端**，本地 `origin/BR` 会因未 fetch 而给出假阳性）。
- 标注**非 MIT 资产**：第三方 SDK、CC BY-SA 素材、GPL 上游 → 单独文档 + 就地标记文件。
- **验收**：任一项目能被三分钟内回答「它在哪、远端在哪、什么许可、谁在用」。

### S2 定目录契约与仓边界
- 一项目一目录一仓；合并优于双仓并存；退役仓进 `archive/` 并写 `MANIFEST.md`。
- 平台层单独立仓（注册表/端口/启动器），项目清单 `launch` **不写死绝对路径**。
- **验收**：`G:\repos` 下每个目录都是 git 仓；每个仓都有 README/LICENSE/.gitignore。

### S3 建文档枢纽（本工作区的形态：**四分类 + 开卷必读四份**）

**四分类**（判据见 `SPEC-005 §2`，判断顺序是「这份文档被违反会怎样」）：

| 类 | 目录（ASCII 别名） | 是什么 | 文件名 |
| --- | --- | --- | --- |
| **规范** | `规范/`（`spec/`） | 有人**将来**必须照它做；带 `SPEC-NNN` 编号与**效力声明头** | `SPEC-<号>-<短名>.md`，**禁日期** |
| **事实源** | `事实源/`（`facts/`） | 当前状态的单一权威台账，别的文档/代码来**取值** | 中文名，**禁日期**；头部带时点 / 观测工具 / 失效条件 |
| **记录** | `记录/`（`records/`） | **某一次**发生的事的证据 / 流水，**只增不改** | `<主题>_<YYYY-MM-DD>.md` 或按月卷 `<YYYY-MM>.md` |
| **历史** | `md/`（`历史/`） | 存量文档树，冻结留证 | 保持原样 |

**开卷必读四份**（这是旧「四件套」的换代形态 —— 旧形态把铁律、流水、流程混装在一个 `MEMORY.md` 里，长到 661 行后不再可读）：

| 文档 | 位置 | 写什么 | 不写什么 |
| --- | --- | --- | --- |
| `INDEX.md`（**总目录**） | `docs/` 根 | 全量登记：编号 / 类别 / 路径 / 状态 / 时点 / 一句话 | 正文（只放链接） |
| `SPEC-001`（铁律） | `docs/规范/` | 铁律 + 准则 + 纪律（编号，可被引用） | 逐次流水 |
| `SPEC-002`（协作流程） | `docs/规范/` | 任务分档、五阶段、放行口径 | 具体项目细节 |
| `机器分区索引.md` | `docs/事实源/` | 盘位 / 工作区 / 运行时**现值**（带时点与失效条件） | 历史快照（那些进 `记录/快照/`） |

- 逐轮事实流水 → `docs/记录/交接/<YYYY-MM>.md`（按月分卷，**只增不改**；新会话读最新卷）。
- **验收**：新会话读完这四份能直接接手，并知道「哪些事不能自作主张」；**索引与磁盘是否一致由门禁保证**（`tools/gate/docs_index.py` / DSH `g15-docs-contract`），不靠人守。

### S4 立铁律：从事故里提炼，不从审美里发明
- 每条铁律必须写清**来源事故**（哪次、哪个仓、什么代价）。无来源的规矩会在一周内被绕过。
- 编号稳定（`.1`/`.2`/…，永不重排），被引用时只写编号（`铁律 25`）。
- **编号一经分配不得复用**：追加前先扫全表取**最大号 + 1**，禁止凭记忆续编；追加后立即校验「编号 == `1..N` 连续唯一」，不通过不得提交。**改号必须同步全部引用点，验收标准是「引用指向的条目内容与上下文语义相符」，不是「编号存在」。**
  > 为什么补这一句（2026-09-24 实证）：本条原只写「永不重排」——**只说了"不许改"，没说"不许重"**，于是本表出现「缺 23 + 29/30 各两次」（44 个条目只有 42 个唯一号），`会话交接` 引「调试铁律 24/25/29/30」时**无法判断指哪两条**；`建设指南` 本页的事故表更整体错位（8 行里 6 行指错，写于 40–43 立完之后未随编号更新）。详见 `MEMORY.md` 调试铁律 45。
- **编号是引用契约，不是排版**：凡是带编号的事实源（铁律、端口、条目索引）都要满足唯一性；引用方只写编号，因此**编号重号 = 引用失效**。
- 本工作区的铁律分四类：**开源与许可**、**协作与放行**、**工程与验证**、**平台与路径**。
- **验收**：任意一条铁律都能回答「它防的是哪次事故」。

### S5 装门禁：把规矩变成退出码
1. **死根门禁**（跨仓扫「已失效的绝对路径」）：`/tools/gate/scan_hardcoded.ps1`
   - 判定口径：路径的**父目录**不存在即死（只看前 1~3 段会把 `/Users/x` 存在而 `Desktop\...` 已删的路径误判为活）；
   - 白名单：系统路径、URL、测试夹具、注释/用法示例、审计注记（在**行内**写明「已失效/已不存在/占位」等）；
   - **基线棘轮**：存量写进基线（`/tools/gate/audit/hardcoded_gate_baseline.csv`），日常只拦新增，退出码 0/1；
   - **自带 `-SelfTest`**：临时建仓验证「能抓死路径、不误报、基线生效」。
2. **AST 未定义名检查**：`/tools/gate/check_undefined_names.py`
   - `py_compile` 只查语法，查不出「用了没导入」「str 与 Path 做 `/`」这类**运行期才炸**的缺陷。
3. **仓内 verify 门禁族**（每个项目自己的 `repos/<仓>/tools/verify.py`）：门禁要能**列出来、单独跑、自检**，
   例：`third-party-notices`、`doc-links`、`plugin-manifest`、`release-payload`、`no-credentials`…
4. **CI/钩子**：本地 `.githooks/` + CI 定义保持一致（注意沙箱里 `#!/bin/sh` 钩子可能假红，需区分「环境限制」与「真失败」）。
- **验收**：门禁全量跑一次 `exit 0`；随便找一个故意破坏（删文件、改数字）应立刻变红。

### S6 接协作流程：先问 → 计划 → review → 执行 → 复盘
- **任务分档**：
  - 小任务（记账/清理/单点修复/文档小改）→ 直接执行 + 汇报；
  - 中任务 → 问一句确认目标 + 简计划；
  - 大任务（结构性、跨多仓、架构、规则改造）→ **书面计划 + 明确放行**（如「开始执行」）后才动手。
- **高风险动作不分档**：推送、建仓、删除、密钥操作、仓库结构变更 → **逐项确认**。
- **验收**：任何一次大改动，都能在文档里找到「计划 → 放行 → 执行 → 复核」四段痕迹。

### S7 记账制度：让三个月后的自己看得懂
- 提交信息写**动机 + 范围 + 实测证据**（不写「更新」「fix bug」）；一个逻辑改动一个提交。
- 提交后 `git show --name-only HEAD` 核对**提交面**（防止误加文件）；`git add` 一律**点名**，禁止 `git add -A`。
- 事实沉淀：新踩的坑 → `MEMORY` 编号条目；过程流水 → 会话交接；计划 → 计划文档。
- **验收**：随机抽一次提交，能回答「为什么改、改了什么、怎么验证的」。

### S8 透明化：文档枢纽入库（本仓 `allin`）
- 把 `docs/`（活文档 + 历史树）放进公开仓并推送；文档里的路径引用同步改净。
- 文档里**不含**：令牌/密钥、第三方版权全文、审计过程产物（含敏感串扫描结果）、二进制。
- **验收**：外部读者只克隆 `siwpan/allin` 就能读懂治理模型，并能按指南在自己机器上复刻。

### S9 定期体检（建议节奏）
| 周期 | 动作 |
| --- | --- |
| 每次改动 | 门禁全量 + `py_compile` 断言 + 一次真实运行（阳性） + 一次人为破坏（阴性） |
| 每周 | 全域同步扫描（逐仓 `ls-remote` 对本地 HEAD）、未跟踪产物清点、大文件体检 |
| 每月 | 冗余三查（见 §5）、许可核对、索引重生成、归档整理 |

### S10 扩张与复用：新项目入列清单
一仓一目录 → `README.md`（含怎么跑/门禁） → `LICENSE`（默认 MIT；**链接 GPL 上游则随上游**） → `.gitignore` →
`SPEC/CHANGELOG` → 门禁与冒烟 → 登记进平台注册表与端口表 → 记账（MEMORY 事实 + 交接流水） → 推送公开仓。

## 4. 五个关键机制（细节；这几条最容易做错）

### 4.1 门禁判定口径（死根门禁）
- **死 = 由浅到深检查「父目录是否存在」**，不是只看盘符/用户名存在。
- **豁免要限定文件类型与层级**：`tests/`、`spec/` 之类子串豁免会漏掉整片（曾把 `weor/legacy/spec/*.spec` 全放过）。
- **审计注记**：注释或文档里说明「已失效/已删除/占位/源自上游」的行不计阻断——但注记必须写在**同一行/同一块**。
- **退出码语义**：`0` 干净、`1` 有新增阻断、`2` 用法错误、`3` 环境错误。**不要用一个 0 混过所有情况**。

### 4.2 基线棘轮（Ratchet）
存量一次性写进基线，此后只拦新增。好处：**门禁可以立刻上线**，不必先完成大清理；
代价：基线会掩盖存量——所以基线文件要**定期复查并归零**（本工作区已把存量从 1,690 条清到 0 条）。

### 4.3 冗余/退役判定三查（用代码，不用印象）
判定「A 已并入 B，A 可删」前：
1. 列出 A 的**全部功能面**（例：`radio` 的转播 + 直播 + 面板 + 排程）；
2. 逐面在 B 里找**代码/文档实证**的接任者（`git grep`/实测，不是印象）；
3. **无接任者的功能面不许删**（先保留，或先在 B 实现）。
提交信息与交接必须附「功能面 × 接任者」对照表。

### 4.4 调整必同步三步
① **推远端**（`git ls-remote` 核实，不是只看 push 输出）；
② **更新引用**（配置 / 索引 / README 路径 / 其他仓的引用）；
③ **跑黄金值**（门禁 + 冒烟；改完必须实跑一次应用或测试）。
禁止「改完留在本地」。

### 4.5 验证纪律（防假绿四件套）
1. **退出码必须如实**：验证脚本不能「打印提示就返回 0」；部分失败也要非 0（曾有体检脚本 12/20 失败仍 exit 0）。
2. **阳性 + 阴性对照**：只跑阳性等于没验证；阴性要用**真实产物**制造失败（删依赖、改一个字节），不是注释掉判断。
3. **编译断言**：提交前对本仓全部跟踪 `.py`/`.js` 跑一次编译/语法检查并**断言全绿**，不通过就中止提交。
4. **看真输出**：GUI/CLI 冒烟要在**默认控制台**跑一次（重定向会掩盖编码崩溃）；日志里的 `exit=1` 必须让脚本失败。

## 5. 事故驱动演化：本工作区铁律的来源（节选）

| 事故 | 代价 | 沉淀成的规矩 |
| --- | --- | --- |
| 把「同名」当「同一物」，判 `musickit radio` 直播端冗余而删 | 丢功能面，靠 3 查才补回 | **冗余判定三查**（功能面 × 接任者） |
| 验证脚本任何分支都 `exit 0`（12/20 失败仍绿） | 假绿，差点放过坏闭包 | **验证退出码如实**（铁律 41） |
| 改写脚本时换行插进 f-string；提交脚本「打印 exit=1 后继续提交」 | 语法错误文件被推上远端 | **提交前编译断言**（铁律 40） |
| 逐字符 splat（`@singleString`）→ 5 个仓提交静默失败 | 以为提交了其实没有 | PowerShell 参数纪律（铁律 25） |
| 中文 Windows 默认 GBK：`json.load(open(p))` 崩 / `json.dump` 写出 GBK | 数据被写坏且难查 | **显式 `encoding="utf-8"`**（铁律 35） |
| 控制台 GBK 让带 `✓` 的输出崩溃，重定向时不复现 | 「跑过一次通过」是假象 | 入口 `sys.stdout.reconfigure` + 默认控制台复跑（铁律 38） |
| `.git/config` 里空值 `credential.helper=` 清空 helper 链 | 连续三次 push 失败、用令牌 URL 绕过 | 配置差异比对（铁律 37） |
| 把「链接期依赖目录」当运行时目录 → 判「依赖坏了」 | 误判根因、改错方向 | 先验证再下结论（铁律 39） |
| 副本仓把根文档搬进 `docs/` 却没改引用/门禁路径 | 三条门禁长期红而源仓全绿 | **搬文件要同步链接/门禁路径/索引**（铁律 42） |
| 用陈旧 `origin/BR` 判「未推送」 | 2 仓假阳性 | **只信 `git ls-remote`** |

> 规律：**铁律不是设计出来的，是被坑出来的**。所以每次事故后第一件事不是修代码，而是问「这条能变成机器能拦的门禁吗？不能的话，写进哪份事实源？」

## 6. 开源与许可纪律

- **默认**：公开仓 + MIT（`Copyright (c) 2026 siwpan`）；新建仓即 public + LICENSE。
- **唯一例外**：发布物**链接/随包 GPL/AGPL 上游**（如随包 GPL v3 的 FFmpeg 构建）时，许可**必须随上游**——
  改 MIT 才是违规。本工作区 `pluginplayer` 即此例（`GPL-3.0-or-later`），且必须在 README 与
  `THIRD_PARTY_NOTICES.md` 里写清义务与证据。
- **非 MIT 资产**（第三方 SDK、CC BY-SA 素材）→ 单独标注 + **就地标记文件**（在该目录放一份说明），禁止进公开仓。
- **凭证红线**：令牌/密钥/证书**永不**进代码、配置、仓库、文档；示例一律 `example` 化 + `.gitignore`。

## 7. 文档枢纽的规矩

> **形态在 2026-09-28 换代**：旧形态是「活文档平铺在 `docs/` 根」+ 一个混装 `MEMORY.md`；
> 现行形态是**四分类 + 总目录 + 索引门禁**（契约见 `SPEC-005`）。下表为现行规矩。

| 规则 | 说明 |
| --- | --- |
| **四分类** | `规范/`（约束，带 `SPEC-NNN` 与效力头）· `事实源/`（活台账，带时点）· `记录/`（证据流水，只增不改）· `md/`（历史，冻结）。判据与命名见 `SPEC-005` §2/§4 |
| **根目录只放三样** | `README.md`（门面）、`INDEX.md`（总目录）、`MEMORY.md`（**路由页**）+ 四个分类目录；新文档**不得**落在 `docs/` 根 |
| **索引即契约** | 每份文档必须在 `INDEX.md` 有一行；未登记 / 登记了不存在的文件 / 规范缺头部字段 / 规范名带日期 / 分类错位 / 交接卷断号 → **门禁报红**（`docs_index.py` D1–D7） |
| **ASCII 别名并置** | `spec/` `facts/` `records/` `历史/` 与中文目录并存；别名是 junction、**不入库**（内容只存一份），换机后 `pwsh -File tools/gate/make_doc_aliases.ps1` 重建、`-Check` 校验 |
| **只放文档** | `.md/.txt`（含说明性 `.yaml`）可以；脚本 → `tools/`，审计产物与归档 → 数据盘 `archive/`，二进制与第三方资料不放 |
| **单一事实源** | 同一事实只写一份：规则在 `规范/`、当前值在 `事实源/`、过程在 `记录/`；其余只放链接（禁止复制第二份规范） |
| **规范不删除** | 废弃只改 `状态` 并在正文首行写明替代者；引用方改为指向替代规范（沿革可追溯） |
| **就地标记不搬走** | 目录内的「非 MIT 标注」等就地提醒文件留在原目录，只更新其指向路径 |
| **敏感信息** | 入库前必须过敏感串扫描（32-hex / `sk-` / `api_key` / 密码 / Cookie）；命中的改写为 example 或移出 |
| **大文件** | 单文件 < 100 MB（gitee 限制）；大索引类产物周期性重生成，不逐次提交 |

## 9. cordis 化内核整体构建（粘合剂模式）

> **这一节回答「allin 怎么把文档、工具、platform 粘成一个有机整体」** —— 不是再立一个顶层 `kernel/` 目录（那只能治标，结构一变又散），而是用 **cordis 声明式 preset 作为粘合剂**，把四类资产按同一份契约有机绑定、互相守护。
> 背景：2026-10-26 把 `siwpan/deepseek-harness` 的治理内核（15 条门禁 `g00-meta`~`g15-docs-contract`）整体并入本仓 `tools/gate/governance/`，原 DSH 远端删除；cordis preset（`preset/allin/allin.patch.yml`）成为唯一可执行治理载体。

### 9.1 为什么用 cordis preset 当粘合剂

- 文档（`docs/规范/` 约束、`docs/事实源/` 现值）是**文字事实源**；工具（`tools/gate/` 机械门禁）是**可执行判据**；`platform/` 是**编排层**。三者各自演化，问题出在「改文档不更新门禁」「加工具不登记契约」「platform 扩却不备案」。
- cordis preset 是唯一**随会话/随仓可重装**的载体：它把「开卷必读四份 + 铁律 + 治理准则 + 本机边界」写进 agent 的 persona 段（`<!-- GOVERNANCE:BEGIN -->`…`<!-- GOVERNANCE:END -->` 标记块），**每次会话启动即生效**，不依赖人记得去读。
- 治理门禁树（`tools/gate/governance/`，`g00-meta` 元门禁 + `g01-paths`…`g20-facts` 共 20 道）反过来**守住这条 preset**：块必须成对有序、段内无盘符路径、引用的仓内文件必须存在、提到的门禁 id 必须已注册（`g14-preset`）。

### 9.2 粘合契约（判据同源、实现不同）

| 资产 | 载体 | 守护门禁 | 引用格式 |
| --- | --- | --- | --- |
| 约束性规则 | `docs/规范/SPEC-*` | 各 `gNN` + `docs_index.py` D3/D4 | `SPEC-NNN` |
| 当前值 / 事实 | `docs/事实源/*` | `g07-doc-freshness`（时点） | `FACT-NN` |
| 机械门禁 | `tools/gate/governance/gates/*` | `g00-meta`（契约自检） | `gNN-*` |
| 编排 / 平台 | `platform/` | `platform/scripts/check.mjs` + `npm test` | — |
| 粘合剂本身 | `preset/allin/allin.patch.yml` | `g14-preset` | — |

**关键不变量**：任何新内容并入（文档改、工具加、platform 扩）都先过两道门禁 —— `npm run check:governance`（仓内判据，聚合默认带 `--no-profile`）与 `python tools/gate/docs_index.py`（索引契约）。门禁红 = 没过关，**不许提交**。

### 9.3 怎么接新内容（沿用同一契约）

1. **文档** → 落 `docs/` 四类之一，领 `SPEC-/FACT-` 编号，登记 `INDEX.md`，跑 `docs_index.py`。
2. **工具 / 门禁** → 放 `tools/gate/`（或 `tools/gate/governance/gates/`），带 `--selfcheck` 与四开关，登记 `governance/registry.json` + `governance/RULES.md`。
3. **平台能力** → 进 `platform/`，过 `platform/scripts/check.mjs` 与 `npm test`。
4. **写进 agent 启动即生效的治理段** → 改 `preset/allin/allin.patch.yml` 的 GOVERNANCE 块，再跑 `check:governance` 确认 `g14-preset` 仍绿。

> 教训（2026-09-24 实测）：副本仓把根文档搬进 `docs/` 却没改引用/门禁路径，三条门禁长期红而源仓全绿 —— **搬文件必须同步链接、门禁路径、索引**（铁律 42）。cordis 粘合剂把这条纪律变成了开机即检查的机械判据。
