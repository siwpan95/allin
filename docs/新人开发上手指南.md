## 第 2 章 环境准备

### 2.1 系统要求

> **模板写法**：列出支持的操作系统、架构、最低硬件/磁盘要求。

**💡 allin 实测**

- **主力系统**：Windows 10/11（本仓开发与排障均在此环境）。
- **跨平台**：源码路径零硬编码（铁律 5「去符盘」），理论上支持 Linux / macOS；但 `.ps1` 脚本需 **PowerShell 7**（非 5.1），`.sh` 脚本需 **bash**（Git Bash 或 WSL）。
- **实测环境**：Windows；Python 3.13.14；Node v22.22.2；Git（近期版本即可）。

### 2.2 运行时版本

> **模板写法**：列出必须装好的运行时及最低版本；给出「怎么查自己版本」的命令。

**💡 allin 实测**

| 运行时 | 最低版本 | 查自己版本 | 配置文件依据 |
|---|---|---|---|
| Python | `>=3.12`（内核）/ `>=3.11`（repocheck） | `python --version` | `kernel/pyproject.toml` 的 `requires-python` |
| Node.js | `>=22.18` | `node --version` | 根 `package.json` 的 `engines.node` |
| Git | 近期稳定版 | `git --version` | — |

> 🔒 建议用**版本管理器**（如 `pyenv` / `nvm` / `mise`）锁定版本，避免「在我机器上能跑」。本仓门禁对解释器敏感（见 FAQ 第 2 条）。

### 2.3 依赖安装（包管理器）

> **模板写法**：给出「创建虚拟环境 → 激活 → 装依赖」的最小可跑步骤。

**💡 allin 实测**

**Python（治理内核 / 门禁）**——仓库已自带 `.venv`（Python 3.13.14），但新人换机后通常要自建：

```bash
# 1) 建虚拟环境（用上面要求的 Python 版本）
python -m venv .venv

# 2) 激活 —— 按你的系统选一条
# 🪟 Windows (cmd):
.venv\Scripts\activate
# 🐧 Git Bash / WSL:
source .venv/bin/activate

# 3) 装门禁所需的两个第三方包（内核运行时 cordis 已 vendored 在 vendor/cordis，无需 pip 安装）
pip install pyyaml watchdog
```

> ⚠️ 本仓**没有根级 `requirements.txt`**：内核依赖以 `vendor/cordis` 内联形式提供（离线、可审计），所以只需补 `pyyaml` + `watchdog`（门禁 `g18` 与 cordis 自身需要）。详见附录 A 第 1 条。

**Node（集成平台）**——只对 `platform/` 子目录装依赖（根 `package.json` 的脚本直接调 `node` 跑 TypeScript，Node 22 原生类型擦除，无需构建）：

```bash
# 🪟 / 🐧 通用（用 npmmirror 镜像加速）
cd platform
npm install --registry=https://registry.npmmirror.com
```

### 2.4 编辑器与插件

> **模板写法**：推荐 IDE、必备插件、格式化/ lint 工具、推荐终端。

**💡 allin 实测**

- **推荐 IDE**：VS Code（本仓栈为 Python + Node + PowerShell，VS Code 原生友好）。
- **必备插件**：Python、ESLint、Prettier、PowerShell（`ms-vscode.powershell`）。
- **终端纪律**（🔒 本仓特有坑）：
  - `.ps1` 脚本**必须用 PowerShell 7（`pwsh`）**跑；PowerShell 5.1 会把文件里的中文注释读成乱码。
  - `.sh` 脚本（如 `scripts/run_all_gates.sh`）用 **Git Bash** 或 **WSL** 跑。
  - 门禁/CLI 输出的中文乱码问题，用 `allin.bat`（已强制 UTF-8）或 `pwsh` 即可避开，详见 FAQ 第 1 条。
- **推荐装 pre-commit**：`pip install pre-commit && pre-commit install`（本仓根 `.pre-commit-config.yaml` 含 gitleaks，会拦密钥，见 FAQ 第 7 条）。

```bash
# 1) 克隆（公开仓，匿名可 clone）
git clone {{仓库地址}}          # 例：git clone https://gitee.com/siwpan/allin.git
cd allin

# 2) 配置提交身份（本仓 git 提交身份）
git config user.name  "siwpan"
git config user.email "siwpan@users.noreply.gitee.com"

💙 pwsh -File tools/credentials/gitee-credential.ps1 test       # 验证令牌有效
#    SSH 方式则需把本机公钥加到 Gitee 账号的 SSH 密钥里。
```

> 🔒 **密钥红线**：真实令牌 / API Key **绝不进仓库、绝不进提交**（一律 example 化 + `.gitignore`）。本仓 `.gitignore` 已屏蔽 `*.token` / `*.key` / `*.pem` / `.env` / `私人令牌.txt`。

## 第 5 章 开发流程

### 5.1 分支与提交规范

> **模板写法**：说明分支模型、提交信息格式、提交前检查。

**💡 allin 实测**

- 🔒 **协作两态**（SPEC-002 §零）：
  - **在场模式**：用户在场时，本地 `git commit` 与「报一句放行再 push」都在场确认。
  - **自主模式**：无人值守时，**本地提交可自主做**，但 **`git push` 一律攒着等用户在场**（铁律 3：推送在场前提）。
- 🔒 **高风险不分档**：推送 / 建仓 / 删除 / 密钥操作 / 仓库结构变更 —— **逐项确认后才做**，不可逆动作绝不自主拍板。
- **提交信息**：建议 **Conventional Commits**（`feat:` / `fix:` / `docs:` / `chore:` …）；本仓另用「记账」式引用（如 `REC-AU-18`、`SPEC-105`），改动若关联规范/记录请带上编号。
- 🔒 **借鉴必记账**：复制/借鉴任何外部代码、配置、概念前，记录「来源 + 许可证 + 借用范围」。
- **提交前自检**：跑一遍相关门禁（见 5.3），确认全绿再提交。

### 5.2 代码评审（PR / MR）

> **模板写法**：说明怎么提 PR、评审关注点、CI 要求。

**💡 allin 实测**

- 本仓为单人开源作者模式；**外部贡献**走 Gitee Pull Request，规范见 `docs/规范/SPEC-103-社区协作规范.md`。
- 评审重点关注 🔒：是否过门禁、是否动了真实密钥、是否写死机器路径（门禁 `g01_paths` 会拦）、文档/索引是否同步更新。
- **配套技术兜底**：`gitee_release.py` 取令牌与 `git push` 走不同链路（见 FAQ 第 3 条），提交前请确认自己用的那条链路通畅。

### 5.3 门禁与测试（Verify Your Setup）

> **最佳实践（来自主流 Onboarding 调研）**：新人第一关 = **跑通门禁/测试并看到「全绿」的预期输出**。这一步能证明你的环境是对的，也是后续每次改动的回归基线。

**💡 allin 实测 —— 跑通即「环境正确」**

```bash
# 1) 本仓治理门禁（预期输出末尾出现「全部门禁通过。」）
bash scripts/run_all_gates.sh
#    若加 --with-platform，还会跑 platform 的 check/test/harness，全绿 exit 0。

# 2) 平台测试（预期 exit 0）
cd platform && npm test

# 3) 文档索引契约（预期「存量应为 0」）
python tools/gate/docs_index.py --no-baseline --list-all
```

> 任何一条非 0 退出，先查 FAQ 第 2 条（解释器不一致）与第 7 条（gitleaks 拦密钥）。

### 5.4 推送与发版纪律

> **模板写法**：说明推送前提、发版流程、tag 规则。

**💡 allin 实测**

- 🔒 **推送在场 + 放行**：推送前必须用户在场并明确放行；推后务必 `git ls-remote` 核对 `IN_SYNC`（铁律 3）。
- 🔒 **发版**：tag 用 `<项目>-v<版本>`；发版/建 release 用 `tools/gitee_release.py`（需 `GITEE_TOKEN`，见 4.2）。流程见 `docs/规范/SPEC-102-发版指南.md`。
- **公开仓纪律**：全部仓库公开 + MIT（铁律 0）；私有仓视为违规。

## 附录 B 30/60/90 上手节奏（来自最佳实践，可选）

> 主流工程 onboarding（Devico / Gitmore / NextMantra 等）普遍采用 30/60/90 天节奏 + 导师（buddy）制。本仓为单人开源模式可酌情简化，但节奏逻辑值得借鉴。

- **第 1–30 天（Orientation）**：环境跑通、读完文档枢纽与铁律、完成第一个小改动（建议从「文档 typo / 门禁小修」入手，走完整 commit→门禁→push 流程）。
- **第 31–60 天（Contribution）**：独立承担中等任务，参与代码评审，深度读 `kernel/` 与 `platform/` 关键模块。
- **第 61–90 天（Independence）**：端到端 owning 一块工作，能解释系统架构给他人，并提出改进。
- **导师制**：新人配一名「buddy」作为技术问题第一联系人；本仓即作者 siwpan，提问走 Gitee Issues。
- **反馈闭环**：新人应把「上手过程中不清楚/踩坑的地方」反写进文档（本仓即此文件的 FAQ 与附录 A），让下一位更快。
