# 非 Python 项目分发缺口：为什么"改引用方式"只走通了一半

> 类型：专题评估 ｜ 时点：2026-11-24（`@SIWPAN`）｜ 关联：[交接卷 §192](../交接/2026-11.md)
> 触发：全哥指出「多副本问题之前是因为没上传 PyPI 才无奈复制，现在应改引用方式 ——
> 有 PyPI 的走 `pip install`，既在虚拟环境里又方便统一更新；同时一个肉眼可见的缺口出现了：
> **非 Python 项目的对应内容目前似乎是没有的**」。

## 0. 结论先行

| 判断 | 结果 |
|---|---|
| "改引用方式替代复制"方向对不对 | **对**，Python 侧已走通（`allin-toolkit 0.1.0` 已上 PyPI） |
| 能不能一次性全铺开 | **不能**。73 个子项目里只有 **1 个**原本真在 PyPI 上 |
| 全哥说的"非 Python 缺口"是什么 | **不是漏了一批文件，是能力不对等**：Python 有 pip 这条路，JS/C++ 没有同等的统一渠道 |
| 本轮处置 | Python 侧做样板并落地；非 Python 侧**只记账不强行统一**（全哥选定） |

## 1. 实测底数（2026-11-24，`D:\projects\repos`）

五个合集仓下共 **73 个**子项目：

| 分类 | 数量 | 说明 |
|---|---|---|
| 有 `pyproject.toml` / `package.json` | 10 | 6 py + 3 js + 1 py+js |
| **真正已发布 PyPI** | **1** | 只有 `music-player`；其余 6 个 Python 包名在 PyPI 上全 **404** |
| 无任何打包标识 | **63** | 其中 **56 个是纯 Python 源码**、5 个 JS、1 个 C++ |

也就是说：**"改 pip install"不是改引用方式，是先得把它们变成包。**

## 2. 另一个硬阻碍：通用名全被占

按原名发布没有可能。实测：

```
calculator 200   print 200   pdf 200   fonts 200   subtitle 200
renamer 200      yasuo 200   arcade 200   mahjong 200   sandbox 200
smile 200        russia 200
```

12 个里 11 个已被占（`test` 虽 404，但属保留/易变名）。

⇒ 只能用带前缀的名字，而 20+ 个 `allin-*` 包会污染 PyPI 命名空间。

## 3. Python 侧：为什么合并成一个包

选定方案：**九个纯 Python 工具合并为 `allin-toolkit`**（`toolkit <子命令>` 单一入口），
而不是九个 `allin-calculator` / `allin-renamer`。

理由：九个 console_script 会让 PATH 塞满名字；装进同一 venv 时与他包重名风险陡增；
而"一次 `pip install -U` 更新九个"恰好命中全哥要的"方便统一更新维护"。

**已落地**（`dev-toolkit` 仓 `97112fc`，PyPI `allin-toolkit 0.1.0`）：

```
whl   2ba6ca5cbb4293d482b93c92caf5be4d9f08cf54f37452e78a960801cfd8d6ee
sdist 29885028558a4a5c088e0a60a762aa009e82167b5d0ca5b3584f9c86b756d0af
从 PyPI 装到干净 venv：version 0.1.0 / toolkit --list 九个 / 子包可 import
```

### 3.1 两个只能靠实测发现的坑

1. **嵌套子包必须逐个声明**。`calculator` 的真实结构是 `calculator/calculator/`，
   只声明外层时 wheel 里没有内层 → 运行报 `No module named 'calculator'`。
   本轮用脚本枚举出 19 个包映射（`tests` 包排除，不进分发）。
2. **脚本式工具的 `sys.path` 假设**。它们靠"脚本目录在 `sys.path[0]`"来
   `import calculator` / `import core`；装进 `allin_toolkit.tools.*` 后那层路径没了，
   必须在分派前把工具目录补进 `sys.path`。9 个里至少 2 个立刻因此报错。

### 3.2 能力边界（必须说清）

**九个工具全部是 tkinter GUI**（实测：9/9 含 tkinter 引用）。无头环境能装、能 `--list`，
但启动具体工具会因拿不到显示而失败。

⇒ `allin-toolkit` 解决的是**分发与更新**，不是"让 GUI 工具无头可跑"。
把它当成"库"来在 CI 里调用是错的期待。

## 4. 非 Python 侧：缺口的确切形状

| 技术栈 | 数量 | 有没有统一分发渠道 | 现状 |
|---|---|---|---|
| Python | 56（裸源码）+ 7（有 pyproject） | ✅ PyPI（需先打包 + 改名） | 已走通样板 |
| JavaScript | 5 + 3（有 package.json）= 8 | ⚠️ npm 有，但**本仓全未发布** | 未动 |
| C++ | 1 | ❌ 无包管理器 | 未动 |

**缺口的本质不是"少了几个文件"，而是**：

- Python 项目至少有**一条可走的路**（打包 → 发布 → 引用），走通后能被 venv 统一管理；
- JS 项目路存在但没走（未发 npm）；
- C++ 项目**根本没有路** —— 只能继续以源码形式存在，或依赖 vcpkg/conan 这类额外基建。

所以"为什么复制大于删除"这个结论在非 Python 侧**仍然成立**，不是保守，是没有替代物。

## 5. 本轮决策（全哥选定）

| 项 | 决策 |
|---|---|
| Python 工具类 | 合并为 `allin-toolkit`，已发布，合集改引用（见 §3） |
| 独立应用（34 游戏 + 播放器等） | **保留源码** + 合集 `archive/<名>` 分支引用，按需检出；不 pip 化（装了也得 `main.py` 跑） |
| 非 Python（5 JS + 1 C++） | **只记账，不强行统一**。等 Python 侧跑顺再谈 |

## 6. 留给后续的判断点

1. **独立应用要不要也打包**？本轮判定"不值得"（它们是作品不是依赖）。若未来要做"一键装上全部原型"，
   那是**另一个包**（`allin-prototypes`）的事，不该混进 toolkit。
2. **JS 侧要不要发 npm**？取决于是否有跨仓复用的真实需求 —— 目前看多为独立小应用，复用例不明确。
3. **C++ 那一个**（`haha` 里的 cpp 部分）建议维持源码，不引入包管理器。
4. **通用名冲突**如果将来要按原名发布，需要向 PyPI 主张名称所有权（PEP 541），成本高、成功率低 —— 不推荐。

## 7. 一条方法论沉淀

这轮最有价值的不是发布了包，而是把"能不能改引用"从直觉变成了可核对的数字：

- 直觉：「有 pyproject 就能 pip install」
- 实测：7 个有 pyproject 的，6 个在 PyPI 上 404
- ⇒ **"本地能构建" ≠ "对方能安装"**。判断能否改引用，判据必须是「包里真的存在这个发行版本」，
  而不是「仓里有没有打包配置文件」。
