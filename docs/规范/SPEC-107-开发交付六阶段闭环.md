## 1. 六阶段总览

| 阶段 | 名称 | 核心产物 | 退出条件（可机检优先） |
|---|---|---|---|
| 一 | 需求分析 | 需求陈述（目标/边界/约束/验收口径） | 四要素齐全；验收口径可判定 |
| 二 | 任务拆分 | 子任务清单 + 落盘状态 | 每子任务有范围与验收；状态文件可支撑"继续"接续 |
| 三 | 开发 | 代码/文档改动 + 改前备份 + 安全检查记录 | 备份 sha256 一致；安全检查全过；改动范围经 diff 复核 |
| 四 | 审查 | 机器实跑日志 + 带行号的问题清单 | 日志落盘；每个问题带 file:line；无证据结论作废 |
| 五 | 测试 | 独立功能测试 + 性能审查 | 功能测试实跑通过；性能审查按范围执行并留数 |
| 六 | 修复闭环 | 修复 + 阶段四/五复验 + 输出闸门快照 | 复验全绿；输出前 D1–D12 快照全空 |

**铁律**：任一阶段的退出条件不满足，不得进入下一阶段宣告完成；"写了不等于跑了，跑了不等于绿了"。

## 2. 阶段一 · 需求分析

四要素必须齐全：

1. **目标**：要解决什么，一句话可陈述。
2. **边界**：做什么、不做什么（Out of Scope 同样要写）。
3. **约束**：不可触碰的线（铁律、安全红线、兼容边界）。
4. **验收口径**：可判定的完成条件（命令 + 期望输出，或可观测事实）。

**反模式**：把"目标 + 需求 + 验收口径"三项缺失包装成"待用户确认"的伪阻断——凡 agent 可用工具从本仓实地发掘的，一律自取，不留给用户（输出闸门 D1、D4、D6 同样拦截此类）。本规范自身即按此原则从本仓发掘：目标仓 = allin，需求 = 六阶段无成文规范，验收 = 文档契约 + 全门禁。

## 3. 阶段二 · 任务拆分与状态落盘

1. 把需求拆成独立可验证的子任务，每项写明范围与验收。
2. **状态必须落盘**：写入当前工作区的 `.workbuddy/memory/<YYYY-MM-DD>.md`（append-only），记录已识别子问题及状态（executed / diagnosed-only）、环境基线、关键决策与回滚方式。
3. **"继续"接续协议**：用户说"继续"时，先读状态文件，从第一个未完成子任务接续，不重复已 executed 的项，不重问已回答的问题。

## 4. 阶段四前置 · 改码前备份与安全检查

> 本章属阶段三（开发）的强制前置，单列以便定位。

### 4.1 备份（强制）

- 改动任何文件前，先把原文件按原目录结构备份到工作区证据目录，保留 `sha256sum` 对照。
- 备份校验：`sha256sum 原文件 备份文件` 两者逐字节一致方可继续。
- 无备份即改文件 = 违反本规范，输出闸门按 D9（可靠验证）拦截。

### 4.2 安全检查（"22 项"口径说明与可执行集）

**口径如实记录**：全哥指令要求"22 项安全强检查，任一不通过即一票否决"。2026-11-20 实地核查——G:\allin 与 WorkBuddy 技能库中**无名为"22 项安全强检查"的成文清单**（Grep `22项|22 项|安全强检查` 零命中；仓内出现的"22 项"指仓库迁移项数，与安全无关）。**本规范不虚构 22 条**。

在完整清单未给出前，执行以下**已有门禁承载体**的核验集作为强制前置，逐项留证；任一不通过即停：

| # | 核验项 | 承载体 / 命令 |
|---|---|---|
| 1 | 工作树基线可解释 | `git status --short` |
| 2 | 备份存在且 sha256 一致 | `sha256sum` 对照（§4.1） |
| 3 | 无凭据泄漏面 | `g03-credentials` |
| 4 | 无机器特定绝对路径 | `g01-paths` |
| 5 | 无硬编码路径 | `check_hardcoded.ps1` |
| 6 | 无 Python 编码/转义缺陷 | `g09-python-hygiene`、`check_ps1_bom.py` |
| 7 | 无未定义名 | `g11-undef-names` |
| 8 | 仓库卫生 | `g05-hygiene`、`repo_hygiene.py --all` |
| 9 | 改动范围可数 | `git diff --stat` + 逐行 diff 复核 |
| 10 | 不触碰密钥/凭据/仓库结构 | 人工判定 + §4.1 备份范围 |

**一票否决**：上述任一项不通过，停止开发，不改文件。清单扩充到 22 项须由全哥给出或明确授权拟定，并在此表追加、升修订记录。

## 5. 阶段四 · 机器审查（证据硬要求）

1. **必须机器实跑**：用 `scripts/run_all_gates.sh` 及专项门禁/测试实际执行，禁止以"看代码应该没问题"替代。
2. **日志落盘**：完整 stdout/stderr 落到工作区证据目录，文件名带阶段与日期；记录退出码。
3. **问题带行号**：每个问题标注 `文件路径:行号`（如 `tools/gate/check_arch_assets.py:167`），并写明判据依据。
4. **无证据作废**：无法给出日志行 + 行号 + 判据的结论，视为幻觉，不得进入问题清单。
5. **先证伪自己**：报"有问题"前先核实权威源与判据（避免误报）；报"全绿"前先确认覆盖完整（避免漏报）。

**稳定判据**：`run_all_gates.sh` 以 `ALLIN_GATE_SUMMARY status=clean fail=0` 且退出码 0、末行"全部门禁通过"为全绿；任何 `fail>0` 为未通过。

## 6. 阶段五 · 测试与性能审查

### 6.1 独立功能测试

- 测试须独立于开发者自述：由机器实跑既有测试（unittest / pytest / smoke / e2e），不是口头确认。
- 记录测试名、通过数、退出码。

### 6.2 性能审查（按范围三选一）

| 范围 | 适用 | 做法 |
|---|---|---|
| 全项目 | 架构/跨面改造 | 全链门禁时长 + 端到端冒烟 + 关键路径基线对比 |
| 全模块 | 单子系统改造 | 该模块基准测试 + 调用链采样 |
| 单一模块 | 单点修复 | 受影响函数/端点的前后对比 |

- 数值先实测基线，再定阈值；无阈值的记录实测值并标注"待裁决"，不虚构达标。
- 证据（命令 + 输出）落盘，格式同阶段四。

## 7. 阶段六 · 修复闭环与输出闸门

### 7.1 修复闭环

1. 对阶段四每个带行号的问题逐条修复。
2. 修复后先跑**单点复验**（失败的那道门禁/测试单独复跑），确认转绿。
3. 再跑**全链复验**（阶段四 + 阶段五全套），确认无回归。
4. `git diff` 复核改动范围，确认无越界改动。

### 7.2 输出闸门（每次结果交付前）

**触发范围**：任何一次向用户交付结果之前——文件、总结、结论、状态汇报、提问，均适用（含本规范自身的交付，元递归）。

**动作**：实际加载 WorkBuddy 技能 `delivery-no-pseudoblock`（产生真实加载状态），对**整条待发消息（含结尾）**逐项执行 D1–D12，并在消息内贴「闸门快照」，每项简略写出实际核对内容；缺任一项视为未跑全。

**口径如实记录**：全哥指令称"C1–C10 检查"，WorkBuddy 技能库中无 C1–C10，实际技能 `delivery-no-pseudoblock` 为 **D1–D12（12 项）**；全哥列的 10 类拦截点（责任转嫁、半途交付、最优步延后、伪阻断提问、结尾藏单、自主闭环缺失、含混表述、口径矛盾、证据缺失、事后补加载）全部可映射到 D1–D12。故按 D1–D12 执行并说明映射。

**加载时机**：闸门加载必须发生在发送前最后，不得在回合开头盖完章再干活。

## 8. 与协作流程的关系

- 本规范六阶段 ⊂ 任务执行面；SPEC-002 §二 五阶段 ⊃ 协作节奏面。
- 一次任务：用 SPEC-002 决定"问不问、计划给谁看、何时推送"，用本规范决定"怎么审查、证据长什么样、何时算可交付"。
- 高风险动作（推送/建仓/删除/密钥/仓库结构）仍按 SPEC-002 §零 权限矩阵与铁律 3 执行——本地提交自主做，推送须在场放行，推后 `ls-remote` 核对 IN_SYNC。
