## 1. 分支与协作模型（🔴 P0 — 受保护，不可跳过）

- **主分支唯一且受保护**：只允许一个 `master`；开发在本地 fork 后提 PR 合入，**禁止强制推送 master**。
  - allin 现状：单人维护，但约定 **master 受保护**——日常提交走 fast-forward / PR，不 `--force` master；
    仅推 tag 可用 `git push -f origin <tag>`（见发版指南 `tools/gitee_release.py` 的 `release` 子命令，已自动探测分支）。
- **每发布版本必须打 tag**：标签含「名 + 描述」（如 `v1.2.0` + 变更摘要）；release 必须基于已推送的 tag。
- **Fork + PR 合入流程**（多协作者场景）：fork → 分支开发 → PR → 代码审查 → 合入；各社区另有「代码合入要求」细则。

---

## 2. 命名与结构约定（🟠 P1）

- **文档（md）**：用 `xxx-xxx.md` 连字符格式，文件名按内容语义命名（如本篇 `gitee协作规范.md`，而非 `规范1.md`）。
- **资源 / 目录**：不含 `*`、`/`、`\`、空格等特殊字符，避免跨平台路径与 URL 编码坑。
- **目录结构**：清晰分层（如 `vendor/板型/demo`、`tools/`、`docs/`），方便导航与门禁扫描。

---

## 3. 仓库卫生与体积软上限（🟠 P1）

- **体积参考值（社区仓内部约定，非 Gitee 平台硬限）**：单仓 ≤ 3GB、单文件 ≤ 300MB（HiSpark 规范）。
  - ⚠ 区分：**Gitee 平台硬限**是**发行版附件单文件 100MB**（社区版）、每仓库总附件 1GB（已联网核实，见发版指南 §2）。
    普通代码文件无 300MB 平台限制，但大二进制应走 Git LFS 或发行版附件，**不进 commit 历史**。
- **`.gitignore` 必须排除密钥（强制）**：
  ```gitignore
  .env
  .env.local
  *.pem
  *.key
  data/
  uploads/
  ```
  - 误把 `.env` / 密钥提交进历史：**删文件 + 提交不够**（仍留历史），须 `git filter-repo` 重写历史才能真正清除。
  - 第一次提交前就设好 `.gitignore` 最省事（见发版指南 P0 安全门禁，门禁也会拦密钥本体）。

## 4. 开源许可证选择（🟢 P2）

- **MIT**：宽松，仅保留版权声明（**全哥项目统一 MIT**）。
- **Apache 2.0**：宽松 + 明确专利授权。
- **GPL**：传染性，衍生作品须同协议开源（带 GPL 第三方二进制时整体受其约束，见发版指南 P0 许可核查）。
- 不对外开源的项目：**不勾许可证**，避免背上不明授权条款。

---

## 5. 分支模型对比（🟢 P2 — 小团队参考）

- **GitHub Flow**：`master` + feature 分支，PR 审查合入后部署。简洁，适合小团队 / 快速迭代（**推荐**）。
- **Git Flow**：`master`/`develop`/`feature`/`release`/`hotfix` 多分支，适合大型多阶段发布。
- Gitee 默认分支 `master`（GitHub 为 `main`）；新建仓库推荐**单分支起步**，按需再建。

---

## 6. 新建仓库选项速查（摘自 cnblogs 指南）

| 选项 | 公司内部 / 私密 | 个人 / 开源展示 |
|---|---|---|
| 可见性 | 私有 | 公开或私有 |
| README | 勾选 | 勾选 |
| `.gitignore` | 勾选 + **手动补 `.env` 等敏感项** | 勾选 |
| 开源许可证 | 不勾（确定开源再选） | 确定开源再选 |
| 分支模型 | 单分支 | 单分支 |
| Issue / PR 模板 | 不勾（流程成型再补） | 不勾 |

> 误区：私有 ≠ 安全。私有仓库只是限制访问，仓库内密钥仍需靠 `.gitignore` + 权限控制。
