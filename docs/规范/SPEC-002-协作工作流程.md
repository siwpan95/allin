## 零、协作模式两态（2026-09-24 用户拍板新增）

> **为什么要这一节**：§一~§六 定义的是"人在场"时的节奏。而**「逐项确认」「等放行」都隐含前提 = 用户在场**。
> 用户不在场时（跨轮自动推进、连续 goal 回合、批量任务），缺一条明确口径 —— 本节补上。
> **本节不改动 §二~§六**；它只回答一个问题：**哪些事在无人值守时可以自己做，哪些必须等人。**

| 模式 | 判据 | 典型场景 |
| --- | --- | --- |
| **在场模式** | 本回合内有用户回应（问答来回） | 用户逐条回「按推荐执行」「先推送这 5 笔」 |
| **自主模式** | 无人值守的自动推进 | 跨轮 goal 回合、用户明确离开、批量长任务 |

### 0.1 权限矩阵

| 动作 | 自主模式 | 在场模式 |
| --- | --- | --- |
| 读取 / 检索 / 分析 / 调研 | ✅ 自主 | ✅ |
| 写工作区内文件（文档、脚本、工具） | ✅ 自主 | ✅ |
| 跑测试 / 门禁 / 冒烟 | ✅ 自主 | ✅ |
| **本地 `git commit`** | ✅ **自主**（记账不等人） | ✅ |
| **`git push`** | ❌ **禁止** | ✅ 报「推什么」等一句放行 |
| 建仓 / 删仓 / 改仓名与可见性 / 强推 / 删分支标签 | ❌ 禁止 | ⚠ 逐项确认 |
| 密钥操作 / 仓库结构变更 | ❌ 禁止 | ⚠ 逐项确认 |
| 改 host composition / 改出厂 preset 安装 | ❌ 禁止 | ⚠ 逐项确认 |
| 删除文件（非归档） | ❌ 禁止（改归档） | ⚠ 逐项确认 |

### 0.2 自主模式的三条纪律

1. **遇岔路选推荐项，别停下等** —— 把每个自主决定写进会话交接：**决定 + 理由 + 备选 + 回滚方式**，标注「**自主决定·待复核**」，用户回来一次性复核。**成果优于待问清单。**
2. **攒着不推** —— 所有产物以本地提交留存；推送攒到用户在场，一次报清楚（铁律 3）。**"没人看的时候推"是纯粹的多余动作。**
3. **不可逆的一律不做** —— 破坏性操作、对外发布、动别人的东西：把命令与理由写进交接**待放行**，不自己拍。

### 0.3 边界与升级触发

- 自主模式**不是无限授权**：一旦涉及 §一 的高风险动作、或需要用户价值判断（不是技术判断），**停下并留下待办**，不硬推。
- 用户回来后：先看会话交接的「自主决定·待复核」清单，逐条 ✅/❌；被否的**入复盘**（教训进 MEMORY）。
- **连续多轮自主后**：主动汇报一次进度与待决项，而不是一路做完再讲。
## 一、任务分档

| 档 | 判据 | 走哪些阶段 | 示例 |
|---|---|---|---|
| **大任务** | 结构性 / 多仓 / 架构 / 规则改造；或跨会话长战线 | 全流程五步，计划必须书面摆出 | R2 内核并入、阶段 1~4 反向重构、建仓迁移 |
| **中任务** | 单仓功能级、多文件改动、影响面可数 | 轻量版：问一句确认目标 → 简计划（几行）→ 执行 → 汇报（复盘并入汇报） | 单仓引擎接入、探针修复 |
| **小任务** | 记账 / 清理 / 单点修复 / 文档小改 | 直接执行 + 汇报；不问不计划 | LICENSE 恢复、.gitignore 补齐、README 记账节 |

**高风险动作不分档**：推送、建仓、删除、密钥操作、仓库结构变更——无论任务大小，
**逐项确认后才做**（放行话术同样适用）。

> ⚠ **本档位表隐含"用户在场"**。无人值守时按 **§零 协作模式两态** 执行：本地提交自主做、**推送与不可逆动作一律攒着等在场**。

## 二、五阶段定义

### 1. 先问（理解项目，补齐目标、边界与约束）
- **产物**：一批 ≤4 个问题（可用选项题，给推荐项 Recommended）；或「无问题，理解如下」的复述。
- **必问项**（影响执行的才问）：目标是什么 / 边界（做什么不做什么）/ 约束（不可触碰的线、验收口径）/ 我容易自作主张的部分。
- **退出条件**：用户回答完毕（或确认无问题）。
- 反模式：盘问式问卷；问「不重要但显得认真」的问题。

### 2. 再计划（拆解路径、依赖与风险）
- **产物**：书面计划——交付物清单、步骤路径、依赖关系、风险与对策、（大任务附）验收判据。
- 计划里必须写「执行中遇计划外重大事实 → 回头补问」这一条（默认含）。
- **退出条件**：计划呈交，等待放行。

### 3. 再 review（对照原始描述，补上遗漏）
- 在执行前把计划**对照用户原始描述逐条自查**：有没有漏掉的目标、边界、约束？
- **产物**：补漏清单（没有也要明说「自查无遗漏」）+ 计划修订版。
- 自查角度：范围是否完整 / 验收口径是否对齐 / 用户此前的偏好（零容忍表面工程、README 先读、记账）是否覆盖。
- **退出条件**：修订版与用户达成一致。

### 4. 执行（按共同认知落地）
- **放行机制**：计划呈交后须用户明确放行（「开始执行」「按计划」等）；用户拒绝/修改 → 回到计划。
- 高风险动作（推送/建仓/删除/密钥/仓库结构变更）在执行到该步前再逐项确认一次。
- 执行中遇**计划外重大事实**（如勘察结论推翻计划假设：异构模型无法接入、应用已损坏等）→ 停下回头补问；**小偏差** → 继续并记入复盘。
- 执行动作自证：每步有验证（测试全绿 / ls-remote 核对 / 黄金值 exit 0）。

### 5. 复盘（第五步，追加）
- 大/中任务执行完**对照计划复盘**：结果 vs 计划、偏差与原因、教训/新坑。
- **产物**：教训与坑写入 MEMORY（通用纪律）与会话交接（事实流水）——现有 §三十五~四十 即此形态。
- 小任务：汇报即复盘（三行内：做了什么 / 验证结果 / 有无新坑）。

## 三、话术约定

| 场景 | 话术 |
|---|---|
| 计划呈交 | 以「## 计划：……」摆出，结尾「无异议请回复『开始执行』；要调整哪里直接说。」 |
| 用户放行 | 「开始执行」「按计划」→ 立即动手 |
| 用户修改 | 按修改重摆计划，再等放行 |
| 执行中重大偏差 | 「计划外事实：……。补问：……」 |
| 任务完成 | 汇报含：结果 / 验证 / 与计划偏差 / 新坑 |

## 四、与既有机制的关系

- **MEMORY**：铁律级精要（铁律 2）；本文件是详版模板，改流程只改这里。
- **会话交接**：每步执行记录照旧追加；本流程本身的启用与变更也记入交接。
- **goal 循环**：长期目标仍可用 goal 工具承载。**goal 回合通常落在"自主模式"**（无人值守推进）→ 按 §零 执行：选推荐项自主推进 + 本地提交 + **不推送** + 决定记交接待复核。
- **工具审批弹窗**：与本约定无关（那是安全机制）；本约定是协作节奏约定。

## 六、冗余/退役判定三查（2026-09-02 落实，musickit radio 误删教训）

判定「A 已并入/迁移到 B，A 可删/归档」属于**仓库结构变更级高风险动作**，除逐项确认外，必须先过三查：

1. **列功能面**：把 A 拆成独立功能面清单（例：radio = 转播 + 直播（渲染推流）+ 控制面板 + 排程 + PWA）；
2. **逐面找接任者**：每个功能面在 B 中找**实证**接任者——git grep / 代码引用 / README 明载为准，不得凭「B 也叫电台」的印象；
3. **无接任者不可删**：任一面无接任者 → A 的该面不可删（保留该面，或先在 B 实现接任再删）。

删除/归档动作的提交信息与交接文档必须附「功能面 × 接任者」对照表。
事故参照（2026-09-02）：93db08f 只验证了转播面（Node 转播版确已接任），直播面
（musickit 渲染→推流）无接任者却被一并删除，管线输出端真空（交接 §六十一）。
