# 多语言棋类引擎实验场（functional-parity engine lab）

适用场景：把"同一套规则内核 + AI 用 N 种语言各实现一遍，并验证功能对等 + 跑跨语言循环赛"这类工程
（原型：`G:\repos\lab` 国际象棋 10 语言；围棋版：`G:\repos\weiqi_lab` 六语言）。

## 1. 交付形态（已被验证的目录范式）

```
<repo>/
  docs/RULES_SPEC.md        规则规范 = 唯一真相来源（含 Zobrist 等跨语言常量、判定次序）
  docs/PROTOCOL_SPEC.md     JSON-stdio 协议（语义对齐 GTP/UCI，便于未来接 GUI）
  docs/PORTING.md           移植简报：交付物 + 验收门 + 性能要点
  spec/golden.json          黄金值测试集（冻结产物；各语言共用的唯一测试真相）
  spec/regress/*.tst        CGTC/UCI 式回归用例（局面 + 期望着法集）
  tools/gen_golden.py       生成器（必须含人工推导交叉校验，见 §3）
  tools/{sgf,gtp,regress}.mjs   ★ 共享 I/O 层：只做一份（见 §2.5）
  <Lang>Engine1..N/         各语言：规则核心 + AI + 自测 + driver
  harness/                  引擎清单 + JSON-stdio 客户端 + 一致性门
  tournament/               独立裁判 + 循环赛 + 开局库 + 战报
```

### 2.5 共享 I/O 层原则（N 语言 ≠ N 份实现）
**规则内核必须逐语言各实现一份**（这正是"移植正确性"的研究对象）；
但 **SGF 读写 / GTP 适配器 / 让子定式 / 任何与规则无关的 I/O 与工具**应当**只做一份**，
放在 `tools/`，通过 JSON-stdio 驱动**全部**引擎。理由：避免 N 倍重复与 N 倍漂移，
且让 GoGui/Sabaki/gogui-regress 一次接入即可驱动所有语言。
验收：`node tools/tests_io.mjs`（快照断言，如让子星位表）+ `node tools/regress.mjs`（每引擎逐条判定）。
> 实现要点：GTP 适配器只做协议翻译（`reg_genmove` = `genmove` 后立刻 `undo`）；
> 让子按规范星位表放子后**白方先走**、`komi` 由控制器显式设置（不隐式改）；
> SGF 坐标是 y 向下、引擎/GTP 是 y 向上 → 必须翻转并写测试。

## 2. 顺序（不要跳步）

1. **联网调研** → 写 `docs/RESEARCH.md`（来源 + 许可证 + 借用范围；本项目全程只借思想不抄码）。
2. **写规范**：把规则写成可直接编码的伪代码级文字（判定次序、常量、输出格式）。
   - 跨语言共享常量必须钉死（如 Zobrist 的 splitmix64 表、种子、hex 输出格式、reason 枚举）。
   - 明确"哪些必须逐位一致 / 哪些允许差异"（规则必须；AI 的 RNG 不必）。
3. **写黄金值用例**（setup + op + expect）→ 见 §3。
4. **写参考实现**（选迭代最快的语言：Python 或 JS），跑到自测全绿。
5. **并行子代理移植其余语言**：每个代理的提示词必须包含"必读文件清单 + 交付物 + 硬性验收命令 +
   「不得修改 spec/golden.json，认为有误则报告」"。参考实现 + 规范齐备时通过率极高（本仓 4/4 一次通过）。
6. **写 harness**（§4 三项）→ ALL GREEN 才继续。
7. **写独立裁判 + 循环赛**（§5）。
8. git init + 三件套（README/LICENSE/.gitignore）+ `.gitattributes`（`* text=auto eol=lf`，消除 Windows 换行告警）。

## 3. 黄金值（本项目最有价值的一环）

- 围棋**没有 perft 等价物**（超级劫使局面依赖历史）→ 改用"**局面 + 期望输出**"范式（CGTC 式）：
  `{"id","op","setup":{size,rules,stones,moves,side,ko_point},"args","expect"}`；
  op ∈ key / legal / legal_moves / play / undo / score / prisoners / over。
- **生成器必须内置人工推导表（HAND）并与参考实现比对，不一致就拒绝生成**。
  代价：写了 ~35 条手算期望，换来抓出 5 处**用例设计错误**（自洽测试等于没测试）：
  - 提子用例必须让目标棋块"仅剩那一口气"（多次把整块气数算错）；
  - 在 PSK（位置禁全同）下，"自提后盘面复原"是**非法**的 → 单纯"允许自杀"用例要改用多子自提；
  - **连续两次 pass 即终局**：任何"pass 清劫再回提"的用例会以 `reason="over"` 被拒（不是 superko）。
- 三档对照用例最有价值：同一局面在 `{ko:simple,suicide:allow}` / `tt(PSK+allow)` / `jp(simple,forbid)`
  下应给出三种不同结论（合法 / superko / suicide），一次锁死自杀与禁全同的判定次序。

## 4. harness 三项校验（跨语言一致性门）

1. **各引擎内置自测**：`selftest` 命令读同一份 golden.json，要求 0 failed。
2. **跨引擎协议差分**：生成**确定性命令流**（覆盖 多种盘径 × 各规则档 × 含故意非法着法），
   喂给全部引擎，比对 `ok/reason/result` **逐位一致**（`error` 文案宽松比对，避免脆性）。
3. **独立裁判交叉校验**：裁判用**机制不同的实现**（围棋版：字符串键判超级劫、无 Zobrist、
   显式队列代替 stamp 数组）重放同一命令流，比对合法性/提子数/合法点集/计分。
   → 这是唯一能证明"规范本身没写错"的环节（五引擎同源同错时，只有第三方实现能发现）。

## 5. 裁决与循环赛

- **裁判层负责**：合法性裁决（非法着法判负）、终局计分、手数上限（超限按现状计分并标注）。
- **状态同步陷阱**：开局线与非行棋方的着法**必须显式同步给引擎**（`play`），否则引擎内部 side 漂移
  → 典型症状 `genmove for wrong side`。每局开始要 `clear` 全部引擎。
- **固定算力**（Gomill 建议）：按各语言实测速度折算 playouts 预算至"等效 ~1s/手"，
  而不是统一 playouts（否则解释器语言被碾压，比的是语言不是引擎）。
- 战报含：设置 / 交叉表 / 逐局（含尾盘与异常）/ 引擎统计 / **走法分歧率**（多样性指标，供跨期对比）。

## 6. MCTS 棋类引擎的结构性陷阱（血泪清单）

1. **纯胜负估值会退化**：局面已定时所有着法同值 → 选择只由"未访问优先"支配 → 实质按下标选点。
   → 必须用**分差归一化估值**：`v = 0.5 + 0.5·clip((我方得分−对方得分−贴目)/scale, −1, 1)`，scale≈点位数/2。
   （Bouzy 讲义：S+WLI 明显优于纯胜负。）
2. **PASS 不要入树**：入树会被系统性高估（先验 0.5 中性值即可抢占访问；虚拟访问还会污染"按访问数选点"）。
   → 改：无任何非填眼着法 → 过手；对手已过手且估值 ≥ 阈值 → 过手终局。
3. **playout 不要"镜像过手"**：对手 pass 就立刻 pass 回会让 **pass 变成必胜手段**（局面立刻结束且领先方赢）。
   → 只保留 Fuego 式"无着可走才 pass"。
4. **空盘候选要限中央区**：否则空盘 81 个候选分薄预算，开局乱下 1-1。
5. 其他必备项：眼位过滤（不填自己单点真眼，打吃例外）、提子/救子优先、避自填气、
   局部候选 playout（最后一手 1 邻域，无候选退全盘）、树内提子先验（等效经验）。
6. **性能**：先实测再优化（profiler，别猜）。棋块扫描用**代际 stamp 数组**（零 set 分配）；
   **提子预检**（邻子除落点外无空邻才整块扫描）+ **气数下界**（落点空邻 ≥2 则己方气必 ≥2）+ **单子判定**
   （own_size==1 ⟺ 无同色邻点）。Python 9 路实测 ~130–300 playouts/s，Rust/C++ ~1.2 万，C# ~1 万，JS ~870。
7. **战术分辨力要量化并如实记录**：纯标准库朴素 playout 在 9 路约 **±5 点**（300 playouts），
   1–3 子局部战术不可靠。不要为了"测试通过"去调参数掩盖，写进 README 的已知限制；
   循环赛结论按"弱引擎互搏"解读。

## 7. 学习型组件（Markov / 特征模型 / CNN）的纪律

**先诊断语料，再选模型**。围棋落子建模的经验链条（已在 weiqi_lab 实测走完，含正反两面）：

1. **状态空间要配得上语料量**：5×5 棋形签名（4²⁵ 态）在千级样本下覆盖率只有 0.9%；
   降到 3×3 主上下文 + **十字邻域退避**（4⁴=256 态）后覆盖率升到 ~95–100%。
   → 任何"状态 × 动作"表都必须配 **backoff/回退层级**，并报告**覆盖率**（低覆盖率下的高命中率是幻觉）。
2. **必须设三类基线**：① 均匀基线（1/合法着法）；② **常数基线**（全局众数动作）；
   ③ **后验众数上限**（同上下文内的最好可能，注意标注留一污染使其偏乐观）。
   只报"命中率"而不给基线 = 无结论。
3. **最强的诊断量是"局部偏置比"**：`紧邻(≤1)手数占比 ÷ 均匀随机期望`。它是**跨盘径可比**的归一化量，
   能一眼判定语料质量：本项目实测 —— 弱引擎自对弈 **1.97×**（top-1 仅 0.91× 均匀，学不到东西）
   vs 人类职业棋谱 **18.1×**（top-1 **17.0×** 均匀，信号强烈）。**同一模型、同一代码，只换语料。**
   另一个直观佐证：人类语料的稳态落子热点落在**星位**，弱引擎语料只有 `pass` 与边角噪声。
4. **两轴独立、都要做**：语料质量轴（0.91× → 17.0×）与模型容量轴（模式模型 11.4% → CNN **25.84%**）。
   先修语料（便宜、收益最大），再上容量（贵、需依赖）。
5. **CNN 的落地形态**：破例依赖要**隔离在独立目录**（本项目 `ml/`，仅 numpy），并写清"破例范围"；
   纯 numpy 手写 conv3x3+Adam 在小规模（~2 万参数 / 12 万位置）即可跑通并显著超查表模型
   （top-1 2.26×），但推理慢 ~22×、且很快碰到容量上限 —— **报结论时要同时给"增益"与"代价"**。
   不建议直接进引擎；更务实的是**蒸馏成零依赖的离线先验表**。
6. **负结论要写进 README 的已知限制**：把"未超过基线 + 根因"如实记录，比虚高的命中率有价值。

## 7.1 「零依赖化」一个学习模型：两条路，先算信息账

训练好的模型（CNN/线性）要进零依赖运行时时，有两条路，**先判断增益来自局部还是全局**再选：

| 路径 | 做法 | 何时有效 | 何时无用 |
|---|---|---|---|
| **A. 蒸馏成查表**（上下文 → 动作分布） | 用 teacher 概率在语料上聚合；上下文半径/退避层级可调（如 主 5×5 / 退避 3×3），并做条目剪枝控体积 | teacher 的增益主要来自**局部模式**，或学生数据稀疏需要 teacher 平滑（本项目 9 路：计数表 4.13% → 蒸馏 7.80%） | teacher 的增益来自**全局**信息（本项目 19 路：蒸馏 7.33% ≈ 计数表 7.25%，而 teacher 本体 25.84% —— 那 18.6pp 是全局棋形，任何固定邻域表都装不下） |
| **B. 权重导出 + 纯 JS/纯语言前向** | 导出参数 JSON（本例 0.22MB），用目标语言手写前向；运行期只需 JSON | 想**无损**保留 teacher 预测力 | 前向太贵的场景（本项目 19 路约 20–40ms/次：够开局/分析用，不够 playout 用） |

- **必须做逐位对拍**：两语言前向各跑同一批局面，比对 logits（本项目 max|Δlogit| = 3.8e-6、argmax 全同）
  —— float32 级一致才算等价。
- ⚠️ **预测力 ≠ 行为合理**：本项目 9 路 CNN 的 top-1 有 17.58%，但它训练于 60 局**弱引擎语料**，
  生成的"开局"落在边角（学到的是弱引擎的怪癖）。**评估新组件要看行为，不只看指标。**
- ⚠️ **蒸馏表在弱语料上反而更有效**这一反直觉现象值得记录：teacher 的平滑掩盖了学生数据的稀疏。

## 7.2 第三方数据的获取与分发纪律

- 语料优先找**结构清晰、体量可控**的公开归档；下载后先算 **SHA256** 存档。
- **大归档不落地就不落地**：写流式解析器（如最小 tar 读取器 + zlib）直接抽取需要的文件，
  避免在 Windows 上生成数万个碎文件。
- ⚠️ **自研二进制格式解析必须用真实样本做端到端断言**：本项目曾把 tar 的 typeflag
  `0x30`（`'0'` = 常规文件）误判为目录，导致**导入 0 局却"看起来成功"**（还打了正常日志）。
  正确判定：仅 `'0'`/`'\0'` 是常规文件，`'5'` 才是目录。
- **分发纪律**：来源许可不明时，**只入库导入脚本 + 来源 URL + SHA256 + 复现命令**，
  数据本体（原始归档与派生语料）一律 gitignore；模型权重（派生自数据）可入库。

## 7.3 多组 A/B 的统计纪律（最容易出错的一步）

- **必须做多重比较校正**。本项目 4 组 → 6 对比较：某对原始 p=0.0091 看似显著（α=0.05），
  **Bonferroni 校正后 0.0543 不显著**（α'=0.05/6=0.0083）——**不校正就会发布错误结论**。
  在脚本里写死：`nPairs = k*(k-1)/2; alphaAdj = 0.05/nPairs; pAdj = min(1, p*nPairs)`，并同时汇报原始与校正后 p。
- **样本量要够，但要如实标注**：≥100 局/组只对"大效应"敏感；弱引擎下开局差异本就小，
  440 局仍不可分辨——**把"无显著差异"当作结论本身**，而不是"继续加样本直到显著"。
- **结果指标之外必须看行为指标**：本项目四组胜负无差异，但开局棋形差异巨大
  （唯一开局线 110/110 vs **25/110**、1–2 线占比 0% vs 74%）。
  行为画像可用 `openings_profile` 式**离线复现**（开局线由 `(mode, plies, seed)` 唯一决定，不必重跑对局）。
- ⚠️「无损保留 teacher」的边界：把大模型导出成"权重 JSON + 纯语言前向"确实无损，
  但**无损的是 teacher 的全部行为——包括它的缺陷**。本项目 CNN 学自 60 局弱引擎语料，
  前向开局忠实复现了"贴边 + 大量重复"的怪癖（25/110 唯一线）。
  → 导出后**必须跑行为画像**（多样性/位置分布），不能只看 top-1。

## 7.4 把学习模型接进 MCTS 当先验：三步与两条铁律

**接线方式（PUCT 先验，AlphaZero 形式）**：`val = Q + c·√(lnN/(1+n)) + w·P(a)·√N/(1+n)`
—— 先验项随访问数自然衰减；`w=0` 时公式退化为原 UCT，**基线逐位不变**（可安全默认关闭）。
根节点每次 genmove 只跑 1 次前向（19 路约 20–40ms），深层节点用 `max_nodes` 预算限制。

**铁律 1：先验质量的上限 = 教师质量的上限。** 本项目实测对照（同一套机制、同一份代码）：
- 9 路教师 = 弱引擎自对弈 → 先验指向**角部一线**（J9/J1/B2/A1），把搜索引导到坏点；
- 19 路教师 = 人类职业棋谱 → 引擎选点与职业棋手**精确吻合 0%→18.8%、邻近 ≤2 路 6.3%→50%**
  （随机基线 0.32%）。
→ 所以"接先验"之前先问：**teacher 比随机好多少**；teacher 是弱引擎自对弈时，先验可能是负资产。

**铁律 2：必须验证"先验真的生效"，不能只看指标。** 三个便宜的探针：
① 同 seed 下开/关先验的选点差异率（应显著 >0）；② 首选着法访问数是否上升（集中算力）；
③ 直接打印 policy argmax 的落点分布（看是否落在合理区域——角部偏置一眼可辨）。

## 7.5 性能优化：先量"调用次数"，再谈"单次成本"

- **用 `node --cpu-prof` + 采样聚合**（自写 15 行解析脚本）定位热点，比猜准得多。
  本项目 19 路剖析：`_scan` 50% + `simulate` 36% = 86.5%（此前误猜是候选生成，实测只占 0.1%）。
- **猴补丁计数**（包一层 `PBP.prototype.probe` 计数）比时间更能说明问题：
  实测 19 路 **probe/playout = 59,299（9 路的 35×）**，而单次成本只高 1.7×
  → 瓶颈是**调用次数**：playout 局部窗口无候选时退化为全盘 361 点扫描。
- **修法：逐圈扩大**（半径 1→2→4→全盘）→ 19 路 probe −38%、genmove −25%；9 路 −22%/−19%。
- 更深的优化方向：增量气数（pseudo-liberties，O(1) 打吃检测）、先选点后验证、in-place undo。
- ⚠️ **改了引擎行为后要重跑在跑的 A/B**：否则"测量的代码 ≠ 提交的代码"。宁可重启实验（损失十几分钟），
  也不要留下版本含混的结论。

## 7.6 实验信噪比纪律

弱引擎会把所有实验信号淹没，**先测"引擎有没有能力体现差异"再设计对比实验**：
- 本项目实测：9 路 400 playouts 时首选着法仅 **15 次访问**（预算被 ~70 个候选分薄）→ 选点近乎噪声。
  后果：开局方案 440 局 A/B、先验开关多组对比，全部"无显著差异"——**不是方案无效，是仪器太钝**。
- 判据：若"首选访问数 / 总预算" < 5%，任何战术级差异都测不出来 → 先做 §7.5 的提速与 §"搜索质量"改进。

## 7.7 对称归一化的"半归一"缺陷（本次抓到的最贵 bug）

**症状**：把棋形按 8 对称（或 4 旋转）归一到同一**键**，但**动作（应手偏移）仍按原始朝向记录**
→ 同一键下混入 8 个朝向的动作，分布被"抹平"（预测 top-1 掉到 1/8 量级）。
本项目实测：人类 19 路 top-1 **7.25% → 21.34%**（CNN 蒸馏表 7.33% → **22.70%**，≈ CNN 自身 25.84% 的 88%），
并因此**纠偏了一条已发布的错误结论**（曾判"表蒸馏路径有损、局部上下文装不下全局信息"——
真实主因是这个缺陷）。教训：**结论里出现"信息装不下"这类物理解释时，先怀疑实现有 bug。**

**为什么容易漏**：键的归一化很显眼（`min over 8 sym`），动作的归一化却"看起来不用做"——
对称群作用在动作上方向会变，必须显式 `action = SYM[INV[s]](action)`（记录）与 `SYM[s](action)`（查询），
且**群的逆元素表要单独列**（本项目 8 对称的逆不是自逆：0→0,1→3,2→2,3→1,4→4,5→5,6→6,7→7）。

**确诊方法（最可复用的技巧）：合成可判定用例。**
造一个"规范朝向"的棋形（对称稳定子平凡 → 朝向唯一可辨），把整组配置按 8 个朝向各喂一次、再各查一次，
真值 = 相应旋转后的动作：正确实现 **8/8 全中**，有缺陷 **2/8**（真值只占 1/8 票）。
把它钉成回归测试（`2/8` 那一侧也要断言"应当失败"），比读代码可靠得多。

**引擎/工具链两份实现必须加逐位交叉校验**：引擎为性能会用**整数编码**重写签名
（本项目：基 4 整数 vs 工具链的零填充数字串），加随机局面 × 多半径的 parity 测试
（比较 `parseInt(str, 4)` 数值）。本轮该测试一次抓到两个真 bug：**变换方向反了**、
**键的字符串形态不一致导致查表永不命中**（`"000121010"` vs `"1604"`）。

**排查清单**（症状 = "机制明明接通了，但指标毫无变化"）：
1. 查表真的命中了吗？（键的字符串/编码形态是否一致）
2. 变换方向对不对？（记录用逆、查询用正；用测试用例验证，别靠推导）
3. 命中后行为真的变了吗？（打印指纹：紧邻率 / 唯一线数 / 同 seed 可复现性）

## 7.8 便宜探针优先于昂贵 A/B（两段式评估）

对"策略类"改动（playout 偏置、先验、蒸馏表），先跑**便宜探针**再决定是否花几小时跑对局 A/B：
- **人类一致度探针**（`tools/human_agreement.mjs`）：固定 n 个人类局面，比"引擎选点 vs 职业棋手着法"的
  精确/邻近吻合率 + 两比例 z 检验。一次就能把"机制无效/有效"分开（本项目 0/32 → 4/32，p=0.0389）。
  ⚠️ **必须用留出段**（表是用同一语料前 80% 训的，否则等于自己考自己）。
- **playout 结构指标**：改动后 playout 平均步数/每手耗时是"机制是否真在起作用"的独立证据
  （本项目：LGR 步数 −14.6%、lib2 步数 +48.7%），比单看胜率更能解释结果。
- **固定 playout 的 A/B 只回答"同等模拟次数下谁更强"**；若改动改变了 playout 长度或每手耗时，
  报告必须同时给"步数/耗时/胜率"，否则结论会被误读（本项目 LGR：强度中性但快 15%；
  lib2：强度中性但慢 17%）。

## 7.9 样本量阶梯（不要在小 n 上宣布胜利）

同一个改进（渐进加宽）三次 A/B：90 局 p=0.0171 → 180 局 p=0.0204 → **300 局 p<0.0001**
——前两次都**没过 Bonferroni 门槛**（α'=0.01）。纪律：
- 小 n（~100 局）只做**筛选**；只有过 α' 的才算"显著"，其余一律写"趋势 / 中性"；
- 对筛选出的候选**升 n 复核**（300 局级）；不要"再加样本直到显著"式 p-hacking；
- **中性结果同样是结论**（本轮 LGR / lib2 都中性），且要把它们的速度/结构收益单独记账。

### 7.9.1 ⚠️ 「两个独立小样本同向」不是证据（本轮差点发布假结论）

本项目实例：某改进（`pbias`）在**两个各 200 局的独立运行**里给出方向一致的 **+7.0pp / +8.0pp**
（合并 400 局 p=0.0339）——看上去完全够写"有正向收益"。按纪律另做 **400 局确认实验**（全新 seed）：
只得 **49.3%**；合并 600 局回落 **50.8%（p=0.5637）** → **正向趋势纯属噪声**。

可复用的硬规则：
1. **筛选与确认必须用不同的 seed**（"独立运行"若共用数据生成方式不算独立）；
2. **方向一致 ≠ 证据**：小 n 下正负号是抛硬币，两个同向的概率本来就有 25%；
3. 报告里区分三档：**筛选（screening）/ 趋势（trend）/ 确认（confirmed）**，
   只有"确认"档能写进结论；合并多个小样本只能得到"探索性"标注；
4. **同一实验组的两侧都要同等复核**：本轮正侧（+8pp, p=0.11）被 400 局确认实验推翻后，
   负侧（−11pp, **p=0.0278——看起来比正侧更"可信"**）也做了 400 局复核，结果 **52.0%**，
   合并 600 局回到 **49.5%（p=0.7290）** → **同样是噪声**。
   **若只复核正侧而保留负侧，就会留下一个方向性错误的结论**（"弱教师有害、强教师有益"），
   而且它比真相"看起来更可信"。合计 **1200 局**后本项结论才是干净的"中性，与教师质量无关"。
5. 这类"确认实验推翻趋势"的记录**要留在文档里**（含被推翻的数字），它比结论本身更有教育价值。
6. **反向提示**：若某"效应"在两侧都容易达到 p≈0.03 而放大后消失，说明该实验的信噪比不足 ——
   与其继续调这个旋钮，不如去做 §7.6 的信噪比提升（提速 / 加预算 / 改估值），再回来测。

### 7.9.2 免费的体检：**传递性闭环检验**（用已有实验结果互相验算）

多个 A/B 若共享同一个实验组（或同一基线），它们之间就存在可验算的约束——
**不用跑新的实验，就能用算术发现矛盾**。

本项目实例：三个实验共用同一个 B（`{probe_k:3, pw_c:0.5, pw_min:6}`），但 A 不同：

| 实验 | A | B 胜率 |
|---|---|---|
| #1 | `{probe_k:3}` | 59.3% |
| #2 | `{}`（全关） | 72.3% |

按 Bradley-Terry / logit 闭合：`logit(0.723) − logit(0.593) = 0.585` → 隐含
`p({probe_k:3} 胜 {}) = logistic(0.585) = 64.2%`。
**而这与早先一次 90 局测量得出的"probe_k=3 无强度损失（46.7%）"直接冲突** →
说明那次小样本测量功效不足（在小 n 下 46.7/53.3 确实测不显著），
或存在未识别的情境差异 → 立刻补一个**直接的 300 局**测量裁决。

**用法（三行）**：
```python
logit  = lambda p: math.log(p/(1-p));  logistic = lambda x: 1/(1+math.exp(-x))
implied = logistic(logit(p_B_vs_A2) - logit(p_B_vs_A1))   # 隐含 p(A1 胜 A2)
```
**判读**：把 `implied` 与"直接测过的 A1 vs A2"（或与其直觉强度差）对比；
若差异明显（如 64% vs 47%），说明**至少有一个测量不可靠**，优先怀疑样本量小的那个。
**顺带的好处**：还能把零散实验拼成一张一致性的强度阶梯，比单点结论更稳。

**⚠️ 但它是"体检"不是"尺子"**（本项目实测）：该检验估算出 `probe_k=3` 应胜 `probe_k=0` 约 **64.2%**，
随后 300 局直接测量得到 **54.7%** —— **方向完全正确（靠它抓到了一条错误结论），量级被高估**。
原因：① 它把两次测量的噪声**逐一复合**（各 ±5.7pp SE）；② 自对弈强弱关系不严格满足
Bradley-Terry（存在非传递性）。
→ **用法定位：只用来"发现矛盾并触发直接测量"，绝不要用它给出的数字下结论。**
本项目由它触发的那次直接测量，推翻了一条已发布的"无强度损失"结论（n=90, p=0.37 → n=300, p=0.022）。

### 7.9.3 教科书级对照：**同一协议下，一个结论被复现、另一个被推翻**

本仓两个实验用**完全相同**的协议（9 路 · 150 playouts · 300 局 · 黑白对调 · 确认实验用各自的新 seed）：

| 实验 | 首次 | 确认实验 | 效应量 | 结论 |
|---|---|---|---|---|
| 推荐配置 vs 原始默认 | 72.3% | **70.7%** | **+44.6pp** | ✅ **复现 → 确认**（合并 600 局 71.5%，p<0.0001） |
| `pbias` vs 基线 | 54.0% | **49.3%** | +4pp | ❌ **未复现 → 判中性** |

**判读**：差别只在**效应量**。大效应即使 n=300 也稳定复现；小效应（±4pp）在任何样本量下都随 seed 飘忽。
→ 推论：**看到"显著但效应量小"的结果，第一反应应是设计确认实验，而不是写结论。**
→ 反过来，若某改进在 n=300 上给出 >10pp 的稳定胜率差，那才是值得投入移植/宣传的强度提升。
→ 这两个结果都是"负结果或确认结果"要同时留下的理由：**它们一起定义了"这套仪器能测出多大的效应"**。

## 7.10 临时探针的正确用法（不污染热路径、不进提交）

要给引擎加计数器/观测时：**复制**引擎源码到临时文件（如 `JsWeiqi/_lgr_probe_tmp.mjs`），
在副本里加计数器，用副本跑探针，**探针跑完立即删除**。理由：
- 计数器写在热路径上（每 playout 每手一次）会给**实验组**引入不对称开销，污染 A/B；
- 副本文件若忘记删，会被 `git add -A` 一起提交（本项目已踩过一次）。
探针输出要能回答："机制被调用了多少次 / 命中率 / 实际采用率 / 步数变化"。

## 7.11 「参数无效」是最强信号：先证明机制在生效，再谈效果

**症状**：调某个参数（如 `rave_k`）对结果**逐位无影响** → 不要当成"该参数不敏感"，**先怀疑机制是死的**。

本项目实例（RAVE 的 no-op，参考实现与全部 6 个移植共同继承）：
- AMAF 集合只在**树下降阶段**记录着法，**playout 里的随机着法从未记入**；
- 于是根节点每个子节点 `amafN ≡ N`、`amafW/amafN ≡ W/N` → `val=(1−β)q+β·qa ≡ q`，**β 被完全消掉**；
- 实测确认：`N===amafN` 且 `q===qa`，两个 seed 各 4/4 全部恒等。
- → RAVE（默认 `rave: true`）一直是**无效负载**，`rave_k` 是**死参数**。

**可复用的三条**：
1. **怀疑顺序**：参数无效 → 查"机制是否真的被调用/命中"（计数器 / 指纹），**再**查"参数是否传进去了"
   （profile 覆盖、字符串键形态、单位），最后才怀疑"效应太小测不出"。
2. **用胜率级指纹做灵敏度检测**，别只用最终着法：同 (局面, playouts, seed, profile) 下
   `[vertex, visits, winrate]` 三元组只要有一项不同就说明 playout/搜索路径变了；
   三元组**逐位相同** ⇒ 该参数没有影响任何一次模拟（比"着法相同"强得多，因为最终着法经 argmax 会掩盖差异）。
3. **能给出代数证明就别只给观测**：`amafN≡N` 这类恒等式一旦证出，就不必再靠"多跑几局看不出差异"来论证，
   也直接给出了修复方向与验证判据（修复后 `amafN>N` 的子节点数应从 0 变成几十个）。

**顺带**：文档里写成"结构性要求"的东西（如 `PORTING.md` 把 RAVE 列为必须等价的结构），
也要**验证它是否真的在起作用**——否则 N 个语言会一起继承同一个死代码。

## 8. 环境陷阱（本机实测，跨会话复用）


- **`spawnSync` 会被沙箱拦成 `EBUSY`**（连 `node --version` 都失败）→ 自动化脚本一律用**异步 `spawn`**。
- **Bash 工具可能因 PortableGit 被删/残缺而整体失效**（报 `Top-level not found: ...\PortableGit\versions\<v>\bin`）；
  兜底：用 PowerShell 跑命令，或写 `.mjs` 用 `child_process` 直接调绝对路径二进制。
- **PowerShell 工具经常不回显输出** → 一律「写文件 → 用 Read 读回」；中文输出会混编码，关键结果读文件。
- **GOROOT 全局变量会覆盖新装 Go 的自动探测** → 构建脚本里显式设 `GOROOT`。
- 受管运行时目录（`.workbuddy/binaries/**`）**可能被清理或残缺**（标准库缺失、版本目录消失）
  → 动手前现场验证，别信旧路径。

### 修复配方（2026-10-09 实测通过）

**诊断顺序：先分清「指针错」还是「内容坏」** —— 看环境变量/PATH 指向什么、那东西是否存在。

- **Bash 工具失效**（`Top-level not found: ...\PortableGit\versions\<v>\bin`）：
  `CODEBUDDY_CODE_GIT_BASH_PATH` 指向只剩存根的版本目录，且 PATH 里另一版本目录已被删。
  **修法**：把这些版本目录建成**指向完整 Git 安装的 junction**（`New-Item -ItemType Junction`，免管理员），
  并把用户级环境变量改为真实 `bin\bash.exe`。**junction 让"指向旧路径的既有配置"当场复活**，
  不必改 PATH，也不必等进程重启。
- **Python 找不到标准库**（`Failed to import encodings`）：多为**缺 `Lib/` 的残缺安装**（不是 PATH 问题）。
  修法：官方 embeddable 包重装。⚠️ **`tar` 解不了 zip**（Git-for-Windows 的 tar 是 GNU tar）→ 用
  PowerShell `Expand-Archive`；需要 pip 时另用完整 CPython 建 venv。
- **调 git/二进制被 PowerShell 拦**（"Spawning a non-PowerShell shell..."）→ **转一层 node**：
  `node script.mjs` 内 `spawn(绝对路径, args)`（异步）即可，且绕开 `spawnSync` 的 `EBUSY`。
- **Node 主模块判定有两坑**（本项目踩全）：
  ① Windows 上 `file://` 手工拼接与 `import.meta.url` 三斜杠不一致 → 判定恒假、CLI **静默不执行**
     → 用 `pathToFileURL(process.argv[1]).href`；
  ② 但 `process.argv[1]` 在 `node -e` / `--input-type=module` 下是 `undefined` → `pathToFileURL(undefined)` 抛错。
     **被当作库 import 的模块尤其危险** → 守卫写成 `if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href)`。
- **`/tmp` 在 Git Bash 与 node 下解析不同**（node 可能解析成 `<当前盘>:\tmp`）→ 跨工具传路径一律用
  **显式 Windows 绝对路径**（`C:/Users/.../x.jsonl`）。
- **shell heredoc 里写 JS 会踩反引号/`${}`**（被 shell 先展开）→ 改动含模板字符串的代码，
  用 Write 写脚本文件再执行，或改用编辑工具，不要用 `node - <<EOF`。

## 9. 纪律

- 改规则/AI 后**必跑**：各语言自测 → harness ALL GREEN → 循环赛冒烟。
- 子代理报告的"规范与实现不一致"一律**回写规范**（本项目一次性修了 rave_k、数值格式、reason 语义等）。
