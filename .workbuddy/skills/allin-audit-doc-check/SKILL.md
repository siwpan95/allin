# allin 审计/报告类文档错漏自动检查

> **定位**：本仓治理体系对**代码**有 20 道门禁 + 30 条 repocheck 规则，对**文档**有 D1–D17 索引契约。
> 但**结论型文档**（审计报告 / 复评报告 / 走查清单）此前零机检覆盖 —— 而它们恰恰是
> 「错了也没人知道」的高危文档：引用了已删除的代码行、把疑点当结论、数字口径彼此矛盾、
> 结论没有任何来源支撑，全都能静默存活。本 skill 补这一段。
>
> **与既有实现的边界**：本 skill **不重造** docs_index（D1–D17 管的是「文件在不在、
> 登记没登记」）、不重造 check_readme_refs（管的是 README 引用路径与包版本）、
> 不重造 repocheck（管的是代码仓卫生）。本 skill 只管**结论型文档的内容自洽性**。
> 两者互补，不重叠。

## 1. 执行器

**内核脚本**：`tools/gate/audit_doc_check.py`（零三方依赖，仅标准库）

```bash
# 检查单个/多个文档
python tools/gate/audit_doc_check.py "docs/记录/审计/深度审计报告_2026-11-10.md"

# 列出受管辖的全部文档
python tools/gate/audit_doc_check.py --list-all

# 自检（验证每条判据真的会红 —— 改判据后必跑）
python tools/gate/audit_doc_check.py --selfcheck

# 机器可读输出（供 agent / CI 消费）
python tools/gate/audit_doc_check.py --json <文档.md>

# 只输出结论，不展开历史基线明细
python tools/gate/audit_doc_check.py --quiet <文档.md>
```

**退出码**：`0` 无**新增**违例 ｜ `1` 有新增违例 ｜ `2` 用法错 ｜ `3` 环境错。
文本输出前缀：`OK` 无违例 ｜ `BASE` 历史基线欠账（不计门禁）｜ `FAIL` 新增违例（判红）。
`--json` 输出含 `violations`（新增数）、`baseline`（基线数）、`findings[].status`（`new` / `baseline`）。

**经 allin CLI 驱动**（见 §3，本仓已接线）：

```bash
allin docs audit-check                          # 检查 docs/记录/审计/ 下全部文档
allin docs audit-check <文档.md> [<文档2.md>...]  # 检查指定文档
allin docs audit-check --json                   # 机器可读输出
allin docs audit-check --quiet                  # 只输出结论
```

自检（`--selfcheck` / `--list-all`）当前只在内核脚本上开放，CLI 只接检查动作。

## 2. 判据清单（E1–E7）

| 编号 | 判据 | 抓什么 | 等级 |
| --- | --- | --- | --- |
| **E1** | 证据锚点核对 | 报告里的 `file.py:123` —— 文件是否存在？行号是否越界（代码改动后报告未同步）？ | 阻断 |
| **E2** | 必备章节完整 | 缺「审计范围 / 问题清单 / 来源 / 疑点 / 处置建议」任一必备章节 | 阻断 |
| **E3** | 严重度排序 | 问题清单段内未按 严重→高→中→低 升序（**按章节分段判定**，跨段不比） | 阻断 |
| **E4** | 无源结论检测 | 结论性表述（「导致 / 构成 / 等同于 / 证实存在…」）既无 `file:line` 锚点也无来源标记 ⇒ 疑似无源推测 | 阻断 |
| **E5** | 来源可核查 | 引用来源但未给 URL（现由 E4 的来源标记 + 人工评审兜底） | 提示 |
| **E6** | 数量口径一致 | 同一事实在文中有互相矛盾的数字（如「19 条门禁」与「20 道门禁」并存） | 阻断 |
| **E7** | 疑点未混入结论 | 「已确认问题清单」段内出现「疑似 / 需确认 / 待验证」等措辞 | 阻断 |

### 判据的设计取舍（为什么这么判，不为什么那么判）

- **E1 支持简称锚点**：报告常写 `registry.js:62` 而非全路径。检查器按「文件名在仓内唯一」反查定位；
  **同名候选多个时不猜**，报「歧义」交人工 —— 猜错比不猜更危险。带目录前缀的简称
  （如 `交接/2026-11.md`）走后缀唯一匹配；候选先按 `realpath` 去重，否则
  `docs/records → docs/记录` 这类 symlink 别名会把唯一文件算成两个、制造假歧义。
- **E1 跳过代码块**：代码块里的 `// index.js:1068` 是**代码摘录的出处标注**，不是报告自身的证据引用。
- **E1 对跨仓盘点文档收窄**：标题含「盘点 / 清单 / 修复计划」的卷，盘点的就是**其他仓库**的文件，
  仓内必然找不到 ⇒ 这类锚点整体跳过（不再逐个维护外部仓名白名单，会随仓库演进腐烂）；
  **仓内确实存在的锚点仍逐条核行号**，不放过真错漏。
- **E2 按「语义等价的章节标题」匹配**：历史审计卷的章节叫「评估范围与方法」「发现与定级」
  「知识库检索结果与边界」「审核范围与方法」「本轮真实复测证据索引」「放行口径」，
  与判据字面「审计范围 / 问题清单 / 来源 / 疑点 / 处置建议」并非同一套命名。
  别名表只收**等价章节标题**、不收泛词；自检有「标题乱写仍报 E2」的反向用例兜底。
- **E4 跳过结构化元数据字段行**：`- 边界：` / `- 置信度：` / `- 构成：` 这类行是条目元数据
  （「构成」在这里是字段名，不是「构成漏洞」；「不构成现时漏洞」是否定式边界声明），
  证据在同一条目的「位置 / 影响 / 依据」行。按行判 E4 会把它们误判成无源推测。
  豁免名单**不含「影响 / 审计意见」**，结论行照判；自检有「结论行仍必报 E4」的
  反向用例证明判据未被削弱。
- **E3 按章节分段**：处置建议段的 `P0` 与问题清单段的「严重」不是同一套编号体系，跨段比较会误报。
- **E4/E7 对「已显式降级为疑点」豁免**：正文写了「列为待验证疑点 V-21」= 作者**主动**标注了不确定性，
  属正确处理，不该重复报警。
- **E6 排除泛词**：「条目 / 项目文件」这类词在不同语境下指代不同对象，比对它们只产假阳性。

## 3. CLI 接线

`allin_cli.py` 的 `docs` 域新增 `audit-check` 动作，`kernel/services/docs_service.py` 提供实现：

```python
# kernel/services/docs_service.py —— audit_check(docs, as_json, quiet)
# 1. 目标：未指定文档时，调内核 --list-all 取 docs/记录/审计/ 下全部 *.md
# 2. 透传 --json / --quiet 给 tools/gate/audit_doc_check.py 的 main()
# 3. 退出码原样返回，违规明细打印到 stderr，供 CI 消费
```

实现要点：
- **零三方依赖**（与本仓其余工具一致），只用标准库；
- **透传退出码**：`0/1/2/3` 原样返回，让 CI 能区分「无新增违例 / 有新增违例 / 用法错 / 环境错」；
- **不吞异常**：脚本内部异常时返回 3（环境错），**不得**映射成 0（那正是本报告 S-3 / H-4 批评的假绿模式）；
- **基线在内核侧判定**：CLI 只透传参数，不自行决定哪些违例算基线，避免两层口径漂移。

| 场景 | 动作 |
| --- | --- |
| 写完审计报告 / 复评报告 | 跑 `allin docs audit-check <文档.md>`，**改到零违例再提交** |

| 改判据本身 | 先跑 `--selfcheck` 验证每条判据仍会红 |

## 5. 报告写作纪律（配合本 skill）

本 skill 只能核「机器能确定」的事。以下**必须人工把关**，检查器不覆盖：

1. **证据与结论对得上**：E1 只核「文件和行号还在」，**不核「这一行真的支撑这个结论」**。
   评审时仍须逐条读代码原文。
2. **来源确实支撑结论**：E4 只核「有没有来源标记」，不核「来源是否真的支持这个说法」。
3. **严重度定级是否合理**：E3 只核「是否排序」，不核「定级对不对」。
4. **疑点是否真的只是疑点**：E7 只核措辞，不核「这个疑点该不该升级为结论」。
5. **禁止 padding 凑数**：门禁不得用「写了就算过」的方式刷绿 —— 检查器报红时**要么改文档，要么改代码**，
   不许改判据来消音（改判据须同步更新本 SKILL.md 的判据表）。

## 6. 历史欠账基线（baseline）—— 当前为空

**缘起**：检查器上线（2026-11-10）时，`docs/记录/审计/` 下已有 4 份历史报告不满足新判据，
合计 17 条。这些欠账既不能抹掉，也不能让它们把 `allin docs audit-check` 顶成常红 —— 与
S-3 批评的「规则崩溃假绿」相反方向的「常红噪声」一样有害。故先按配额登记，再逐条清理。

**清理结果（2026-11-10 20:35）**：17 条已全部清零，`quota` 现为 `{}`。

| 性质 | 条数 | 处置 |
| --- | --- | --- |
| E2 章节命名等价写法未被识别（判据假阳性） | 9 | 补语义等价别名；章节本来就存在，不是放宽判据 |
| E4 元数据字段行 / 否定式关键词误判（判据假阳性） | 3 | 精准豁免字段行，补 2 条反向自检 |
| E4 审计意见缺行内依据标注（文档真欠账） | 1 | 在 `深度审核报告_2026-08-27.md` 补真实依据标注，**不改结论文字** |
| E1 简称锚点歧义（文档真错） | 1 | `复评第4轮最终汇编` 补全为 `website/src/public/js/governance.js` |
| E2 确实缺章节（文档真欠账） | 3 | 两份历史卷末尾**追加补记**：内容全部取自既有段落，不新增结论、不改写历史记录 |

⇒ 全量 **29 份文档 / 新增违例 0 / 基线 0 / exit 0**；自检从 11/11 扩到 **14/14 PASS**
（新增：等价别名不误报 E2、元数据行不误报 E4、结论行仍必报 E4）。

**机制保留**：`tools/gate/audit_doc_baseline.json` 仍作为载体（当前 `quota: {}`）：

```json
{ "quota": { "docs/记录/审计/整改复评报告_2026-11-08.md": { "E2": 5 } } }
```

- 实际违例数 ≤ 配额 ⇒ 输出 `BASE`，不计门禁；
- **超出配额的部分**、**未登记文档的任何违例** ⇒ 输出 `FAIL`，退出码 1；
- 按「判据 + 数量」而非文本指纹：行号漂移、措辞微调不会让基线失效，但多出来的同类
  违例或新判据违例都会判红；
- 基线文件缺失 / 损坏 ⇒ 按**无基线从严**判定并打印警告，绝不静默放行。

**纪律**：

1. 只允许登记上线日之前**已存在**的历史欠账，禁止用它给新写的违例洗白。
2. 修复历史欠账后**下调或删除**对应配额，不许留空额当「免死金牌」。
3. 新写的审计报告必须**零违例**提交（本次 `深度审计报告_2026-11-10.md` 即零违例）。
4. 改判据导致基线数变化时，先跑 `--selfcheck`，再核对配额，不要直接调大数字。
5. **清理历史文档只追加补记，不改写历史结论**；补记内容须全部取自该文档既有段落。

**实测**（2026-11-10）：全量 29 份文档 → 新增违例 0 / 历史基线 0 / 退出码 0；
注入一份含 5 条违例的临时文档 → 新增违例 5 / 退出码 1。
