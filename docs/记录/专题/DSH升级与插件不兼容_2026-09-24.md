> **起因**：用户提供 [阿里云文章 1761125](https://developer.aliyun.com/article/1761125)，要求联网调研「DeepSeek Harness 更新后 DSH plugin 不兼容」。

> **本文只记「升级风险」这一件事**；机器事实见 [`新机配置汇总_2026-09-24.md`](../快照/新机配置汇总_2026-09-24.md)。

## 一、结论先行

1. **用户的担心是对的，而且本工作区已经踩过**：旧机 `DEPLOY.md` 记着一次**同日（2026-09-24）的上游版本漂移故障**，含四类不兼容与四步修复。
2. **本机（新机）风险显著低于旧机**：本机是**从源码跑**（`bin.ts` + tsx），不走 npx 包；**未装任何第三方插件**（profile 零依赖）。
3. **但有一个决定性风险，且要分清两件事**（2026-09-24 实物比对后订正）：
   - **官方四个 preset（standard / ptc / minimal / cordis）在新版不会丢** —— 它们由 bundle 提供，
     新版仍在 `packages/bundle/web-app/presets/` 以 `.patch.yml` 形式随包交付（实测 zip 四个都在）；
     改的只是**交付形态**（目录 → 声明），**不是把 preset 取消**。所以"官方模式不会失效"这个判断**成立**。
   - ⚠ **但我们的「治理模式」不是官方 preset** —— 它是**叠加**在出厂 `cordis` preset 的 persona 上的
     一段内联文本（`GOVERNANCE:BEGIN/END`）。新版把 `packages/preset/agent-presets/` 整个移除
     （**zip 条目数 = 0**），而**治理 persona 只存在于 `C:\deepseek-harness-master` 这一个位置、没有第二份**
     （见 §4.2.6）。⇒ **升级 = 那段文本随目录一起消失**，官方四模式照旧，治理内容没了。
4. **本机源码 checkout 无法正常升级**：无 `origin` remote、工作树 **73 项改动** → 无干净升级路径。

**建议：在解决第 3、4 条之前，不要升级 DSH。**

## 二、旧机第一手档案：上游版本漂移的四类不兼容

> 出处：`/notpython/deepseek-harness-master/DEPLOY.md` §「2026-09-24 上游版本漂移故障（四步修复，均已固化并实测）」
> 触发条件：**上游重发了 rc.6/rc.8 同版本号的 tarball**（同号不同物）。

| # | 不兼容 | 现象 | 修复 |
| --- | --- | --- | --- |
| 1 | **peer 依赖激增** | 50+ 插件新增 peer（17 个 `@deepseek-ai/*` + `@cfworker/json-schema` + react 系）；`--legacy-peer-deps` 不装它们 → 启动报 **`Cannot find package`** | 把 peer 以**精确版本**写入安装目录 `package.json`（`gen_start_bat.py` 的 `PKG_JSON`，caret-free 防 cmd 转义） |
| 2 | **`cordis-plugin-loader` 的 `internal.import` 挂起** | 动态创建的插件条目经 `ctx.loader.internal.import(...)` **永不解析**（fiber 停在 state 1、**无报错**） | 补丁改为普通 ESM import（`dsh-local-compat: internal.import stalls`） |
| 3 | **profile-boot 竞态** | 私有 HMR 条目 `loader.create()` 在激活完成前返回 → `watchUserPatches` 查 `ctx.get("hmr")` 为空 → **崩溃** | 补丁加**有界等待**（`dsh-local-compat: hmr wait`） |
| 4 | **hmr API 漂移** | 新 hmr **不再暴露 `registerConfig`** → `watchUserPatches` 抛 **TypeError** | 补丁降级为**静态 patch 层**并告警：patch 热更不可用，但启动正常 |

**同源记录（2026-08-27，R8）**：三层版本不一致 —— 源码快照 `0.1.0-rc.5` / npx 实际运行 `rc.6` / GitHub master `0.1.1-rc.2`。原文纪律：

> **任何一次 dsh 升级（含 rc.7/0.1.x）都必须先重放补丁并核对 SHAPE**，失配时人工重推。

**这条纪律是本次调研最有价值的可复用资产。**

### 4.1 与本工作区治理模式的直接冲突（**最要紧**）

**我们的治理模式挂在 preset 上**：`/deepseek-harness-master/packages/preset/agent-presets/presets/cordis/agent.cordis.yml` 的 persona 内联了治理段（`GOVERNANCE:BEGIN/END`）。

而新版机制是**声明式**（`@deepseek-ai/dsh-agent-preset` + `agent-preset-registry`，**注册表不扫目录**）。
⇒ **升级到新版会打断治理模式**：目录式 preset 不再被读取，那个文件里的一切（含治理 persona）失效。

**这也是《治理模式换机可迁移化方案》§2.1 的机制层结论**，此前我在该文 §十一 标注「对本机不成立（本机是目录式）」—— **那个标注只描述"当前版本"，不否定"升级后会成立"**。本次把这层关系补全。

### 4.2 一个官方确认的设计缺陷，正是我们踩过的坑

官方讨论 **#5873**：「**Renamed agent preset leaves a stale user default that breaks new-session creation**」（『被改名的 agent preset 留下陈旧的用户默认值，导致新建会话失败』）。

这正是本会话实测到的现象链：

```
settings.yaml 写入 default: allin（不校验名单健康度）
  → 名单里没有/装不上该 id
  → 新建会话失败（或静默回落到别的 preset）
```

⇒ **本会话的排查不是"操作失误"，而是撞上了一个已被上游记录的设计缺口。** 这条应作为**升级评估的输入**（新版是否修了它，需重测）。

### 4.2.3 新版 preset 的落地面与格式（实物）

新版把 preset 从「一个目录」改成「**一行声明 + 内联子插件列表**」，落地面在 bundle 里：

```
packages/bundle/web-app/presets/cordis.patch.yml
packages/bundle/web-app/presets/minimal.patch.yml
packages/bundle/web-app/presets/ptc.patch.yml
packages/bundle/web-app/presets/standard.patch.yml
```

格式（摘自 `cordis.patch.yml` 原文）：

```yaml
- insert:
    - id: preset-cordis
      name: '@deepseek-ai/dsh-agent-preset'
      config:
        id: cordis
        order: 4
        plugins:
          - id: persona
            name: '@deepseek-ai/dsh-persona'
            config:
              suffix: Your working directory is {{cwd}}.
              prefix: >-
                You are a coding agent powered by the {{model}} model.
          - id: agent-instructions
            name: '@deepseek-ai/dsh-agent-instructions'
            config:
              maxBytes: 65536
          # …（其余行与旧版同名同序）
```

### 4.2.4 新版 README 的三句关键原文

摘自 zip 内 `packages/preset/agent-preset-registry/README.zh.md`：

> 1. 「定义使用普通插件行；**注册表不扫描目录，也不接受 preset 路径**。」
> 2. 「新建 preset 或覆盖内置 preset 都是 **bundle 补丁**：插入一行 `@deepseek-ai/dsh-agent-preset`，
>    或**按该行 id 写覆盖补丁**，再用 `plugin_manager` 安装到 profile；创造模式在对话中编写这类 bundle。」
> 3. 「Edits saved from the Web editor **override this row's `config.plugins` by id from the profile patch**。」

**第 2、3 句给出了治理模式在新版的干净出路**：不必维护 preset 目录 ——
改为**往 profile 的 `cordis.patch.yml` 写一行按 id 的覆盖补丁**，把治理 persona 作为 `persona` 行 config 覆盖进去。
这正是《治理模式换机可迁移化方案》§4.2 的设计，**现在有了可照抄的实物格式**。

⇒ **推论（对我们的旧做法是坏消息）**：既然「注册表不扫描目录」，
那么旧机制里「**往 `$DSH_HOME/.agent-presets/` 丢一个目录就能多出一个预设**」这条路
在新版**彻底失效**——不是弃用告警，是没有代码去读它。
所以治理模式**不能再靠"放目录"过活**，必须落成 bundle 补丁行。

### 4.2.5 一处对 §三 的自我修正

§三 曾引外部资料说「缺 **`engines.dsh`** 闸门」。**实测 zip：含 `"dsh": "<range>"` 的 package.json 仅 2 个**
（根 `package.json` 与 `apps/cli/package.json`），**不是**每个插件的版本闸门。
⇒ **那条外部说法对本机不适用**，据此判断升级风险时会失真。

### 4.2.6 治理 persona 的唯一位置（**升级前必读**）

| 位置 | 该文件 | 含治理段 |
| --- | --- | --- |
| **`C:\deepseek-harness-master`**（**运行中的部署**，以 `node --import tsx/esm apps/cli/src/bin.ts` 跑） | 19,609 B | ✅ **是** |
| `/notpython/deepseek-harness-master`（旧机遗留副本，无 `.git`） | 14,010 B | ❌ 否 |

⇒ **治理 persona 只存在于"正在运行的那个部署"里，没有第二份。**

补充实测（完整解压件复查）：
- 新版 zip 内 `agent-presets/` 目录 **0 个残留**（不是空目录，是不存在）；
- 在新版 zip 全树搜 `GOVERNANCE:BEGIN` / `siwpan` / `DESKTOP-8RSV60V` / `铁律` → **命中 0 处**。

⇒ 两条合并的结论：**升级/覆盖安装会连带删掉承载治理段的那个目录，且新版里没有任何替代副本。**
失联风险不在"版本变了跑不起来"，而在"**唯一那份 persona 被删且无处可寻**"。
（这也正是本机治理模式当前状态的写照：它只活在 `C:\deepseek-harness-master`。）


**残迹与出路（2026-09-24 实查）**：

| 项 | 实测 | 含义 |
| --- | --- | --- |
| `/Users/psw/.dsh/.agent-presets/` | **存在但为空**（0 条目） | 旧机那套「丢目录」做法（`会话交接_2026-08-27.md` L47/L50 的 `code-nocompact`）在本机**已弃用**；治理 persona 因此只能来自部署内的那份，**没有第二副本** |
| `/Users/psw/.dsh/profiles/web/cordis.patch.yml` | **已存在**（217 B，当前为 `[]`） | §4.2.4 给出的新版出路**落点就是本机现成机制**——不是要新建东西，是要往这个空补丁里写行 |
| `/Users/psw/.dsh/profiles/web/cordis.yml` | 223 B，注释明写「**Edit `cordis.patch.yml`, not this file**」 | profile 根只是空条目表，真正的组成层是补丁 |
| `profiles\web\package.json` | `dsh.profile.bundles = [@deepseek-ai/dsh-base, @deepseek-ai/dsh-web-app]` | 两个 bundle 层之上叠 `cordis.patch.yml`——与 §4.2.4 的「按 id 覆盖」语义完全一致 |

⇒ **这条把「治理模式可迁移化」从"设计"推进到"有现成落点"**：出路不必等升级，
现在就能在 `cordis.patch.yml` 里写一行覆盖，把治理 persona 从「内联在出厂 preset 里」搬到「profile 自己的补丁层」。
**搬到补丁层 = 出厂 preset 被升级覆盖也不会再连带删掉治理段**（这是移除 §五那两条"高"风险的唯一根治手段）。

## 五之二、已完成的缓解措施：治理模式已可复原（2026-09-24）

**做了什么**：把治理 persona 从"内联在随包 preset 里"变成"**一个独立、可重装、已入 git 的 preset**"。

| 项 | 值 |

**为什么不是"往 `cordis.patch.yml` 写一行"**（原计划）：0.1.7-rc.1 的声明式注册表才支持按 id 覆盖
`config.plugins`；**本机 0.1.6-alpha.2 无此语义**（本版 README 原文：「本层也没有表达『standard 加一处改动』的 patch 语义」），

届时本目录的组装文本仍可直接搬用。

**仍未做**：把 `agent-presets.default` 从 `cordis` 改成 `allin`（改配置即生效，但只影响之后新建的会话）；

## 六、若将来要升级：检查清单（照抄执行，勿凭记忆）

> 依据：旧机 DEPLOY.md 的「任何一次升级都必须先重放补丁并核对 SHAPE」+ handbook 的「Ship what the manifest promises」12 条。

**升级前**
1. **备份（第一步，不可省）**：`$DSH_HOME`（settings/sessions/storages/profiles）**+ 治理 persona 段**。

## 八、上游关系纪律（官方维护版仅作参考，PR 合并前须确认无冲突）

> 依据：本工作区已将 DSH 治理 overlay 独立建仓 `siwpan/deepseek-harness`（gitee，remote `gitde`），
> 与上游 `github.com/deepseek-ai/deepseek-harness` 解耦；详见 `preset/allin/安装说明.md`。

1. **官方 GitHub / 维护版 DeepSeek harness 仅作「参考对象」**，不是我们的部署源。
   它的角色限于：核对 preset / 插件 SHAPE 漂移、定位破坏性变更、取声明式格式样本。
   **不得**直接把它 `fetch`/`merge` 进我们的工作部署。
2. **上游更新若要合入，必须经 PR 合并，且合并前确认「不会产生冲突」**：
   - 冲突判定对象 = 我们的 overlay 与上游改动的**交集文件 / 同名 capability 行 / 同一 `{{variable}}` / 同一 YAML schema 字段**；
   - 用 `preset/allin/verify-mount.ps1` 的漂移层（比对 shipped `cordis.patch.yml`）作为机械判据之一；
   - 任何「上游重发同版本号不同物」「renamed preset」「移除/新增 plugin id」都算潜在冲突，须先在隔离副本上重放验证——能挂载、治理段不丢——才允许合入。
3. **合入方式**：上游可作为参考分支 / submodule 引入均可，但**主干永远是我们的 gitee `siwpan/deepseek-harness`**；
   PR 合并到主干前，须 `dsh --profile web --dump-config` + `verify-mount.ps1` 双绿。
4. **为什么这样定**：上游破坏性变更（0.1.7 已实证——移除 `agent-presets`、改声明式）只动我们的 **pin**，不动源；
   我们永远有「回退到上一可用 pin + 重放 allin 补丁」的退路，不会因上游一次 rebase 失联治理。
