## 一、死因回顾（README 事实）

helminth 自述是「统一爬虫框架 v1.0」= webcopier + font_downloader2 + sfx **三工具代码级融合**。
crawl_hub README 记录的失败事实：融合框架被冷落，三原工具一个没退役、反而更活跃，等于 4 份副本。

**讽刺的是**：helminth 的架构本身已经半只脚踏进插件化——core/（身份轮换/限速/反爬/下载器，共享运行时）+ engines/（BaseEngine 抽象接口 name/discover/download/cancel + 3 个引擎）+ sources/（JSON 配置驱动）。它失败的**不是技术**，而是"融合"这层关系：吞并了三个仍在独立演进的工具，自己的副本必然漂移。

## 二、复活设计：从"融合框架"到"插件注册表"（原型已落地）

三个动作（已交付到 helminth 目录内，不污染 crawl_hub）：

| 交付物 | 内容 | 验证 |
|---|---|---|
| `PLUGIN_SPEC.md` | crawler-plugin 插件规范 v1：每个爬虫 = 一个目录 + manifest.json（name/version/entry/interface/port/config）；五条纪律（独立更新/子进程隔离/统一端口/任务日志/共享库引用不融合） | — |
| `crawler_registry.py` | 注册表扫描/校验原型（纯标准库）：扫描 manifest、必填字段校验、**端口登记检查**（port 必须先在端口分配表登记）、--check/--json 审计 | 实测 exit 0 ✅ |
| `example-sfx/` | 示例插件：helminth 的 sfx 引擎包装为独立插件（manifest + 入口），演示"包装不重写" | registry --check 全过 ✅ |

**与 crawl_hub 的关系（合流方案）**：crawl_hub 已是进程级 hub（聚合不融合教训的产物）——升级路径是：crawlers.json → 扫描插件目录 manifest.json（注册表化）；helminth core/ → 提炼为 `crawler-kit` 共享库（带版本，插件声明依赖）；helminth engines/ 三个引擎 → 三个独立插件目录（各自版本、各自更新）。**hub 依旧子进程隔离、不 import 插件逻辑**——插件化不推翻 helminth 教训，而是把"独立更新"制度化。

## 三、决策建议

1. **推荐：分三步渐进复活**（不一次性吞回）：
   - 步骤 1：把 PLUGIN_SPEC + crawler_registry 原型移入 crawl_hub（注册表升级），helminth 保持隔离区仅作参考；
   - 步骤 2：三个引擎以 example-sfx 为模板各建插件目录（先 sfx，再 font，web 视 webcopier 意愿）；
   - 步骤 3：crawl_hub 的 crawlers.json 支持 `"registry": true` 混用模式（既有独立工具 + 新插件目录共存）。
2. 不推荐：把 helminth 整体解禁回活跃区——它的价值已被提炼（core 库 + 规范），残留副本保持隔离。
3. 待拍板：crawler-kit 共享库是否成立（涉及"复制优于共享 vs 库引用"的取舍；按纪律 5 用"版本化依赖引用"，只在爬虫插件间共享反爬运行时）。

## 四、统一端口落实

- 插件 port 字段空 = 无服务（纯 CLI/GUI 爬虫）；有服务必须在端口分配表登记（registry 已强制校验，未来表同步为文件读取而非内置集合）。
