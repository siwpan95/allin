## 1. 实体性声明（本卷最重要的一节）

1. **它不是机器。** 无 `hostname`、无盘位、无硬件、无运行时清单 —— 任何要求**以本卷为主体自测**的判据
   只能答『不适用』，不能被写成「本卷已自测」。
   ⚠ **但它的残留可以被别人测**：残余盘位、运行时、目录形态都实存于承载机 `@DESKTOP-8RSV60V`，
   由该机现场核验并记为「承载机对原型机残留的观测」，见 §5.1。两者不可混为一谈：
   **自测**（主体是原型机）不成立；**他测**（主体是承载机，客体是残留）成立且应做。
2. **它不是第四台机。** 机器清单里它排在**三台真机之后**、标注 `kind: archive`；
   任何「三台机」的表述**不因本卷存在而改口**。
3. **它不参与实机判据。** `g20-facts` 的 `self-anchor` / `self-ownership`、`verify_facts.py` 的本机过滤、
   `machine_content_audit.py` 的「含机器标识却不在该机事实源」——本卷一律**不作为判据对象**，
   也**不作为豁免依据**。
4. **它的存在理由是记账完整，不是记账方便。** 2026-09 与 2026-10-29 之前的活是真干过的，
   只是当时没有「哪台机干的」这个字段；把它们摊给三台真机的任何一台，都是**替该机认领它没做的活**。

## 2. 承接边界（这一条会做成判据）

| 边界 | 规则 |
| --- | --- |
| **只承载** | `< 2026-10-30` 的提交与交接卷章节（2026-09 全月、2026-10-01 ~ 10-29） |
| **不得承接** | 2026-10-30 及之后的一切工作 —— 那时分机事实源已建立，事实有机器归属 |
| **判据形态** | 月账条目日期一律 `< 2026-10-30`；出现 `>= 2026-10-30` 的条目即为越界 |
| **反向约束** | 三台真机的月账**不得**收录 `< 2026-10-30` 的工作 —— 那段时期它们还不是「记录主体」 |

理由（一句）：**分界不是日期偏好，而是事实源的结构变更日**。2026-10-30 之前只有单一
`本机事实.md`，「本机」指的就是「干活的那台」，没有机器维度可归；当日按机器拆成
「本索引 + 每机一件」之后，机器归属才成为**可判定**的事实。

## 3. 与三台真机的关系

- **不是替代关系**：三台真机的分区文件记载的是**现值**（盘位、运行时、仓数），
  本卷记载的是**一段无机器维度的历史**。两者没有一行会重叠。
- **不是来源关系**：本卷内容来自交接卷与提交记录，**不来自任何一台机的自述** ——
  所以本卷条目写成「历史归档」，而三台真机的月账写成「本机自述」。
- **不是免责关系**：分机之后若有活被写进本卷，不能借「归档卷」免受追责。

## 4. 与 `DESKTOP-8RSV60V` 的关系：**承载 ≠ 产出**

⚠ 这一节是给「下一个读仓的人」写的防误读声明。

**事实**：原型机的外置盘（`F:` / `G:`）现接于 `@DESKTOP-8RSV60V`。因此在该机分区文件里能看到
「F:/G: 都在（**原型机的外置盘已接到本机**）」这类表述，也能在文件系统上摸到 `G:\repos`、
`G:\archive`、`G:\nodejs` 等痕迹。

**误读**（必须避免）：「`G:\repos` 在 8RSV60V 上 ⇒ 那些仓是 8RSV60V 建的 / 那些活是 8RSV60V 干的」。

**正确读法**：
- 盘在谁身上，只说明**谁在承载它**，不说明**谁产出了它**；
- 8RSV60V 的产出以**该机自己分区文件里的时点块与其月账**为准，不以盘上存量为准；
- 同理，**`G:` 盘上的仓数不是该机的业绩指标** —— 那是原型机时期的存量 + 后续同步的结果。

**盘符指纹（原型机时期的物证，可交叉验证）**：交接卷 2026-10 卷里多次出现本仓在 `G:` 上的作业
（`G:\archive` 归档统一 38→39）、以及用户指认的主 Python 在 `F:\Python\pythoncore-3.14-64`。
这两处盘符**同时属于原型机**，而 8RSV60V 分区文件记的盘位是 `C/D/E` 三卷 —— ⇒
**盘符不能用来判「谁干的」，只能用来判「盘现在在谁那儿」。**

### G. 索引本体与 git 历史的可还原性（2026-11-26 核查）

> 全哥给出线索：Gitee 提交历史 `page=38` 有 `40a38d8`「docs: G 盘目录索引 (仅索引, 体量超 gitee 限制)」（2026-08-13）。
> 据此核查本地 git 历史，结论如下。

**演进链（提交记录仍在，可逐条 `git show`）**：

| 提交 | 日期 | 内容 | 状态 |
| --- | --- | --- | --- |
| `40a38d8` | 2026-08-13 | 「docs: G 盘目录索引 (仅索引, 体量超 gitee 限制)」——**实查只新增 `.gitignore` 15 行，索引本体未入库**（当时已超 Gitee 单文件限制） | 提交信息与内容不符，史实如实记录 |
| `267751d` / `c40c5b4` / `b4539bc` / `1874ca6` | 2026-08 | 多轮「重新生成目录索引」（全盘快照形态） | 索引本体曾入库 |
| `ccdbda1` | 2026-09-25 | **形态换代**：全盘文件快照（48.53 MB / 555,220 行）→ 项目目录文档化索引（123 项目） | 现行实物的形态起点 |
| `7cfe256` | 2026-09-25 | `.gitignore` 明确「`目录索引.txt` 不入库（可重生成）」 | 索引本体停止入库 |
| `3a0dea7` | 2026-09-25 | 仓历史重写：**10.5 GB → 14 MB**（`filter-branch` 剔除 17 个历史版本累计 568 MB） | 索引本体从**全部历史**消失 |

**可还原性结论（实测，不是推测）**：
- `git rev-list --objects --all | grep 目录索引` 只命中 **1 个 blob**——即 2026-11-26 归档的这一份（`621e1bf`）。
- `git for-each-ref refs/original` 为空、无 `replace` ref、`.git/filter-repo/` 不存 ⇒ **历史重写无残留、不可回溯**。
- ⇒ **2026-09-28 那份实物是唯一存世的初代索引**；任何「从 git 历史还原早期索引」的做法都不成立。
  这也是它必须入库归档（而非继续 ignore）的根本理由：**所谓「可重生成」的两个前提——原型机整盘形态、生成器
  可跑——都已不成立；一旦实物再丢，这份索引就永久消失。**
