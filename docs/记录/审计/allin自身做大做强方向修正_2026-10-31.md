# 方向修正：把「组合做大做强」改成「allin 自身做大做强」

- **时点**：2026-10-31
- **触发**：全哥指出 REC-AU-20 跑偏了 —— **「组合」做不大做强，要做的是 allin 本身**。
- **性质**：战略方向修正。与 REC-AU-20 **不是并列的两篇**，本文**取代**它的战略结论；
  REC-AU-20 的**实测数据仍全部有效**（本文引用并复述其口径），但它的**「做什么」被替换**。
- **口径纪律**：沿用 REC-AU-20 的纪律 —— 每个数字标观测工具与时点；未经实测的一律标【推断】。
- **读法**：只想知道「接下来做什么」→ 直接看 §零 与 §六。要驳我 → 看 §三（论据）与 §五（反证）。

## 零、结论先行

**一句话**：REC-AU-20 诊断对了病（供给过剩、需求为零），**开错了药** —— 它要你去修 137 个仓的
门面、选一个旗舰、内容传播；而正确的动作是**把 allin 这个治理中枢本身做成一个可被外部采用的产品**。

| 维度 | REC-AU-20 的处置 | 本文（方向修正） |
| --- | --- | --- |
| **主体** | 137 个 repos 的组合 | **`G:\allin` 本身**（治理中枢） |
| **增长单位** | 某个仓的 star / 下载量 | **被外部采用并持续跑绿的治理实例数** |
| **repos 的角色** | 待做大做强的对象 | **allin 的压力测试场**（load test），不是产品 |
| **90 天主战场** | 修元数据 + 造旗舰 + 做内容 | **把 allin 变成可 `pip install` / 可 fork 复刻的治理工具** |
| **停手令** | 冻结新增仓 | **冻结新增仓 + 冻结「在 allin 内部继续加治理功能」**（见 §五） |

**三个动作**（顺序有依赖，不可并行）：

- **D1 命名与封装** —— 把 allin 的可复用面打包成**可安装的治理工具**（PyPI `allin-governance`
  + 独立门禁包 + GitHub 模板仓）。**这是全部后续动作的地基**：没有可安装的东西，
  「外部采用」无从谈起。
- **D2 外部证据** —— 跑通 `REC-PL-06`（3 名陌生人各自在陌生机器上 30 分钟跑绿），
  并把结果接成 CI 绿章。**「可复制」目前仍是推断，不是事实**；这一条不落地，D1 交付的
  只是一份「据说能用」的工具。
- **D3 叙事与通道** —— 用一条命令能跑通的事实说话（不是用 137 个仓的 star 说话）。

**一条停手令（比 REC-AU-20 更严）**：**冻结「在 allin 内部继续加治理功能」**。
REC-AU-20 的 F4 已经指出「治理的边际收益已过拐点」，但它只建议「不再新增门禁」。
本文认为这不够 —— 本仓最近一个月 161 次提交里，`platform` 350 次文件改动、
`tools` 213 次、`docs` 240 次，**没有一次是在给外部提供价值**。继续往中枢里加功能，
就是继续把「中枢」做得更复杂，而复杂度不等于采用率。

## 一、REC-AU-20 错在哪：把「供给侧」当成了主体

### 1.1 它的诊断是对的

REC-AU-20 §1.1~§1.5 实测：137 仓 / star 2 / fork 0 / issue 0 / Pages 0；
发布区 22 仓 368,300 行代码；治理侧 20/20 门禁全绿、84 份文档、69,908 行。
**供给侧已达中型团队产量，需求侧近乎为零。** 这个诊断没有错，本文完全采纳。

### 1.2 但它的处方指向了错误的层级

REC-AU-20 §五的 90 天计划里，**11 项动作有 9 项的作用对象是 repos**：
O1.1 修 137 仓简介 / O1.2 发布面去占位符 / O1.3 三个仓挂 Release 附件 /
O1.4 三个仓放 GIF / O2.1 `an-engine` 开 Pages / O2.3 GitHub 镜像 3 个旗舰 / O3 内容线 …

**这些动作的隐含假设是「allin 是目录，repos 是商品」。** 全文唯一的例外是
§3.7「内部体系能否产品化」与路线 C「治理体系产品化」，但 §4.2 把它判为
**「C 后置（有 100 个真实用户之后）」** —— 这条判断把顺序完全倒过来了。

### 1.3 顺序为什么是反的

因为 §1.5 推出了一个正确但被低估的结论：

> **「库形产品」是这个组合唯一被验证过的出口，仓页不是。**

它据此选了 `an-engine` 当旗舰（§八第 1 条）。但**为什么不是 allin 自己当旗舰？**
`an-engine` 是 allin 管的一个游戏引擎；**allin 是管 137 个仓的那个东西**。
用 §1.5 的口径推下去：库里唯一被验证过的出口是「可安装可运行的产物」，
而**allin 早就有这个产物**（20 道门禁 + 84 份文档 + 10 步复刻 playbook），
只是它**从未被打包成一个「外部的人能装、能跑、能用」的东西**。

REC-AU-20 写这句话的时候，把 allin 排除在「商品」之外了 —— 因为它把 allin 当成了
**目录本身**。**这就是方向修正的全部内容。**

## 二、方向修正的核心论据：中枢与外围的存续期差

**这一节是本文的支点。** 论据不是修辞，是三组可实测的事实。

### 2.1 存续期：外围在批量退场，中枢不在退场名单上

REC-AU-20 §零的停手令引了分级表：**135 个决策对象（①23 / ②32 / ③68 / ④12）加 4 个归档容器**。
按 [`组合分级决策索引.md`](../../事实源/组合分级决策索引.md)（时点 2026-10-30）：

| 决策层 | 仓数 | 含义 | 对「做产品」的影响 |
| --- | --- | --- | --- |
| ① 核心推进 | 23 | 持续投入 | 可能成为独立产品，但**各自面向不同用户** |
| ② 精选旗舰/保留 | 32 | 维持但不扩张 | 39.6% 的仓，其定位是「维持」 |
| ③ 收敛合并 | **68** | 迁入 `*-prototypes` 等，**原仓冻结** | **已被判死** |
| ④ 止损 | **12** | 停止维护，逐项确认后**删除或冻结** | **已被判死** |
| ③b 归档聚合仓（容器） | 4 | ③ 的落点，非被收敛对象 | 只是容器 |

> **139 个决策对象里，80 个（57.6%）已被判为「合并或删除」。**

**⇒ 论据 1**：如果把资源投在这 137 个仓的「门面与可见度」上，等于把资源投在
**一个已经被自己判定为要退场的资产集合**上。①+② 只有 55 个（39.6%），
而它们是「维持」层 —— 维持不是长大。

### 2.2 依赖方向：中枢被 100% 依赖，外围被 0% 依赖

| 观测 | 实测 | 工具 / 时点 |
| --- | --- | --- |
| `allin` 自身是否在分级索引里 | **不在**（它是索引器，不是被分级对象） | `grep` 分级索引，2026-10-31 |
| 全组合唯一的索引 / 事实源 | `allin`（145 条 registry 全部指向它） | `platform/registry/projects/` 实扫 |
| 门禁覆盖 | 20 道门禁**只审 allin 自己**（对外仓是 `repocheck`） | `tools/gate/governance/registry.json` |
| 文档枢纽 | 85 份规范/事实源/记录，全部以 allin 为根 | `docs/INDEX.md` D1–D8 契约 |
| 外围仓对 allin 的依赖 | **0**（各仓自洽，有自己的 README/LICENSE/门禁） | 逐仓自检口径见 README §本仓自检口径 |

> **⇒ 论据 2**：这是**单点依赖**结构 —— 137 个仓**不需要** allin，但 allin 需要 137 个仓
> 来证明自己成立。**allin 是唯一「不能停」的那一个**，所以它也是唯一值得做大做强的那个。

## 三、外部证据：治理工具本身是可被采用的产品

REC-AU-20 §3.7 已用 `airbnb/javascript` → `eslint-config-airbnb`（148.3k star，
npm 每周 375 万次下载）与 Spotify Backstage → CNCF 两个案例说明
**「内部规范外化为可安装包」是一条被反复走通的路**。本文补三条更贴近本组合的证据：

1. **`govctl`（Rust，MIT，240 star）** —— 「Governance-as-Code CLI for AI Coding」，
   把 RFC / ADR / work item / 验证闸门做成**仓内 TOML 工件**的一等公民，
   提供 `rfc advance` / `work move` 等生命周期命令。
   **含义**：治理工件 + 生命周期命令这套形态，已有独立项目在跑，且面向的正是
   「AI 参与写代码」的团队 —— 与 allin 的 `g16-skill-preset-parity`、
   `g14-preset`（治理段注入 AI 协作者）**是同一个问题域**。
   —— 来源：reporank.net 快照，2026-08-16。
2. **ApexYard（MIT，`me2resh/apexyard`）** —— 一套**纯文本文件 + shell hooks** 的
   AI 编码治理体系：ticket-first 编辑、子代理评审、合并闸门。
   README 自己写明「**没有包可装，工具就是那些文件本身**」，采用方式是
   **star 并 fork**（`gh repo clone your-org/apexyard`）。
   **含义**：①「治理体系可以不发包，直接以文件形态被 fork 采用」——
   这条路对 allin **成本更低**，因为 allin 本来就是文件形态；
   ②它的更新机制是「upstream remote + `/update` skill 做 diff 预览与同步」——
   **这恰好是 allin 对 137 个仓该做的事**，而 allin 现在连自己的 `SPEC-105`
   都还没对外做过一次同步演练。
3. **Red Hat / NVIDIA / IBM 的 `asago`（Apache-2.0，筹建期）** —— 把 AI 治理政策
   变成可部署控制项，每条政策条款 ↔ 一个测试 ↔ 一个运行时控制，
   强调「可追溯性」是卖点。**含义**：治理的价值主张在 2026 年正在被大厂
   制度化地买单 —— 说明「治理中枢」不是小众自娱，而是有预算的市场。

4. **OPA / Conftest / Kyverno / Gatekeeper**（Policy-as-Code 品类，Spacelift 2026 综述）——
   共同点全是**「策略即代码、写在 Git 里、在 CI 与运行时两处执行」**，
   OPA 约 11.8k star 且已 CNCF 毕业。**含义**：allin 的 g01–g20 与
   「policy as code」在形态上同源，差别在于 allin 治理的是**仓库与 AI 协作**，
   不是 K8s 资源 —— 这是一个**尚未被占据的定位**，但也意味着**没有现成的用户群**。

## 四、结论：allin 应该长成什么

### 4.1 产品形态：四选一，判据是「外部的人第一步要做什么」

| 形态 | 外部用户的第一动作 | 成本 | 对 allin 现状的改动 | 判定 |
| --- | --- | --- | --- | --- |
| **P1 可安装的治理工具包** | `pip install allin-governance` 然后 `allin init` | 中（要拆包、要发版） | 拆 `tools/` + `preset/` 出独立包 | **主线** |
| **P2 模板仓**（fork 式采用） | `gh repo create --template siwpan95/allin` | 低（但每仓都要裁剪） | 需一个「最小可用子集」目录 | **并行走 P1 的验证** |
| **P3 纯文件 + 一键脚本** | `git clone` + `bash scripts/bootstrap.sh` | **最低**（2026-10-31 已落地并实测） | 已完成 | **今天就能给外部用**，但不可「安装」 |
| **P4 只做内容传播** | 读文章 | 低 | 无 | **拒绝**：这正是 REC-AU-20 跑偏的那条路 |

> **推荐组合：P3 立刻对外可用（已就绪）+ P1 作为主线 + P2 作分发形态。**
> P1/P2 的存在不推翻 P3 —— P3 是**已经完成且实测通过**的那一档，
> 它让 allin **今天**就能被一个陌生人用起来；P1 只是把同一套东西装得更顺手。

### 4.2 命名约束（实测，不是猜测）

**这是 P1 的第一个硬约束，且必须先解决**：

| 目标 | 名称 | 状态（实测 2026-10-31） |
| --- | --- | --- |
| PyPI | `allin` | ❌ **已被占用** —— Aprila Hijriyan 的 async web framework（0.1.1a1，github.com/aprilahijriyan/allin） |
| PyPI | `allin-cli` | ✅ 空闲（404） |
| PyPI | `allin-governance` | ✅ 空闲（404） |
| PyPI | `repocheck` | ❌ **已被占用** —— Dario Giovannetti（github.com/kynikos/repocheck） |
| npm | `allin` | ❌ **已被占用** —— chilijung 的「make scripts and stylesheets in a single html file」（1.1.1） |
| npm | `allin-cli` | ❌ **已被占用**（1.0.7） |
| npm | `allin-governance` / `@allin/preset` / `@allin/governance` | ✅ 空闲（404） |

> **⇒ 结论**：PyPI 主包用 **`allin-governance`**（空闲，且语义正确）；
> `repocheck` 若要独立发版，**必须改名**（建议 `repocheck-siwpan` 或
> 并入 `allin-governance` 作为一个子命令）。
> ⚠ **PyPI 新建项目有配额**（20 次/小时/用户、100 次上传尝试/小时；
> 且「attempt」与「create」是两套独立计数器）⇒ **首次发布要用占位版本号
> （如 `0.0.0a0`）先占名字**，别在热头上连试。

### 4.3 门面：allin 自己的 Gitee 门面是坏的（实测）

| 字段 | 实测值 | 判定 |
| --- | --- | --- |
| `description` | **`do it better than future`** | ❌ 英文占位句，与内容无关，**搜索时零命中率** |
| `homepage` | `None` | ❌ 无 |
| `has_page` | `False` | ❌ 无演示 |
| releases | `[]`（零个） | ❌ 无交付物 |
| `.github/` 目录 | **不存在**（`git ls-files` 实查 0 个文件） | ❌ 无 CI |
| star / fork / issue | 0 / 0 / 0 | 与 REC-AU-20 实测一致 |
| license | `MIT-0` | ✅ |
| language | `Python` | ✅ |

> **⇒ 这是「allin 自己就是第一个该被修的仓」的硬证据。**
> REC-AU-20 §F1 指出 21 个仓简介乱码、22 个简介过短 —— **而 allin 自己的简介
> 比「乱码」更糟：它是一句与内容无关的英文占位符。**
> 若方向是「allin 是主角」，那么**主角的门面必须是第一个被修的**。

## 五、反证与止损：什么情况下本文是错的

**本文是可被推翻的。** 以下每条都是它成立的前提，任一条不成立则方向需重议：

| # | 反证 | 若成立则 | 当前判定 |
| --- | --- | --- | --- |
| 1 | 外部其实**要的是产品，不是治理** | 继续做 allin 产品化是浪费 | **未证否**。外部反馈通道至今 0 issue（REC-AU-20 §F3），**没有反例也没有正例** ⇒ 本文主张的是**先去取证据**，不是断言 |
| 2 | ①+② 那 55 个仓里有**真能长大的** | 旗舰路线不算跑偏 | **未证否**。但它们「维持但不扩张」的定位本身说明增长不发生在那儿 |
