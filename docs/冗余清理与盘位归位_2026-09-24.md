## 三、D:\musickit（122.8 GB）—— 「伪冗余」判定全过程

**曾误判为「两个不同项目」**，依据是 remote 不同（`siwpan/music.git` vs `siwpan/musickit.git`）。
**这是错的**，与 MEMORY.md L57 禁止的「按同名事物整体判冗余」是同一个坑的另一面。

**README 优先判定**（正确做法）：

| 依据 | `D:\musickit` | `G:\repos\musickit` |
| --- | --- | --- |
| README 首行 | `# G:\music\musickit — phonk 混音项目（真实采样 + 本地混音引擎）` | `# <PATH> — phonk 混音项目（真实采样 + 本地混音引擎）` |

| HEAD 时间 | 2026-08-21 12:35 | **2026-09-24 08:33** |
| HEAD 祖先关系 | `605efc47` **在 G 的历史里** | G 的 HEAD 不在 D 里 → **G 是 D 的后代** |

**素材面逐目录字节级核对**：`bass`/`drum`/`guita`/`woodwind`/`acapella`/`keys`/`strings`/`synth`/`sfx`/`brass`/`animal`/`cowbell` **全部 0.00 MB 差**；`archived` 里 D 独有 **0 个**；D 独有的 141 个文件全在 `.venv`/`.workbuddy`（缓存）。

⇒ 判定：**`D:\musickit` 是 `G:\repos\musickit` 的旧工作树，无可再生内容之外的东西。**

**生成物核查 —— 这里我第一遍判错了，必须留档**

**第一遍（错）**：我只查了 `radio/music`、`radio/recordings`、`radio/*` 与 `.venv`/`packages`/`ffmpeg`/`cloudflared` 等，
见 `music`/`recordings` 是空目录，就下了结论「**不可再生的本地生成物为零，整体可删**」并**启动了删除**。

**漏掉的正是用户指出的 `output` 文件夹**：

| 目录 | D 侧 | G 侧（合并前） | D 独有 |
| --- | --- | --- | --- |
| `remix/output` | 169 文件 / 2251.5 MB | 108 文件 / 1880.3 MB | **126 个 / 1415.2 MB** |
| `musickit-fix-20260817/mirror2/remix/output` | 35 文件 / 797.3 MB | 35 文件 / 797.3 MB | 0（G 本就完整包含） |

`remix/output` 是**本地渲染出来的混音成品**（`phonk_remix_2026*.wav`、`act/短视频*.wav`、`mixer_stream/`、`short/` 等），
且 `.gitignore` 里 `remix/output/` 是被**刻意排除**的生成物 —— 排除规则写在 `.gitignore` 不等于可以不保留，**那是"不入版本库"，不是"可删"**。

**处置（先抢救后删，逐步验证）**：

1. 收到用户指正后**立即终止删除任务**。当时已删 19 个顶层项，**两份 output 均完好未损**。
2. 用 `robocopy /E /XC /XN /XO`（**只补缺、不覆盖**）把 D 侧独有文件合并进 G：
   - `remix/output`：退出码 3，耗时 87.8 s，G 侧 108 → **234 文件**，1880.3 → **3295.5 MB**
   - `fix/mirror2/remix/output`：退出码 0（无需复制），G 侧保持 35 / 797.3 MB
3. **反向验证**：期望 108 + 126 = **234**，实测 **234 ✅**；`act/` 57 文件 744.8 MB 在；`LBGM1.wav` 等 3 个顶层大文件都在；第二个 output 与 D 侧**完全一致**。
4. 验证通过后**只显式删除这两个 output 目录**（不做宽范围删除），再重启整体删除。

⇒ **修正后的结论**：`D:\musickit` 除 `remix/output`（已抢救入 G）外无其它不可再生内容；抢救完成后整体可删。

> ⚠ **教训（与 README 优先同源）**：判「生成物」不能只看 `.venv`/缓存/日志这类显眼的，
> 也不能因为某个路径写进了 `.gitignore` 就当成可弃 —— `.gitignore` 管的是"进不进版本库"，不是"留不留"。
> 用户一句话（`output 文件夹`）直接指出了盲区。

## 六、受限文件与 ACL 修复脚本

`G:\platform\registry\projects\` 下 **8 个 yaml 读不出来**（连 `Get-Acl` 都被拒）：

```

```

- 目录共 112 个 yaml，其余 104 个正常 → **同目录混排**，说明是旧机 SID 残留而非目录级策略
- 与 2026-09-24 修过的 `G:\allin\docs` 三个文件同类问题、同一手法

**修复脚本**：`G:\tools\fix-registry-acl.ps1`（与 `fix-docs-acl.ps1` 同款）
- 需**管理员**运行；非管理员 → **exit 3**（已实测）
- **自动发现**：实测读不出来的才算受限，不靠硬编码清单
- `-WhatIf` 干跑；逐文件 `takeown` + `icacls /grant <user>:(F)` + **复验可读**才算通过
- 退出码：0=全修好；1=仍有失败；3=缺管理员权限
- 只改 ACL，不动内容，不动同目录可读的那些

用法：
```powershell
pwsh -File G:\tools\fix-registry-acl.ps1 -WhatIf   # 干跑看清单
pwsh -File G:\tools\fix-registry-acl.ps1           # 真正执行（需管理员）
```
