二、工作流：两条链路与一道监工

allin 的工作流不是单一流程，而是两条正交链路 + 一套机械监工的组合。这一点在 SPEC-107 的开篇写得很清楚：

协作节奏面（SPEC-002：先问 → 计划 → review → 执行 → 复盘） ├─ 在场模式：逐项确认，高风险动作（推送/建仓/删除/密钥/仓结构）逐项放行 └─ 自主模式：选推荐项并记账 · 攒着不推 · 不可逆不做 交付 substance 面（SPEC-107：需求 → 拆分 → 开发 → 审查 → 测试 → 修复） ├─ 阶段四强制机器实跑，问题必须带 file:line，无证据结论作废 ├─ 阶段三前置强制备份 + 10 项安全核验（"22 项"口径经核查无成文清单，未虚构） └─ 阶段六输出闸门：交付前跑 D1–D12（"C1–C10"口径订正为 D1–D12） 机械监工（tools/gate：20 道治理门禁 + D1–D17 文档契约 + 30 条 repocheck） └─ 退出码词汇 0/1/2/3（干净/阻断/用法/环境），SKIP 如实计数，不冒充通过

机制的核心设计：门禁是事故的封印

每一条门禁都对应一类真实发生过的事故，而不是审美偏好。抽样验证：

门禁封印的事故判定方式
g01-paths脚本里写死某台机器绝对路径 → 换机即坏正则扫盘符字面量
g03-credentials凭据写进仓库或 .git/config → 公开历史只能吊销重发密钥模式 + 熵值判据
g08-deletion-evidence删掉功能面却没记接任者 → radio 直播面整片消失删除证据留证
g11-undef-names改写脚本丢了 import → 编译通过、运行才炸AST 静态扫描
g14-presetpreset 悄悄漂移 → 新会话静默失去治理段（仓内门禁全绿也发现不了）profile 探针 + 挂载三层校验
g20-facts9 处断言与磁盘不符，而 19 道门禁 exit 0 → 判据没覆盖path-exists / count / self-identity 三类声明

三个值得称道的机制设计

  • 自检写进契约：每道门禁必须用真实破坏用例（临时仓里真写一条死路径、真删一个字节）证明自己还能抓到缺陷，--selfcheck 要求 caught≥1、misreports==0。只有阳性测试的门禁会把假绿卖给所有人。
  • 基线棘轮：存量一次性冻结进 baseline/，此后只拦新增。门禁能「今天就绿」而不被绕过。
  • SKIP 不算通过：服务缺席时门禁记 SKIPPED (not a pass) 并计数。全部跳过时退 EXIT_ENV 而非 0——「一个都没跑」≠「一个都没问题」。

这是本次勘察最重要的产出。以下三项均为现场复测所得，非照抄文档：

失守一：CI 连续红灯 8 天，回归点精确定位

项实测值

根因链（已逐环验证）：

559eb31 把 7 个 registry 条目的 category 从 game 改到 engine/prototype/content ↓ （gameplay 标签未同步） registry.js:271 判据「非 game 类项目不应填写 gameplay 标签」触发 ↓ 7 条 problems：cordis-snake · dict-scene-engine · lab · novel-reader sin-virtue-cordis-host · sin-virtue-game · weiqi-lab ↓ platform/scripts/check.mjs 能报出来 —— 但它不在默认跑批里 ↓ 盲区：run_all_gates.sh 只在 --with-platform 分支跑 platform check g17-registry 只判 id/生命周期/完备性，不调 validateEntry 字段级判据 ↓ 结果：20 道门禁全绿 ✅ ＋ CI 全红 ❌ —— 两者同时为真

CI 上两个失败 job 实为同一根因：Windows job 在 npm run smoke:e2e 之前先跑 npm test --prefix platform，该步 exit 1 导致冒烟根本没执行。smoke:e2e 本身无问题——本地实跑 8/8 全绿。

这件事的治理意义，比红灯本身严重

方向修正文档（2026-10-31 §7.1）把「CI Linux+Windows 双平台绿，run 41154530905」列为本仓历史上第一次有外部可复现的绿，并据此判定「可复制性」从推断升级为事实。

该论据现在已不成立——CI 连续 8 天红灯，且红灯的根因恰恰是「数据改了、门禁没覆盖」，与文档批评的「只有一台机器验过」是同一类问题的变体。

更要紧的是：这份报告的其余部分（叙事传播 D3.1）恰恰建立在「CI 绿」之上。对外发声前必须先恢复这个事实，否则就是把已知红灯的仓推给陌生人。

停手令写得很清楚——「新增门禁、新增 SPEC、新增 registry 条目，一律先问『这条是给外部用的，还是只是让中枢更好看？』」。

一条反向建议：考虑做减法

方向修正文档的反证第 4 条至今「未证否但有张力」。综合本次实测，这个张力的量级已经变化——CI 连续红灯 + 对外产出为零 + 近 30 天改动量创新高，三条同时成立，说明系统正在高速生产无人消费的产物。

一个候选动作：把 20 道门禁中 P1 档的门禁合并或降频，只保留事故封印类（g01/g03/g04/g08/g11/g14/g20）。门禁的价值与它拦住的事故成正比，而「跑得更多」不等于「拦得更准」。

八、结论

1. allin 的工程质量是真实的高水平。20 道门禁 + D1–D17 文档契约 + 30 条 repocheck + 基线棘轮 + 自检契约 + 双形态注入 + 结构化事实投影 + 三栈派生层 + 零依赖可安装包——这套东西的完整度在个人开源项目里罕见，且每条机制都有事故出处，不是纸上谈兵。

2. 但它当前正被自己的成功反噬。机制越完善，内部投入的回报感越强，而外部价值信号为零——两者叠加，产出量在创新高（240 笔/月），采用者在零。这不是执行不力，是优化目标设错了：allin 优化的是「治理完备性」，而方向修正文档已经把战略目标改成了「外部采用」，机制却没跟着换。

3. 三处失守都在同一个位置：判据与现实之间的缝。CI 漏检 registry 字段漂移（判据在 platform，门禁在 tools）、远端仓数无人核（判据要求本地路径）、停手令靠自觉（无机器判据）。allin 已经有成熟范式可循——把每条「靠自觉的纪律」变成一条带自检的门禁——但每一次这样做都会增加中枢体积。这是这个体系最深层的结构性矛盾。

4. 最紧迫的动作是修 CI，不是做新东西。当前 CI 红状态下，任何对外传播都是把一个已知有缺陷的仓推给陌生人；而 D3.1 长文的唯一硬论据恰恰就是「CI 双平台绿」。修 CI 是解锁传播的前置，不是并行项。

5. 对未来的判断：allin 大概率会长期保持「一个人维护、零外部采用」的状态——这不是失败，因为服务对象①（作者本人）和②（AI 协作者）都已成立且受益。但若要兑现方向修正文档设想的第三条腿，必须接受一个前提：接下来 90 天的产出量应当下降，而不是继续上升。

勘察方法：全程只读，未修改 G:\allin 任何文件。所有数字均现场复测（门禁实跑 6m11s、platform 单测实跑、Gitee/GitHub API 实查、git 历史实测），未照抄文档。文档声称值与实测值的差异已在文中逐条标注。

本报告的两处局限：① 仅在本机（DESKTOP-KQABATS）实测，另两台机器（DESKTOP-8RSV60V / SIWPAN）的状态未复核；② CI 失败日志未取到完整 step 输出（无 gh CLI，API 未提供完整日志），失败根因由「本地复现 + 提交历史二分 + workflow 定义」三方交叉推定确认。
