## 零、结论先行

**一句话**：这个组合的问题不是「不够大」，而是**大得没有出口** —— 供给侧已经是一个中型团队的产量，需求侧还停在 0。

| 维度 | 实测 | 含义 |
| --- | --- | --- |
| 供给 | 137 个公开仓；发布区 22 仓 **368,300 行代码 / 1,226.8 MB** | 产量不缺 |
| 需求 | **star 合计 2 · fork 0 · 外部 issue 0** | 需求侧几乎为空 |
| 治理 | **20/20 门禁全绿 · 84 份文档 · 145 条 registry · 15 个 skill** | 内部一致性已到很高水位 |
| 出口 | 4 个 PyPI 包（唯一被验证过的通道），近月下载量级 **0–93 次/包** | 已有活口，但极窄 |

**一条主线**：把已经存在的产能，换成外部能看见的成果。不是再造一批仓，也不是再加一批门禁。

**三个动作**：**O1 开门**（30 天，修 137 个仓页的「首屏 + 交付物」）→ **O2 举旗**（60 天，1 个旗舰做到「10 秒看懂、一行跑起来」）→ **O3 播传**（并行，用过程记录做内容杠杆）。

**一条停手令**：**冻结新增仓**。[分级表](../../事实源/组合分级决策索引.md)里 135 个决策对象（①23 / ②32 / ③68 / ④12）加 4 个归档容器，已远超一个人的兑现能力；再加仓等于继续稀释注意力。

## 二、诊断：五个结构性断层

### F1 发现断层 —— 元数据不合格，等于结构性隐身
- **证据**：112/137 无语言识别、21 个简介乱码、22 个简介 <12 字、0 个 Pages、1 个 homepage。
- **机理**：Gitee 探索页的仓库卡片**只展示「名称 + 简介 + 语言 + star/fork」四项**（[Gitee 推荐体系解析](https://segmentfault.com/a/1190000048182475)）。这四项里**只有「简介」和「语言」是作者可控的文本变量** —— 而这两项在本组合里分别有 21 个乱码、112 个空缺。
- **代价**：137 个门面 ≈ 137 个无人到访的页面。热榜看 star 增量，而 star 需要先有人来。
- **纠正**：这不是「推广问题」，是「元数据问题」——**修复成本约 1 天**，是全篇投入产出比最高的动作。

### F2 交付断层 —— 「跑起来」断在下载物与占位符上
- **证据**：抽样 10 个旗舰仓 release 附件 **0 个**（其中 7 个有 release）；Gitee Pages **0 个**；README 首屏 **6/22** 直接把 `<PATH>` 占位符摆给陌生人看；`allin-engine` 的 PyPI 项目主页（唯一有真实流量的页面）第一句至今是「注：文中 `<PATH>` 为路径占位符，请替换为你本机实际的目录」。
- **根因**：这是 **铁律 5「去符盘」的机械副作用** —— 盘符被去掉是对的，但换上的不是可读口径，而是占位符。发布面（PyPI 描述 / README 首屏 / Release 说明）与开发面混用了同一套写法。
- **代价**：最强的视觉能力（`3dworld` 的 48 秒五幕演出、150 秒程序化走廊）**只能靠文字描述**；陌生人在 10 秒内接收不到任何证据。
- **纠正**：把「去符盘」升级为「**去占位符**」—— 发布面一律不写 `<PATH>`，改「仓根」「<工作区根>」，或直接删掉该句。

### F3 反馈断层 —— 体系从未收到过一个外部信号
- **证据**：0 issue / 0 fork / 2 star（且来自 2 个不同仓，非传播）。
- **代价**：所有优先级判断都建立在内部推测上。**门禁证明的是「账实一致」，不是「有人要」**；一个没有反馈回路的系统，只能不断优化自己的自洽性 —— 这正是过去 30 天发生的事。
- **现成的解**：[`REC-PL-06`](../计划/T2可复制性计时实证_待执行_2026-10-30.md)（3 名陌生人 × ≤30 分钟独立跑通 20 道门禁）**至今待执行**。它就是一次被完整设计好、却还没开跑的外部验证，成本 1 天。

### F4 注意力断层 —— 治理的边际收益已过拐点
- **证据**：2026-10 单月 159 次提交全部在本仓（占历史 316 次的 50.3%）；而最近抓到的三类真事故（`g15` 假阳性、`g01` 回归、门禁口径 15→19 未回写）**全部是治理自身的缺陷**，不是产品缺陷。
- **代价**：每加一道门禁，都在增加「维护治理」的固定成本，而不是「获得用户」的边际收益。
- **纠正**：下一阶段治理的产出指标不该是「门禁数量」，而是「外部指标有没有动」。

### F5 单点断层 —— 一人 · 三机 · 20/22 仓无 CI
- **证据**：机器事实源已到第 3 个分区文件；发布区仅 2 仓有 CI；全部提交单一作者。
- **代价**：换机/停机即断供；「可复制」目前仍是**推断**而非事实（`REC-PL-06` 的判据原话）。
- **纠正**：先把「一台陌生机器 30 分钟跑通」变成事实，再谈扩张。

## 三、外部证据（联网核实，标源）

### 3.1 星标是幂律，不是加法
- 覆盖 1,950 份 README 的实证研究因「最少 star 的仓大多为 0」而**无法取到最低分层样本**，并把「流行」门槛定在 ≥5,153 star（各语言 top100 下界）—— [arxiv 2206.10772](https://arxiv.org/abs/2206.10772)。
- 2026 年一项经济学论文发现：某组件被前沿编程模型推荐后**下载上升、star 下降**，star 与真实使用已经脱钩 —— [arXiv 2601.15494](https://arxiv.org/abs/2601.15494)。
- 【推断】**多仓不叠加影响力**，只会把每个仓都钉在 0–2 star。唯一能叠加的是「同一批用户被反复服务」。

### 3.2 漏斗节点的真实杀手
- 一手案例：36 个工具开源后 **157 人 clone、2 star、0 fork、0 购买**；作者自诊断的漏点＝README 无截图/GIF、无 30 秒 quickstart、首屏无价值主张、人群错配 —— [DEV: 157 Cloners, 2 Stars, 0 Sales](https://dev.to/473185670/157-cloners-2-stars-0-sales-diagnosing-my-open-source-funnel-4m5)。
- README 含图片、列表、外链、贡献指南与流行度显著相关 —— [arxiv 2206.10772](https://arxiv.org/abs/2206.10772)。
- 【推断】转化杀手排序：① 首屏没有 10 秒动图 → ② 不是一行命令能跑 → ③ README 以架构/治理开头 → ④ 缺 license、CI 徽章等「项目还活着」信号 → ⑤ 没有「下一步」。

### 3.3 Gitee 的分发机制（近程能拿的只有两件事）
- 体系由 **GVP 认证 / Explore 探索页 / 热度榜单 / 搜索分发 / OSS-Compass 健康度** 构成（[Gitee 推荐体系解析](https://segmentfault.com/a/1190000048182475)）。
- **GVP 有硬门槛**（转引自 `gitee.com/gvp` 的 10 条要求，经两个独立来源交叉印证）：托管 Gitee、OSI 许可证、专家评审创意性、**年更新 ≥10 次**、响应反馈、官网标注 Gitee 链接、**贡献者 ≥5**、文档完善、**Star ≥100**，且**年审制**；累计入选仅 **466 个**（平台 4,000 万仓）—— [GVP 条件转载](https://blog.csdn.net/tianmaxingkonger/article/details/121421671)、[SegmentFault 2026-08](https://segmentfault.com/a/1190000048150727)。
- 【判定】**`Star ≥100` 与 `贡献者 ≥5` 两条直接卡死，GVP 不是近程路径**（这是硬条件，不是推断）。但注意名额分布：程序开发 116 / WEB 应用 82 / **人工智能仅 50** —— AI 赛道相对空位最多，属于中长期可瞄准的方向。
- 【判定】**近期真正可得的是两件事**：① **元数据资格**（能被 Explore 分类与搜索命中）；② **热榜的 star 增量**（Trending 分日/周榜，官方未公开权重）。两者都先要求「能被搜到」—— 回到 F1。
- **活动纠正**：现行官方活动是「**Gitee 年度开源项目评选**」（2025 届 2026-01-09 投票截止、2026-01-29 揭晓；冠亚季军可得官网 Banner + 推荐标签 + 搜索引擎专属卡片），**没有**名为「Gitee 开源大赛」的现行活动。2026 届截至 2026-10-31 未检索到公告（是「未找到」，不是「不存在」）—— [2025 届报道](https://www.sohu.com/a/981438443_827544)。若开赛，这是**低成本曝光位**，应列 P2 参加。

### 3.5 平台选择：Gitee 是「主仓」，但 GitHub 是「主场」
- 量级对比：GitHub 约 **1.8 亿开发者 / 6.3 亿仓**（其中 63% 公开），Gitee 约 **1,400 万用户 / 4,200 万仓** —— 受众差约 **12–13 倍**（[Octoverse 2025](https://itsfoss.com/news/github-octoverse-2025/)、[Gitee 官方博客](https://blog.gitee.com/)）。
- 生态对比：PyPI / Awesome 列表 / topic / 英文搜索的长尾都在 GitHub 侧；Gitee 侧的独有筹码是 GVP 与年度评选资格。
- 【建议】**双轨，不二选一**：Gitee 保持主仓与治理事实源；**3–5 个旗舰在 GitHub 建镜像仓**（带 topic、README 同步、PyPI 项目链接指向 GitHub）。冲突点只有一个：GVP 要求「官网标注 Gitee 链接、文章用 Gitee 地址」，与主推 GitHub 有轻微张力 —— 用 README 双写（首屏同时给两个地址）即可化解，且 GVP 本来就不在近程射程内（§3.3）。

### 3.6 变现现实（先把预期钉住）
- Tidelift 2024 调查（400+ 维护者）：**47% 完全无收入**、25% 来自捐赠类、24% 是雇员工资、直接来自公司仅 5% —— [Tidelift](https://dev.to/tidelift/whos-paying-the-maintainers-donation-programs-employers-and-tidelift-3j4k)。
- 收全球钱实际靠 MoR，微信支付支持付款但**不支持订阅扣款**；自申微信商户号需公司主体 + 备案 —— [MoR 中国实操](https://www.waffo.ai/zh/blog/merchant-of-record-china-developers)。
- 【推断】**90 天的目标不该是收入**，而是「真实用户」。可行性排序：教程/课程 → 定制外包 → 赞助（需 500+ 真实用户才有意义）→ 付费进阶版 → SaaS（最重，不建议先做）。

### 3.8 AI 杠杆的真实边界
- MCP 生态已有 **1 万+ 活跃公共 server**、SDK 月下载 9,700 万+；但实践中同时接 5–7 个 server 后工具选择准确率就下降 —— [Anthropic](https://www.anthropic.com/news/donating-the-model-context-protocol-and-establishing-of-the-agentic-ai-foundation)。

## 四、战略选择

### 4.1 三条可选路线

| 路线 | 内容 | 优点 | 代价 | 90 天可见成果 |
| --- | --- | --- | --- | --- |
| **A 产品化单点突破** | 选 1 个旗舰做成有真实用户的产品 | 唯一能通向收入 | 需要读懂用户，最慢 | 一个能装的产品 |
| **B 影响力优先** | 元数据开门 + 过程记录做内容 + 体系外化 | 成本最低、素材已在库 | 不直接带来收入 | 第一批关注与 issue |
| **C 治理体系产品化** | repocheck / 规范模板 / MCP server 对外 | 差异化最高 | 需要 A 的用户基数才有分发 | 一个模板仓 |

### 4.2 推荐：**B 先行 + A 并行，C 后置**

- **B 先行**（第 1 天起）：它的原料全部已经在库里 —— 84 份文档、158 次门禁留痕、137 仓治理实验、三机事实源。**这是唯一「边际成本接近 0」的杠杆。**
- **A 并行**（第 2 周起，只选 1 个）：选**库形**而不是桌面 exe —— 因为 §1.4 已证明「pip 可装」这条管道是通的，而桌面包要面对无签名、杀软误报、无下载附件三重摩擦。
- **C 后置**（有 100 个真实用户之后）：体系产品化的分发依赖 A 的用户，提前做只会做出一个没人 import 的包。

### 4.3 停手令（与动作同等重要）

1. **不再新增仓**（除归档容器）。
2. **不再新增门禁**，除非它拦下的是一类**已发生过**的真事故（沿用 REC-AU-15「先 shadow 再阻断」）。
3. **不同时打磨多个仓**：同一时间只有 1 个旗舰处于「打磨态」，其余只做元数据级修复。
4. **不把收入写进 90 天指标**（依据 §3.6）。

## 六、把增长写进机器（本仓最擅长、但现在完全缺失的一环）

现在 20 道门禁**全部在测内部一致性**，没有一条在测外部。建议补的**不是**「门禁」，而是**两层可分离的机制**（严格遵守本仓「离线、零依赖、可复跑」的门禁哲学）：

### 6.1 采集层（联网，单独跑，不在门禁套件内）
`tools/traction/collect.py`：抓 Gitee API + PyPI/pypistats + GitHub，落 **`data/traction.jsonl`**（一行一次快照，只增不改）。指标口径固定为：
`stars_total`、`forks_total`、`external_issues`、`releases_with_assets`、`pages_live`、`pypi_downloads`、`desc_defects`。
> 为什么不让它进门禁：门禁必须离线可复跑；外部数据源一联网就引入不确定性。**证据采集与门禁控制分离**，与本仓「事实源 vs 规范」的分离是同一个道理。

### 6.2 门禁层（离线，只校验快照，不联网）
| 拟增门禁 | 判据 | 级别 |
| --- | --- | --- |
| `g21-listing` | 仓页元数据快照：简介非空/不乱码/≥30 字、`language` 有值 | P0（先 shadow 30 天） |
| `g22-release` | ① 层仓必须有 ≥1 个 release **且附件 ≥1** | P0（同上） |
| `g23-demo` | 旗舰仓 README 首屏必须含媒体或「一行命令」 | P1 |
| `g24-traction` | `data/traction.jsonl` 新鲜度（≤14 天）+ 与 INDEX 自述一致 | P1 |

### 6.3 为什么值得做
过去 30 天的教训是：**只有被机器看着的指标才会被维护**（门禁逃逸率 3.2%、例外台账带到期日，都是靠机械保证才没退化）。而 star / 下载 / issue 这些真正决定「做大做强」的指标，目前**没有任何机器在看** —— 所以它们在 5 个月里一次也没动过。

## 七、风险、止损线、不做清单

| 风险 | 现实依据 | 止损/对策 |
| --- | --- | --- |
| 内容写了没人看 | 陌生渠道首篇命中率低是常态 | O3.1 连续 8 篇无外部信号 → 内容线降级为季度一次，力气全回 O2 |
| 单点断供 | 1 人 / 3 机 / 2 仓有 CI | O2.2 先做；换机前先复跑 `REC-PL-06` |
| 把「下载量」当用户数 | 镜像与机器人污染 pypistats | 只认**issue 与 fork**为「真实用户」信号 |
| 变现幻觉 | 47% 维护者零收入 | 90 天内不设收入指标 |
| **把 0 star 当个人失败** | 约 **90%** 的 Claude 关联输出指向 0 star 仓、**98%** 指向 0–1 star 仓（[腾讯云开发者社区](https://cloud.tencent.cn/developer/article/2647709)）→ 0 star 是全球常态 | 自我评价改用「**有没有被真实用户用过**」（issue/fork/下载），不用 star |
| 治理继续膨胀 | 治理文档已与最大旗舰等量 | §4.3 停手令 |
| 元数据修复被当成「已完成」 | 平台侧有缓存 | 修复后 7 天复扫，写入 `data/traction.jsonl` |

**明确不做**：① 不再开新仓；② 不做桌面 exe 作为首推形态（无签名、无附件、杀软误报）；③ 不在同一季度打磨 3 个以上旗舰；④ 不为「好看」重写 README 全文（只改首屏）；⑤ 不把 MCP/Skill 当分发渠道；⑥ 不做 SaaS。
