## 一、为什么需要它（事故驱动）

文档写得再全，缺了监工照样一遍遍踩坑。这里的每一条门禁都对应一类**真实发生过**的事故；门禁不是审美产物，是事故的封印。

| 事故类型 | 代价 | 对应门禁（allin 侧 15 道） |
| --- | --- | --- |
| 脚本/配置里写死某台机器的绝对路径 | 换机即坏、克隆即错 | `g01-paths` |
| 门禁自己骗自己（排除项过宽、打印了就返回 0） | 报绿反而更危险 | `g00-meta` + 每个门禁的 `--selfcheck` |
| 凭据写进仓库或 `.git/config` 的 `branch.*.remote` | 公开历史只能吊销重发 | `g03-credentials`（已上线） |
| 用陈旧的 `origin/BR` 判断「推上去没有」 | 以为推了其实没推 / 以为没推其实推了 | `g04-push-evidence`（已上线） |
| 目录被 `.gitignore` 吞掉，`git status` 却沉默 | 克隆副本跑不起来，本地全绿 | `g00-meta` 的 `untracked-support` 检查（已上线） |

## 二、怎么跑（allin 侧命令）

```powershell
npm run check:governance            # 全部门禁，仓内判据（聚合默认带 --no-profile，不读 host profile）
npm run check:governance:selfcheck  # 证明每个门禁仍能抓到注入的缺陷
npx tsx tools/gate/governance/run.ts --list            # 列出 id / 档位 / 覆盖的规则
npx tsx tools/gate/governance/run.ts --only g01-paths # 只跑某几条（逗号分隔）
npx tsx tools/gate/governance/run.ts --no-profile     # 显式声明「只看仓内」（聚合默认已带）
npx tsx tools/gate/governance/run.ts -- --quiet       # `--` 之后的参数透传给每个门禁
python tools/gate/governance/gates/g01_paths.py --selfcheck       # 单条门禁自检（不经 Node）
python tools/gate/governance/gates/g01_paths.py --no-baseline --list-all  # 看全量存量，忽略基线
python tools/gate/governance/gates/g14_preset.py                  # 单跑：含 profile 探针（读 preset 安装点）
```

> **2026-10-26 订正（入口去 tsx）**：聚合入口已改为 `node tools/gate/governance/run.ts …`
> （Node ≥ 22.18 原生类型擦除，不需要 `npm install`、不需要 tsx）；上面命令里的 `npx tsx` 一律按此替换。
> 新增一条全量命令 `npm run check`（治理 + 文档 + `.ps1` 编码）与提交钩子用的 `npm run check:precommit`（13 条快速子集）。
> 原因与证据见 `docs/记录/交接/2026-10.md` 的 `20261026130032` 节。

**仓内 vs 仓外的边界（重要）**：`check:governance` 是**仓内**判据 —— 它带 `--no-profile`，只转发给
注册表里声明了 `profileProbe` 的门禁（当前只有 `g14-preset`），其他门禁不会收到这个开关。
**要查「仓外部署面」**（preset 安装点的 `link:` bundle 是否悬空、挂载的 patch 是否完整）就**单跑** `g14-preset`，
或显式 `npx tsx tools/gate/governance/run.ts --only g14-preset`（不带 `--no-profile`）。两种模式都有 A/B 实证：
带标志时输出里 0 条 profile 解析行，不带时 1 条。

**退出码（全部门禁统一）**：`0` 干净 · `1` 基线之外的新阻断 · `2` 用法错误 · `3` 环境错误。
`run.ts` 会把各门禁的结果按「最坏优先」聚合（`3` > `2` > `1` > `0`）；任何一条非 0 都不会被吞掉。

**依赖**：Python 3.9+ 与 `git`。解释器按 `DSH_GOVERNANCE_PYTHON` → `python3` → `python` → `py -3` 的顺序探测，**探不到就带名字报错**（`exit 3`），不会静默跳过 —— 静默跳过等于这条门禁不存在。
平台专属能力（如 Windows 事件日志）在别的平台上记 `SKIPPED (not a pass)` 并计数，**SKIP 不算通过**。

## 三、门禁契约（为什么自检必须写进契约）

每个登记在 [`registry.json`](../../tools/gate/governance/registry.json) 的门禁必须满足的全部条款（由 `g00-meta` 逐条机械校验）：

1. 注册表条目含 `id`/`title`/`script`/`tier`/`rules`/`platforms`/`requires`/`selfcheck`；
2. 脚本存在，且 `--help` 暴露 `--selfcheck`、`--quiet`、`--baseline`、`--no-baseline`、`--write-baseline`、`--list-all`；
3. `--selfcheck` 退出 0，并输出 `SELFCHECK {"caught":N,"clean":M,"misreports":K}`，要求 `N≥1`、`M≥1`、`K==0`；
4. 门禁 id 在 [`RULES.md`](../../tools/gate/governance/RULES.md) 里有记载（规则必须能找到执行它的那条门禁）。

**为什么把自检写进契约**：只能跑阳性、或者「打印了提示就返回 0」的门禁，会把假绿卖给所有人。自检必须用**真实破坏用例**（临时仓里真的写一条死路径、真的删一个字节），不是把判断注释掉。

## 四、基线棘轮（让门禁「现在就能绿」）

存量没清完就上线的门禁，通常的结局是被绕过。因此每条门禁都支持基线：存量一次性写进 `baseline/<gate>.txt`，此后**只拦新增**。

```powershell
python tools/gate/governance/gates/g01_paths.py --no-baseline --list-all   # 先看全量
python tools/gate/governance/gates/g01_paths.py --write-baseline           # 再冻结存量
git diff tools/gate/governance/baseline/                                    # 基线变化必须可评审
```

**纪律**：刷新基线前必须先看全量；基线文件随仓提交（收紧与放宽都要在提交信息里写明理由）；`g01-paths` 的基线当前**为空**，即存量已清零。

## 六、粘合剂不变量（并入 allin 后的新增约束）

2026-10-26 起，治理门禁树（`tools/gate/governance/`）与 cordis 声明式 preset（`preset/allin/allin.patch.yml` 的 GOVERNANCE 块）互为守护：

- 文档改、工具加、platform 扩，任何新内容并入都先过两道门禁 —— `npm run check:governance` 与 `python tools/gate/docs_index.py`；
- 门禁反过来守住 preset：`g14-preset` 校验 GOVERNANCE 块成对有序、段内无盘符路径、引用的仓内文件必须存在、提到的门禁 id 必须已注册；
- preset 反过来守住门禁：治理段随 agent 启动即生效，会话首轮即带治理判据，避免「仓内门禁全绿、会话却静默失去治理段」。
