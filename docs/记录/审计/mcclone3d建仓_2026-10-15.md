## 二、建仓是两步（Gitee 既定行为，非缺陷）

令牌建仓的结果**必然私有**，需显式转公开 —— 与 `SPEC-001 §铁律 4` 记载的 2026-09-24 实测一致：

1. `POST /user/repos`（带 `license_template: MIT`）建仓 → 响应 `private: true`；
2. `PATCH /repos/{owner}/{repo}` 显式转公开 → 成功。

**这一步不是"字段被静默忽略"，也不是 API 缺陷，而是 Gitee 的既定语义**（该判断已在 `铁律 4` 的留档里纠正过一次，
本次直接按既有结论执行，未重复踩）。

### 2.1 新坑（本次新增的第二条）：PATCH 用 form-urlencoded 正体会 406

| 正体形态 | 结果 |
| --- | --- |
| PowerShell 默认的 **form-urlencoded**（`-Body @{...}`） | ❌ **406 Not Acceptable** |
| `-ContentType 'application/json; charset=utf-8'` + **JSON 正体** | ✅ 成功转公开 |

* **原有记载**：`SPEC-001 §铁律 4` 只记了「PATCH 的 body 必须带 `name`，否则报 `name is missing` **400**」。
* **本次新增**：即使带了 `name`，**正体编码不对仍会失败，且失败码是 406 而不是 400** —— 4xx 的具体码会误导人往
  「路径 / 权限 / Accept 头」上找，实际病根在**正体编码**。
* **可复用判据**：Gitee v5 的写接口**一律用 `application/json; charset=utf-8` + JSON 正体**；
  看到 406 先查 `Content-Type`，不要先查 URL。
* **为何值得沉淀**：这是"同一接口的第二条坑"，且**只在用 PowerShell 默认正体时出现** ——
  换工具（curl / Python requests）不会复现，所以它属于"**工具默认值的隐性契约**"这类坑，靠人记必然再犯。

> **待放行（本次未做）**：把 2.1 这条并进 `SPEC-001 §铁律 4` 的建仓流程段。改规范属**受控修订**（`SPEC-005 §10` 结构变更级），
> 不在本次记账的写入面内，故**只登记不执行**。

## 四、首次推送遇到 `Initial commit` —— 用 merge 而不是 force push

`license_template: MIT` 会让 Gitee 自动生成一个 `Initial commit`（`36a411d`，只含 LICENSE 21 行）
⇒ 远端非空，首次推送**必然**遇到 unrelated histories（`SPEC-001 §铁律 4` 已预告这一点）。

| 处置 | 命令 | 为什么不是别的 |
| --- | --- | --- |
| ✅ 采用 | `git merge --allow-unrelated-histories -X ours` | 保住远端提交、不改写历史 |
| ❌ 未采用 | `git push --force` / `--force-with-lease` | 会**抹掉远端那个提交**；`铁律 0` 要求资产与历史永远保全 |

* **两份 LICENSE 的关系**：逐行**完全相同**，唯一差异是 **CRLF/LF** ⇒ `-X ours` 不会丢任何实质内容。
* **判定依据**：先逐行比对两份 LICENSE，确认"文件级冲突但内容级无冲突"，**再**选 `-X ours`；
  顺序反了（先 merge 再看内容）就可能把真差异一起丢掉。

## 七、复盘：偏差与教训

1. **偏差（计划外重大事实）**：建仓转公开时**新增一条未知失败 406**。按 `SPEC-002 §二.4`，这属于"执行中遇计划外事实"，
   但**不推翻计划假设**（仓已建成、目标不变），故按小偏差处理：当场定位（正体编码）→ 继续 → 记入本条记录。
2. **教训 A（4xx 的码会撒谎）**：406 看起来像 `Accept` 头问题，实际是**正体编码**问题。
   ⇒ 排查顺序应是「`Content-Type` → 正体形态 → URL/权限」，不是从状态码字面猜。
3. **教训 B（工具默认值也是一种接口契约）**：同一个 PATCH，PowerShell 默认正体失败、显式 JSON 成功。
   ⇒ **"换个工具就好了"的现象，本质是我方未显式声明契约**；凡调外部写接口，正体形态必须**显式写死**。
4. **教训 C（同一条铁律会以新形态复发）**：`铁律 4` 已经为「PATCH 必须带 name」留过一次档，
   本次仍在**同一个接口**上踩到第二条坑 ⇒ 说明"记录一次踩坑"不等于"该接口已被驯服"，
   **同一接口的第二坑要并进同一条纪律**（已登记待放行，见 §2.1）。
5. **未做项（明写，不含糊）**：`SPEC-001 §铁律 4` 的正文**本次未改** —— 属受控修订，需用户放行；本记录只承载证据。
