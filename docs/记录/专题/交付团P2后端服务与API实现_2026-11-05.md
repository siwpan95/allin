## 1. portal bridge 模块实现设计

### 1.1 文件落点与路由注册（对齐 portal src 现有组织）

现状：`index.js` 是**单文件 + createServer 内 if 链分发**（既有 13 路径全部内联，无 Router 抽象）。bridge 若另起文件，不应引入路由框架——落点为：

```

├── index.js        # 现有：在 if 链中新增 2 个 bridge 分支（各 1 行守卫 + 1 行委托）
└── bridge.js       # ★ 新增：聚合与编排两个 payload 函数 + 共享读取器
```

`bridge.js` 不自己 createServer、不 import http——只导出纯数据函数，由 index.js 的既有 `json(res, ...)` 响应器投递。这样 Host 围栏（`hostAllowed`，已在 createServer 最顶端全局生效）与 `loopbackOnly` 的调用方式完全沿用现有模式，**不新增安全判别路径**。

```js
// index.js 内新增（位置：/api/gate-history 分支之后、静态文件回退之前）
if (p === '/api/overview' && req.method === 'GET') {
  if (!loopbackOnly(req, res)) return
  return json(res, 200, await overviewPayload({ readAlerts }))
}
if (p === '/api/orchestration' && req.method === 'GET') {
  if (!loopbackOnly(req, res)) return
  return json(res, 200, await orchestrationPayload(url.searchParams))

```

依赖注入说明：`readAlerts` 目前是 index.js 内部函数（聚合 divergence-events.jsonl）。bridge.js 不反向 import index.js（会成环），由 index.js 以参数注入——与它已注入 `@allin/core` 导出的方式同构，依赖方向仍是 `index → bridge → core/文件`，单向无环。

### 1.2 `/api/overview` 聚合逻辑

**遍历的状态文件与数据源**（全部只读）：

| 数据块 | 来源 | 读取方式 | 开销 |
|---|---|---|---|
| portal | `process.uptime()` / 常量 `port` / package version | 内存 | 0 |
| library.total / invalid | `loadRegistry(REGISTRY)` → `entries.length` / `_valid===false` 计数 | 内存缓存复用 | 低 |
| library.running | 逐条 `isRunning(id)`（pid 0 信号探测 + running.json，launch.js 现成导出） | 每条 O(1) | 低（105+ 条 < 10ms） |
| alerts.last24h / latestTs | 复用既有 `readAlerts()`（已按 ts 倒序、封顶 100） | 文件遍历 | 中（已有函数，不重写） |
| gates | gate-runs.jsonl tail 200（逻辑与既有 `/api/gate-history` 相同） | 文件读 | 低 |
| orchestration | g21 结果 JSON（见 §1.4）→ `{ synced, driftCount }` | 单文件读 | 低 |

关键裁决 **D-B2**：不用 `probeEntry()`。既有 `/api/library` 对 105+ 条目做并行 HTTP 探测（含慢启动宽限期），是它最重的端点；overview 是看板首屏聚合，只回答「总数/活着几个/几个坏」，pid 存活级足够。前端要探测级细节时走既有 `/api/library`（G1 链路本就如此设计）。

**缓存失效策略**（沿 engineCache 惯例）：

```js
// bridge.js
let overviewCache = { at: 0, payload: null }
const OVERVIEW_TTL_MS = 30_000
export async function overviewPayload(deps) {
  if (Date.now() - overviewCache.at < OVERVIEW_TTL_MS && overviewCache.payload) return overviewCache.payload
  overviewCache = { at: Date.now(), payload: await buildOverview(deps) }   // build 失败时不更新缓存，下次重算
  return overviewCache.payload
}
```

- **只有 TTL 失效，不做文件监听**：Windows 上跨进程 FSWatcher 语义不可靠（P1 决策三已实证记录），且单用户形态 30s 陈旧可接受（库页本就有 5s 前端刷新惯例，overview 走 30s 是刻意的降频）。进程重启缓存自然清零。
- build 过程任何子数据源读失败**不整体 500**：对应块降级为 `{ readable:false }`（与 gate-history 的 readable 模式一致），缓存照常写入——坏块 30s 内不自愈是接受的代价，避免坏文件把缓存击穿成每次请求都重读。

### 1.3 `/api/orchestration` 读取逻辑

```js
// bridge.js（示意）
const ALLIN_ROOT = path.join(PLATFORM, '..')                     // PLATFORM 变量 index.js 已定义
const GATE_AUDIT = process.env.ALLIN_GATE_AUDIT || path.join(ALLIN_ROOT, 'tools', 'gate', 'audit')

// g21 产物 v3（2026-11-04 主理人终裁，覆盖此前 agent-parity.json 快照方案）：
// JSONL 逐行快照 tools/gate/audit/g21-runs.jsonl——每行一次运行，5MB 轮转沿 tasks.log 模式；
// 行 schema 基准 = 安智体 §2.4 并入 summary{total,ok,drift}/routesFile/routesReadable，
// side 枚举含 "routes" 第三值，崩溃行含 error{code,msg}。portal 只读「最后一行」= 最新判据快照。
function readLastGateRun(file) {
  const text = fs.readFileSync(file, 'utf8')
  for (let i = text.length - 1; i >= 0; ) {          // 从尾部取最后一个可解析行（容忍末尾坏帧，D1 纪律）
    const end = text.lastIndexOf('\n', i)
    const line = text.slice(end + 1, i + 1).trim()
    i = end
    if (!line) continue
    try { return JSON.parse(line) } catch { continue }
  }
  return null                                        // 文件全空/全坏行
}

export async function orchestrationPayload(params) {
  const include = String(params.get('include') || 'routes,status')   // 逗号分隔白名单
  const result = { readable: true, routes: [], drift: [], lastCheckAt: null, lastCheckError: null,
                    summary: { total: 0, driftCount: 0 }, healthy: false }
  try {
    const j = readLastGateRun(path.join(GATE_AUDIT, 'g21-runs.jsonl'))
    if (!j) { result.readable = false; return result }              // 文件缺失/无可解析行 → 降级，不报错
    if (include.includes('routes')) result.routes = j.routes || []
    if (include.includes('status')) {
      result.drift = j.drift || []
      result.lastCheckAt = j.lastCheckAt || null
      // 门禁自身故障透出：崩溃行的 error{code,msg}，前端据此区分「门禁挂了」与「跑完但全绿」
      result.lastCheckError = j.error
        ? { code: String(j.error.code || 'GATE_CRASHED'), msg: String(j.error.msg || '').slice(-500) }
        : null
    }
    result.summary = { total: result.routes.length, driftCount: (j.drift || []).length }
    // 判红三条件（终裁口径）：routesReadable=false ∨ 任一 drift severity:error ∨ drift>0
    result.healthy = !(j.routesReadable === false
      || (j.drift || []).some(d => d && d.severity === 'error')
      || (j.drift || []).length > 0)
  } catch { result.readable = false }                               // 读取异常 → 降级，不报错
  return result
}
```

降级语义与 P1 契约一致：**文件缺失 → 200 + `readable:false` + 空数组**，绝不 500。前端渲染「编排台账尚未生成，请先跑 g21 门禁」提示。env 覆盖 `ALLIN_GATE_AUDIT` 沿既有 `ALLIN_GATE_RUNS` 的命名惯例（异机/测试可指路）。

### 1.4 裁决 D-B1：routes.yaml 解析方案对比（三选一）

| 方案 | 做法 | 优点 | 缺点 | 裁决 |
|---|---|---|---|---|
| (a) 手写极简 YAML 子集解析器 | Node 侧写 ~80 行解析 routes.yaml 的平面映射子集 | 零依赖字面达成 | ① 双语言双解析器：g21（Python yaml）与 portal（手写）对同一文件各解析一遍，anchor/多行/引号转义任一差异 = 判据结果与展示结果不一致；② YAML 子集是移动的边界——routes.yaml 未来加一个合法 YAML 特性就红；③ 门禁校验的是「Python 眼中的 yaml」，展示的却是「手写解析器眼中的 yaml」，语义漂移恰是本方案要消灭的东西 | **否决** |
| (b) 复用 @allin/core 已有的 js-yaml | portal 直接 `yaml.load(routes.yaml)`（js-yaml 已在 core 依赖树内，非新增依赖） | 解析器成熟 | ① portal 拿到的是**未经门禁校验**的原始文件——展示面与判据面脱钩，g21 红时 portal 仍展示「看似正常」的路由；② bridge 的职责边界被打破：bridge 应读「已验证的事实快照」，不该自担解析职责；③ version 字段/枚举演进时要同时看 yaml 消费方（Node）与生产方（Python）两处代码 | **否决** |
| **(c) g21 产出扁平 JSON，portal 直读** | g21 每次运行结束时把「解析成功且通过校验的路由条目 + 漂移判据结果」以 **JSONL 逐行快照**落 `tools/gate/audit/g21-runs.jsonl`（每行一次运行，5MB 轮转沿 tasks.log 模式；2026-11-04 主理人终裁 v3 定名，覆盖此前 agent-parity.json 单文件快照方案）；portal 只读**最后一行** `JSON.parse` | ① Node 侧零解析代码、零解析语义漂移；② portal 读到的必然是**通过校验的快照**，g21 红/未跑 → 文件缺失/含 drift → 展示面如实反映；③ 与「日志即事实源」纪律同构：g21 产物是治理事实的落盘事实源；④ 单一解析点（Python），单点维护 | 时效性 = 门禁运行频率（非实时）；文件缺失时展示面降级为空 | ✅ **采纳** |

g21-runs.jsonl 单行 JSON 契约（本文顺带定义，g21 专项设计须对齐；v3 终裁后每行 = 一次运行的完整快照）：

```json
{
  "lastCheckAt": "2026-11-04T13:00:00.000Z",
  "routes": [
    { "id": "gitee-release", "skill": "gitee-release", "entry": "tools/gitee_release.py",
      "forms": ["workbuddy", "dsh"], "trigger": "发布|发版|release" }
  ],
  "drift": [ { "routeId": "gitee-release", "side": "routes", "severity": "error", "reason": "anchor missing: <!-- route:gitee-release -->" } ],
  "routesReadable": true,
  "totals": { "routes": 15, "formsWorkbuddy": 15, "formsDsh": 15 },
  "error": { "code": "PARSE_FAILED", "msg": "routes.yaml 解析失败于第 42 行" }
}
```

- `error` 字段仅崩溃行存在（门禁自身故障，如 yaml 解析炸了/IO 异常）；正常完成的行无此字段。portal 以 `lastCheckError` 透出，前端区分「门禁挂了（红 + 故障原因）」与「跑完全绿（绿）」与「判出漂移（红 + 漂移清单）」三态。
- `side` 枚举：`workbuddy` / `dsh` / `routes`（第三值 = routes.yaml 侧自身问题，v3 新增）。

### 2.2 端口发现（复用 data/portal.port）

```js
// services/portalProxy.js（示意）
const fs = require('node:fs');
const path = require('node:path');
const PORT_FILE = process.env.ALLIN_PLATFORM_DIR
  ? path.join(process.env.ALLIN_PLATFORM_DIR, 'data', 'portal.port')
  : path.join(__dirname, '..', '..', '..', 'platform', 'data', 'portal.port');   // website/ → allin/platform/data/
let portCache = { at: 0, port: null };

function discoverPort(ttlMs = 10_000) {
  if (Date.now() - portCache.at < ttlMs && portCache.port) return portCache.port;
  try {
    const raw = fs.readFileSync(PORT_FILE, 'utf8').trim();
    const n = Number(raw);
    portCache = (Number.isInteger(n) && n > 0 && n <= 65535)
      ? { at: Date.now(), port: n }
      : { at: Date.now(), port: null };          // 残留垃圾文件 → 视同未发现，探活兜底
  } catch { portCache = { at: Date.now(), port: null } }
  return portCache.port;
}
```

- portal.port 文件本身有竞态窗口（P1-R1：重启瞬间读到旧端口），**代理不负责解决，只负责优雅暴露**：旧端口 fetch 失败 → `PORTAL_UNREACHABLE` → 看板显示「平台未运行」，10s 端口缓存过期后自动重发现。根治靠演进路径（portal 转常驻），不在代理层打补丁。
- 端口纪律：**绝不硬编码 9000/9900 段**，只信 portal.port 文件（PORT=0 临时端口形态下硬编码必错）。

### 2.3 代理函数签名与超时/错误三分类

```js
/**
 * 代理一次到 portal 的请求。绝不向调用方抛异常——返回结构化结果。
 * @returns {Promise<{ok:boolean, status:number, data?:object, error?:{code, message}, stale?:boolean, snapshotAt?:string}>}
 */
async function proxyPortal({ routePath, method = 'GET', body = null, timeoutMs = 3000 }) {
  const port = discoverPort();
  if (!port) return { ok: false, status: 503, error: { code: 'PORTAL_UNREACHABLE', message: '平台未运行' } };
  const ac = new AbortController();
  const timer = setTimeout(() => ac.abort(), timeoutMs);
  try {
    const resp = await fetch(`http://127.0.0.1:${port}${routePath}`, {
      method,
      headers: { Accept: 'application/json', ...(body ? { 'Content-Type': 'application/json' } : {}) },
      body: body ? JSON.stringify(body) : undefined,
      signal: ac.signal,
    });
    if (resp.status === 403) return { ok: false, status: 502, error: { code: 'PORTAL_FORBIDDEN', message: '平台围栏拒绝（fail-loud，请检查 Host/回环配置）' } };
    const data = await resp.json();
    if (resp.ok) { snapshotSet(routePath, data); return { ok: true, status: 200, data }; }
    return { ok: false, status: 502, error: { code: 'UPSTREAM_ERROR', message: `平台返回 ${resp.status}`, data } };
  } catch (e) {
    if (e.name === 'AbortError') {
      const snap = snapshotGet(routePath);
      return snap
        ? { ok: true, status: 200, data: snap.data, stale: true, snapshotAt: snap.at }   // 超时 → 上次快照 + 时间戳标注
        : { ok: false, status: 504, error: { code: 'UPSTREAM_TIMEOUT', message: '平台响应超时（3s）' } };
    }
    return { ok: false, status: 503, error: { code: 'PORTAL_UNREACHABLE', message: '平台未运行' } };  // ECONNREFUSED 等 TypeError 族
  } finally { clearTimeout(timer); }
}
```

错误码三分类对照（P1 决策三）：`PORTAL_UNREACHABLE`（ECONNREFUSED/端口文件缺失 → 503，前端显示「平台未启动」）；`PORTAL_FORBIDDEN`（上游 403 → 502 包装 + **stderr 打 warn 日志**，围栏被改属 fail-loud 事件，不该静默吞）；`UPSTREAM_TIMEOUT`（AbortError → 有快照给快照、无快照 504，响应带 `stale:true, snapshotAt` 供前端标注「数据截至 HH:MM」）。**绝不把原始 502/ECONNREFUSED 文本吐给页面**。

Host 围栏天然通过：website 服务端 fetch 的 Host 头即 `127.0.0.1:<port>`，命中 portal `LOOPBACK_HOST` 正则；socket 为回环命中 `loopbackOnly`——platform 零改动（决策二已拍板，此处为实证）。

### 2.4 快照缓存（内存，D-B3）

```js
const snapshots = new Map();   // routePath → { data, at }
function snapshotSet(k, data) { snapshots.set(k, { data, at: new Date().toISOString() }) }
```

- **只存内存，重启即失效**：① 决策三明文「website 不持久化任何治理状态」——快照落盘 = 在 website data/ 建治理状态镜像，直接违约；② 单用户场景，重启后下一次成功轮询（≤30s，portal 缓存 TTL 之内）即重建快照，冷启动空窗由 `PORTAL_UNREACHABLE/UPSTREAM_TIMEOUT` 降级文案兜底，代价可忽略；③ 换来零磁盘清理、零敏感状态落 website 库外的额外面。
- 容量上限：仅覆盖固定几个读路径（overview/orchestration/gate-history/library），Map 不会无界；不设 TTL 主动清除——新快照覆盖即失效，语义足够。

写代理的幂等与防抖：portal `start` 对已运行条目返回 `{ok:false, reason:'already-running'}`（launch.js 实证），本身幂等，代理层**不加锁不排队**（单用户无并发写场景）；前端按钮 loading 防双击属 frontend 职责。

### 2.6 audit_log 落点与文案（对齐 notices.js / audit.js 惯例）

| 事件 | action | target | ok | detail |
|---|---|---|---|---|
| 看板页访问 | `governance.view` | `/member/dashboard` | 1 | `portal=<reachable\|unreachable>` |
| 写代理成功 | `governance.entry.start` / `governance.entry.stop` | `<entryId>` | 1 | `pid=<n>` 或 `graceful=true`（取 portal ActionResult 关键字段） |

- 复用既有 `logAudit()`（写失败不拖垮请求，已 handle）；actor 自动为当前会话邮箱。
- 前端 notice 文案新增（NOTICES 表追加，风格对齐现有条目）：

## 3. kernel `allin status` 子命令实现设计

### 3.1 读取面（纯文件，零网络）

| 数据 | 文件 | 解析 |
|---|---|---|
| 平台运行摘要 | `platform/data/running.json`（launch.js 原子写 + .bak） | `{id:{pid,startedAt,owner,command}}`；逐 pid `os.kill(pid,0)` 存活校验，死条目标「陈旧」 |
| 门禁摘要 | `tools/gate/audit/gate-runs.jsonl` | tail 200；`exit!=0` 计数 → 逃逸率、lastRunAt、lastOkAt |
| 编排漂移 | `tools/gate/audit/g21-runs.jsonl`（g21 产物 v3，D-B1 同一份；取尾行） | `totals.routes` + `len(drift)` + `error.code` |
| platform 进程本身 | `platform/data/portal.port` 存在性 | 存在≈portal 曾启动（文件可能残留，标注「待探活」，CLI 不发 HTTP——G3 铁律：不依赖网络） |

### 3.2 落点取舍（D-B4）：新服务 vs 复用 platform_service

| 方案 | 裁决 | 理由 |
|---|---|---|
| (a) 塞进 `platform_service`（check_repos/registry_count 旁边加 `status()`） | 否决 | ① platform_service 的职责是「platform 仓内治理操作」（registry 校验/计数），status 是**跨面聚合**（kernel 门禁 + platform 运行态 + g21 产物三源），塞进去模糊服务边界；② platform_service 已有单一职责的测试面，混入会牵连 |
| (b) allin_cli.py 里直写读文件逻辑 | 否决 | 绕过 kernel 服务分发纪律，CLI 变成第二个实现落点，`allin-governance` 包复用时无法引用（CLI 不是库）；且直 import 文件 IO 进 dispatch 违背「kernel 一切经 SERVICES 白名单挂载」的既有评审口径 |
| **(c) 新增 `kernel/services/status_service.py:StatusService`** | ✅ | registry.py 的扩展纪律明文：「新增一个被内核调度的支柱/工具，只改这张表 + 对应 services/*.py，不再加样板文件」——完全照办 |

接线 diff 级描述（3 处，全部最小增量）：

```python
# kernel/registry.py：SERVICES 增一条（白名单纪律：短名必须命中本表）
SERVICES = { ..., 'status': 'kernel.services.status_service:StatusService' }

# allin 配置 yml（mount_tree 的 config_path(ALLIN_CONFIG) 指向的挂载清单）：增一行 status 服务条目
# allin_cli.py：
#   build_parser():
p_stat = sub.add_parser('status', help='三面贯通只读状态汇总（纯文件，不依赖网络）')
p_stat.add_argument('--json', action='store_true', help='输出机器可读 JSON')
p_stat.add_argument('--strict', action='store_true', help='数据源损坏时退出码升级为 2（供机器消费方 fail-loud）')
#   dispatch():
if args.domain == 'status':
    return ctx.status.summary(as_json=args.json)
```

### 3.3 输出格式

人读（默认，对齐 CLI 中文输出惯例 + `_configure_stdio` UTF-8 已保证）：

```
$ allin status
平台运行    portal 端口文件存在（12345，待探活）；运行中项目 3/105（web_a, web_b, game_c）；陈旧登记 1 条
门禁健康    最近一次 2026-11-04 12:58 全绿；近 200 次逃逸率 2.1%；上次全绿 2026-11-04 12:58
编排台账    15 条路由 · 漂移 0 · 判据时间 2026-11-04 13:00
```

`--json`（供 smoke:e2e 机器断言，对齐 SC6 ⑤「检查点结果可解析」）：

```json
{ "platform": { "portFile": 12345, "running": 3, "total": 105, "stale": 1 },
  "gates": { "lastRunAt": "...", "lastOkAt": "...", "escapeRate": 0.021, "readable": true },
  "orchestration": { "routes": 15, "drift": 0, "lastCheckAt": "...", "readable": true } }
```

**退出码**（2026-11-04 主理人对齐修订，原「恒 0」提案否决，理由：fail-loud 文化）：
- 数据源**缺失**（文件不存在）→ exit 0 + 降级展示「尚未生成」——缺失是正常生命周期状态（g21 未跑过），不是故障；
- 数据源**损坏/不可解析**（文件存在但 JSON/JSONL 解析失败）→ 默认 exit 1；加 `--strict` 时升级 exit 2——损坏才是真异常，strict 模式供 smoke:e2e 等机器消费方 fail-loud；
- 「状态不好」（有漂移/逃逸）永不影响退出码——红不红由 g21/run_all_gates.sh 判，status 不越权当门禁。

## 4. 端点契约总表（含 openapi.yaml 增量对应）

### 4.1 platform 侧（进 `platform/apps/portal/openapi.yaml`，version 0.2.0）

**GET /api/overview** — 同步；入参：无；鉴权：Host 围栏 + loopbackOnly。

```json
{ "portal": { "version": "0.2.0", "uptime": 3600, "port": 53121 },
  "library": { "total": 105, "running": 3, "invalid": 0, "problems": 0 },
  "alerts":  { "last24h": 2, "latestTs": "2026-11-04T12:00:00.000Z" },
  "gates":   { "lastRunAt": "2026-11-04T12:58:00.000Z", "lastOkAt": "2026-11-04T12:58:00.000Z", "escapeRate": 0.021 },
  "orchestration": { "readable": true, "routes": 15, "driftCount": 0 },
  "generatedAt": "2026-11-04T13:05:00.000Z", "cached": false }
```

| 错误码 | 条件 |
|---|---|
| 403 | Host 非回环字面量 / remote 非回环（既有围栏，零新增逻辑） |
| 200 恒定块级降级 | 单数据源读失败 → 对应块 `{readable:false}`，整体仍 200 |

**GET /api/orchestration** — 同步；入参：`?include=routes,status`（缺省两者）；鉴权同上。

```json
{ "readable": true, "lastCheckAt": "2026-11-04T13:00:00.000Z", "lastCheckError": null,
  "healthy": true,
  "routes": [ { "id": "gitee-release", "skill": "gitee-release", "entry": "tools/gitee_release.py", "forms": ["workbuddy","dsh"], "trigger": "发布|发版|release" } ],
  "drift": [], "summary": { "total": 15, "driftCount": 0 } }
```

`lastCheckError`：g21 崩溃行的 `error{code,msg}` 透传（正常完成行为 `null`），前端据此区分「门禁自身故障」与「判据结果」；`healthy` 按判红三条件计算（routesReadable=false ∨ severity:error ∨ drift>0，任一命中即 false）。错误码：仅 403；JSONL 缺失/无可解析行 → 200 + `readable:false`（P1 契约原样落地）。

## 5. 安全实现清单（为什么不扩大 platform 暴露面）

| # | 项 | 来源 | 说明 |
