# SPEC-206 · 公共核边界

> **编号** SPEC-206 ｜ **效力** 准则 ｜ **状态** 生效
> **生效** 2026-11-25 ｜ **最后修订** 2026-11-25 ｜ **适用面** 「什么东西该进公共核（A 层）」——`allin-governance` / `allin-toolkit` 两个发行版、公共文档（纪律 / 指南 / 约定）、以及任何声称「换台机就能用」的产物
> **承载体** `packages/allin-governance/pyproject.toml` + `tools/_shared`（判定器）· `pyproject.toml`（toolkit）· `docs/规范/`·`docs/新人开发上手指南.md`（公共文档）
> **引用格式** SPEC-206 §2（边界四问）· §3（该进）· §4（不该进）· §5（上提流程）

> **为什么需要这一版**：此前「公共核」只有零散口径（「能 pip 装的」「共享的」「不写死机器的」），
> 结果是同一件事反复被误判——机器事实混进公共核（交接卷 §212–214 清了机器 @ 标识）、
> 记录类被当公共文档维护（交接卷 §211 指南写成日志）、包内被写入用户状态（交接卷 §213 VirtualStore）、
> 台账与声明混装（交接卷 §205 / §214）。边界不写成可判定的条件，就只能在每次误判后补一次。
> 参考业界内部平台（IDP）的 golden path / paved road 实践，见 §9「借鉴记账」。

## 1. 三层分域里的位置

公共核 = 三层分域（SPEC-005 §3.10 之外的独立判据，见 `docs/事实源/机器分区索引.md` 头部的分域说明）中的 **A 层**：

```
A 公共核      可 pip 装走 / 可被别的仓直接引用；只读、零机器事实、零项目实例数据
B 事实源      跨机共识（规范 / 台账 / 词表）与各机特化（B'），随仓走、由人维护
C 运行产物    可重建、可删除、不入库（observed / data / dist / 缓存 / 留痕）
```

**A 层只承担「判定与工具」，不承载「今天的事实」。**事实永远在 B，状态永远在 C 或用户目录。

## 2. 边界四问（先问，再决定）

一条内容要不要进公共核，按顺序问四问；**任一问落在右列，就不进**：

| # | 问题 | 落在左列 ⇒ 候选 A 层 | 落在右列 ⇒ 不进 A 层 |
| --- | --- | --- | --- |
| **Q1 复用面** | 若没有公共核，有多少地方要各自实现同一件事？ | **3 处以上**（多机 / 多仓 / 多工具都要） | 只有 1–2 处用 —— 留在原地，等第三个用户出现 |
| **Q2 爆炸半径** | 做错了会不会污染别处？ | 会（判定器判错 → 所有仓/机一起错）；因此**必须只读** | 只影响一个项目自己 |
| **Q3 变化频率** | 它为什么变？ | 跟**安全补丁 / 上游规范 / 判据升级**变（慢、可版本化） | 跟产品需求变（快、项目自己定） |
| **Q4 谁 Maintain** | 破坏时谁被叫起来、有没有权限和上下文？ | 一个人可维护、且他掌握上下文 | 需要「不是维护者的人」被叫起来 —— 说明它根本不该集中 |

> Q4 是最常被跳过的一问，也是「平台变成瓶颈」的根源：**若下游要为上游的组件 on-call，
> 上游就把 on-call 外包了、却没把权限外包。**

## 3. 该进公共核的七类内容

| # | 类别 | 判据（缺一不可） | 本仓实例 |
| --- | --- | --- | --- |
| **A1 判定器** | 把「什么算合规」变成退出码；判据与具体仓无关，输入由调用者给 | 门禁 `g00–g20`、`repocheck` 规则族、`docs_contract`、`facts_drift` |
| **A2 采集器** | 只读采集本机/目录事实，输出结构化；无仓时能降级但不假装 | `facts measure`、`scan`、`deps`、`secrets-scan`、`github` |
| **A3 骨架执行器** | 从**只读模板**生成骨架；生成物不含具体值，值由调用者/后续步骤填 | `init`（空骨架）、`verify`（校验骨架形状） |
| **A4 只读模板与数据** | 模板 = 结构，不是实例；数据 = 只读资产（词库/规则表），且**带许可与来源** | `init` 的骨架模板、`print` 的 allin 词库（15 KB，MIT + SOURCE.txt） |
| **A5 通用工具** | 解决一类通用问题 + 稳定 I/O 契约 + **跑完产出产物**（SPEC-207 判据） | `allin-toolkit` 的 `print/renamer/subtitle/yasuo` |
| **A6 通用文档** | 跨机/跨项目成立的**纪律、指南、约定**；无机器名、无时点值、无项目实例 | `docs/规范/SPEC-*.md`（跨机部分）、`docs/新人开发上手指南.md`、路径与命名约定 |
| **A7 接口契约** | CLI 子命令 + JSON schema + 退出码词汇表；下游可据此编程 | 8 个子命令的 `--help` / `--json` / exit code 语义、`facts.schema.json` |

**A6 的三条硬约束**（交接卷 §211–216 的教训）：

1. **体裁单一**：指南 = 操作手册（只写现在怎么用），记录 = 只增不改的时点证据，二者不得混装；
2. **零特化**：不出现机器名、某机的数字、某项目的实例名 —— 用指针指向各机事实源；
3. **可执行优先**：能写成判据/命令的，不写成散文；写不成判据的，说明它可能不是规范。

## 4. 明确不进公共核的五类

| 类别 | 为什么 | 本仓实例（各自的家） |
| --- | --- | --- |
| **B 实例数据 / 台账** | 是「今天的事实」，会天天变；进包就等于把数据焊进代码 | `tiering / tools / licenses / registry/projects / ports` → `docs/事实源/`、`platform/registry/` |
| **B' 机器特化** | 换机即失效；进公共核即产生两套真相 | 盘位 / 主机名 / `free_gb` / 各机检出集 → `docs/事实源/机器/<机>.md` + `facts/machine/<机>.json` |
| **项目专属集成** | 只对本仓布局成立（装配自己 ≠ 通用能力） | `kernel/` 的 cordis 装配、`platform/` 的门户与 CLI 总线、`preset/` |
| **记录类** | 时点证据，只增不改；属于用户层/运行时 | 交接卷（共持，按机索引）、月账（划归各机事实源）、审计报告 → `docs/记录/` 与 `docs/事实源/机器/<机>/月账/` |
| **运行产物** | 可重建、可删、不该入库 | `platform/registry/observed/`、`platform/data/`、`dist/`、缓存与日志 |

**「暂时放在公共核里」不是选项**：如果它属于上面五类之一，进公共核就是错的，
无论当前只有一处用、或者「以后可能复用」。等第三个用户出现再上提（Q1）。

## 5. 上提流程（自扫门前雪 → 提炼 → 上提）

```
各机/各项目自己解决  ──沉淀──▶  本机事实源 / 本机月账 / 项目仓内实现
        │                                    │
        │                    提炼（去掉实例数据、机器特化、项目耦合）
        ▼                                    ▼
   不进公共核                    ┌───────────────────────┐
   （只在本地有效）               │ 公共核候选：判据 + 接口 + 模板 │
                                └───────────┬───────────┘
                                            │ 三处以上复用（Q1）+ 只读（Q2）
                                            ▼
                                     进 A 层（版本化）
```

- **上提四步**：① 抽成判据/命令/模板（去掉实例值）② 定 I/O 契约（`--help`/`--json`/退出码）
  ③ 加自检（`--selftest` 或门禁夹具）④ 记账（来源、许可、影响面）。
- **不许反向**：不得先在公共核里写、再靠机器标识「混血」各机内容（交接卷 §214 教训）。
- **版本与弃用**：破坏性变更升主版本并在 CHANGELOG 写明；弃用先公告窗口，
  下游仍能 pin 旧版 —— 「被维护」是 A 层的义务，不是姿态。

## 6. 怎么判一个东西现在该不该在 A 层（体检）

```bash
# 1) 包里有没有机器特化 / 实例数据（应为 0）
python tools/machine_content_audit.py

# 2) 包映射与仓内真身是否一致（防止「进了 wheel 但没人核对」）
python tools/check_pkg_parity.py

# 3) 包内是否被运行时写入（安装目录只读，见 README「运行时可写位置」）
#    跑一遍工具后看安装目录有无 cache / 用户数据

# 4) 换台机（或干净 venv、cwd 不在仓内）能不能站起来
python -m venv /tmp/v && /tmp/v/Scripts/python -m pip install allin-governance
/tmp/v/Scripts/allin-governance facts measure        # 期望 exit 0，缺仓时如实标「未采集」
```

四条全绿 = 当前 A 层是干净的；任一条红，按 §4 归位，而不是「加个豁免」。

## 7. 例外与已知边界

| 项 | 处理 | 理由 |
| --- | --- | --- |
| `vendor/cordis` | **留仓内**，不抽 A 层 | 上游许可随上游；且它是「装配器」依赖，不是通用能力（Q1 只 1 处） |
| `kernel/` | 留仓内 | 装配的是本仓布局；换机需要的是「采集/扫描/体检」，不是「装配自己」 |
| `platform/` 代码 | 留仓内 | 门户/CLI/MCP 总线服务于本仓治理台；可移植性已单独整改，但复用量不足 Q1 |
| 门禁夹具 | 随包（属 A1） | 判据的自证必须在包内可跑，否则「装完包跑不了门禁」 |
