### 117.1 外部图谱：AgentOps 是什么

- **核心命题**：AgentOps 是 LLMOps 之上新的一层。LLMOps 的产物是「prompt + 检索」，
  AgentOps 的产物是**执行图（execution graph）** —— agent 会调工具、产生副作用、链条式执行，
  于是失败模式从「自信地说错一句话」变成「**做了无法解释、无法回滚的动作**」。
- **业界五层**（缺口自下而上加剧：MLOps 高 → LLMOps 中 → AgentOps 低）：
  ① **编排**（状态机式工作流、审批节点；LangGraph / CrewAI / AutoGen）→
  ② **工具面**（**窄化**类型化工具、运行时策略网关、幂等键）→
  ③ **检索**（混合检索 + 重排 + 权限感知；LlamaIndex / RAGAS）→
  ④ **评估**（版本化数据集、CI 门禁、LLM-as-a-Judge、红队；OpenAI Evals）→
  ⑤ **可观测**（分布式 trace、**OTel GenAI 语义约定**、成本/延迟；LangSmith / Langfuse / Phoenix）。
- **最该抄的一条**：**OpenTelemetry GenAI 语义约定** —— `gen_ai.request.model`、`gen_ai.usage.input_tokens`、
  `gen_ai.tool.name` 等**标准属性名**，一次埋点、任意后端可读，避免 vendor lock-in。
  （注：OTel GenAI 约定**尚未覆盖 eval 分数与人类标注**，属厂商扩展字段 —— 评估层仍需自建。）
- **MCP 可观测性（2026 新增要点）**：要记 server 身份（name/version/来源/传输）、**完整参数**（schema 合法≠无注入载荷）、
  输出规模与目的地（异常放大或含陌生域名 = 外泄特征）、授权身份、**跨 server 调用序列**
  （「读 Jira → 立刻写 GitHub」是影子攻击指纹）。
- **成本**：Agent 的成本是**路径相关**的 —— 同一任务，调 3 次工具比调 1 次贵；
  业界共识是「**步数预算 + token 预算 + 熔断器**」三重闸门，触顶即**确定性降级**（澄清提问 / 升级人工 / 降级模型），
  **不允许静默烧钱**。
- **红队**：场景须**版本化为数据**（非 notebook 里的散装 prompt），每次生产事故转为**脱敏回归用例**；
  oracle 不能只看回复文本，要看**实际工具调用 / 数据去向 / 文件变更 / 授权决策**（agent 可能嘴上拒绝、手上已动手）。

### 117.2 allin 现状实证：它**已经是**一个 AgentOps 平台，只是用治理语言写的

> 逐文件核实后的事实是 —— allin 已把 AgentOps 五层里的**三层**做得比多数团队成熟，
> **缺的恰好是评估层与「agent 侧观测」**。**因此本轮结论是「扩展」而非「引入」**。

### 117.3 规划建议（按投入产出排序，含「不做什么」）

- **P0-① agent 侧 trace 补齐** —— **不引入任何新工具链**。复用 `gate-runs.jsonl` 的同款 append-only 范式，
  新增 `tools/gate/audit/agent-runs.jsonl`：每次 agent 任务落 `trace_id / 步数 / 工具调用序列 / 决策点 / 耗时`；
  再给 `gate_metrics.py` 增第 5 类指标：**agent 任务成功率与步数分布**。
  ⇒ 这是 AgentOps 定义的**最小闭环**，把 allin 从「治理平台」升级为「agent 运行观测平台」。
- **P0-② 修 `mcp-actions.jsonl` 落痕** —— `index.js` 的 `auditWrite()` 已写好 `appendFileSync`，但该文件**至今不存在**
  ⇒ 要么查调用链断点，要么补一条自检（「写工具必须留痕」）。
  对应 AgentOps 硬原则：**遥测由中间件发出，不由模型自述** —— allin 这条设计已对，只是没落地。
- **P1-① `agent_regression` 升级为 eval harness** —— 三件事：
  ① **golden set 版本化**（当前样例**内嵌在代码里**，改了看不出回归）→
  ② **通过率基线 + 版本间 diff**（「改 prompt 修好 1 个、悄悄弄坏 5 个」必须能发现）→
  ③ **CI 门禁化**（**已挂在 `run_all_gates.sh` 里，差的是基线与 diff**）。
- **P1-② 工具面加「窄化 + 预算」** —— 工具面已窄（13 个、语义清晰），缺 AgentOps 两个标配：
  **每次运行的工具调用次数上限**（防 agent 在自己尾巴上烧钱）+ **不可逆操作显式审批**（现仅 2 个写工具需 `confirm`，
  可扩展为三级：**只读 / 可逆写 / 不可逆**）。
- **P2-① 检索层走向混合检索** —— allin 文档高度结构化（事实源/规范/记录分层），做 **BM25 + 结构化字段权重**收益高、成本低。
  ⚠ **明确不做：不上向量库** —— allin 的价值主张是「确定性、可审计、零外部依赖」，
  引入 embedding 模型会打破该属性，与 `SPEC-001` 铁律取向冲突。宁可做**引用可验证性**（grounding：
  agent 答「合同到 3 月 15 日」时能指回源文档的哪一行）。
- **P2-② 字段名向 OTel GenAI 对齐（不换栈）** —— 不引入 OTel SDK，但把自产字段名**向 `gen_ai.*` 命名靠拢**，
  将来若接 Phoenix/Langfuse/自有 collector，映射是机械工作，不需重写埋点 ⇒ **零锁定成本**。
- **⚠ 明确不做（与本仓取向冲突）**：**不引入 Langfuse / LangSmith / Phoenix 等外部 AgentOps 平台**。
  理由：它们是 SaaS 或需独立部署，与 allin「零外部依赖、可审计、单仓自持」的取向冲突（见 `SPEC-001` 铁律与
  `platform/AGENTS.md` 的 fail-loud / 原子写纪律）。**引入外部 AgentOps 栈会削弱而非增强本仓的差异化**。
  （工具生态调研已做，结论是**借鉴范式、不借工具**。）

纪律执行了、判据却假失败；若不先做负向自测，这次会白重下 45 MB。

|---|---|---|
| 元信息 | `curl` 无 token 打 `/api/v5/repos/...` | `public=true`、`private=false`、`permission=null` |
